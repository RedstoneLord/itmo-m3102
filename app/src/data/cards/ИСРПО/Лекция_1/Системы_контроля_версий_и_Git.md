@@ id=vcs-why type=concept src="Хронология"
Q: Зачем нужна система контроля версий (VCS) и чем она лучше, чем папка с копиями вида `проект_финал`, `проект_финал2`?
A:
VCS отслеживает изменения в файлах проекта и **хранит все их версии**. Из этого следует то, чего папки с копиями не дают:

- **история**: кто, когда и зачем изменил (сообщение коммита), можно сравнить любые две версии;
- **откат**: вернуться к рабочему состоянию, если правка всё сломала;
- **совместная работа**: несколько человек правят один проект, а изменения потом объединяются (а не перезаписывают друг друга);
- **параллельные линии работы** (ветки): новую функцию можно писать, не ломая стабильную версию.

Когда не нужна: разовый файл, который никто не будет менять и возвращать к старым версиям.

@@ id=vcs-generations type=compare src="Хронология"
Q: Сравни три поколения систем контроля версий: что отслеживали, как была устроена работа и сеть, какие системы к ним относятся.
A:

| Ось                    | 1-е поколение                  | 2-е поколение                                            | 3-е поколение                                       |
| ---------------------- | ------------------------------ | -------------------------------------------------------- | --------------------------------------------------- |
| Системы                | SCCS (1972), RCS (1982)        | CVS (1986), SVN (2000)                                   | Git (2005), Mercurial (2005)                        |
| Что отслеживают        | отдельные файлы, не проект     | —                                                        | проект целиком (коммит — снимок всего проекта)      |
| Сеть                   | нет, только локальная работа   | есть: общий сервер                                       | есть, но у каждого своя полная копия репозитория    |
| Одновременная работа   | один пользователь за раз       | несколько разработчиков с одними и теми же файлами       | несколько, у каждого свои ветки и локальная история |
| Где «официальная» версия | на одном компьютере          | в **центральном репозитории** на сервере                 | по договорённости команды (обычно общий сервер, но технически он такой же репозиторий, как у всех) |

Главный сдвиг 1→2: **сеть и общий репозиторий**. Главный сдвиг 2→3: репозиторий **не один на всех, а у каждого целиком** (распределённая модель) и Git быстрее и гибче предшественников.

@@ id=gen1-limits type=concept src="Первое поколение"
Q: Какие два ограничения были у систем первого поколения и почему из-за них нельзя было нормально работать над проектом командой?
A:
1. Отслеживали изменения только в **отдельных файлах**, а не в проекте целиком. Правка, затрагивающая два файла (функцию и её вызов), не фиксировалась как единое целое: версию «всего проекта на такой-то момент» получить было нельзя.
2. Редактирование было **только локальным и одним пользователем за раз**. Сети не было, поэтому двое не могли одновременно работать с одним файлом, а общего хранилища не существовало.

Примеры: **SCCS** (1972, Марк Рочкинд, Bell Labs) — одна из первых успешных систем; **RCS** (1982, Уолтер Тихи) написана как альтернатива SCCS, которая тогда не была опенсорсной.

@@ id=gen2-central type=concept src="Второе поколение"
Q: Что принесла сеть во втором поколении (CVS, SVN) и какие у модели «централизованный репозиторий» плюсы и минусы?
A:
Сеть дала **централизованное хранилище** с «официальными» версиями проектов. **CVS** (1986, Дик Грун) впервые позволила **нескольким разработчикам одновременно работать с одними и теми же файлами**: каждый берёт версию с сервера и отправляет изменения туда же.

- Плюсы: одна «правда» для всей команды, простая модель, легко управлять доступом.
- Минусы (общее знание о модели, в конспекте не расписано): сервер — единая точка отказа; без сети нельзя сохранить версию и посмотреть историю, потому что полная история лежит только на сервере.

Третье поколение (Git) убирает эту зависимость: полная копия истории есть у каждого.

@@ id=svn-pitfall type=pitfall src="Второе поколение"
Q: SVN создана в 2000 году, а Git — в 2005. Значит ли это, что SVN «примерно как Git, только старее»? Что общего у SVN и CVS?
A:
Нет. Поколение определяется **моделью работы**, а не датой. **SVN (Subversion)** — «более надёжное централизованное решение, чем CVS» (создана Collabnet Inc., сегодня поддерживается Apache Software Foundation) и, как и CVS, использует **модель централизованного репозитория**: общий сервер, история на нём. Это второе поколение.

Git принадлежит третьему: у каждого разработчика полная копия истории. Поэтому на вопрос «какие системы централизованные» ответ — CVS и SVN, а SCCS и RCS (локальные) и Git (распределённый) — нет.

@@ id=gen3-git type=concept src="Третье поколение"
Q: Чем Git (третье поколение) принципиально отличается от CVS/SVN и откуда он взялся?
A:
Git создал в 2005 году Линус Торвальдс (создатель Linux): сначала для кодовой базы Linux, потом он стал самой популярной системой управления версиями. Написан в основном на C с командными сценариями; отличается от предшественников функциями, гибкостью и скоростью. В том же 2005 году появился Mercurial (Мэтт Макколл).

Принципиальное отличие модели: Git **распределённый**. `git clone` приносит **всю историю**, коммиты создаются локально без сети, ветки дёшевы, а `git push` / `git pull` лишь синхронизируют репозитории. Центральный сервер остаётся соглашением команды, а не технической необходимостью.

@@ id=object-store type=concept src="Что внутри?"
Q: Что происходит с содержимым файла, когда он добавляется для отслеживания, и как устроена база объектов `.git/objects`?
A:
С содержимым делаются две вещи:

1. оно **сжимается** алгоритмом **zlib**;
2. для него вычисляется хэш **SHA-1**.

Git кладёт результат в **базу объектов** `.git/objects`: **имя файла-объекта — хэш**, а внутри — сжатое содержимое (на диске первые два символа хэша — имя подпапки, остальные — имя файла). Новый объект создаётся каждый раз, когда добавляют новый файл или новую версию существующего.

```diagram
diagram
F: box "Содержимое файла" @ 90, 110
H: box "SHA-1" @ 290, 50
Z: box "zlib" @ 290, 170
O: db ".git/objects" @ 490, 110
F -> H : хэш
F -> Z : сжатие
H -> O : имя объекта
Z -> O : содержимое
```

@@ id=content-address type=concept src="Что внутри?"
Q: Почему именем объекта служит хэш содержимого, а не имя файла? Что это даёт и чем хэш отличается от имени исходного файла?
A:
Хэш вычисляется **только по содержимому**, поэтому он «уникален»: другое содержимое — другой хэш. Следствия:

- одинаковое содержимое хранится **один раз** (дедупликация), как бы файл ни назывался и где бы ни лежал;
- изменённый файл — **новый объект**, а старый остаётся: так хранится история;
- **целостность**: если объект повредился, его содержимое перестанет давать своё имя-хэш, и порчу видно.

Не путать: имя исходного файла (`a.txt`) и хэш — разные вещи. В базе объектов файл называется хэшем, имени `a.txt` внутри содержимого нет (его хранит другой объект — дерево, см. следующую карточку).

@@ id=same-content type=calc src="Что внутри?"
Q: В репозитории два файла, `a.txt` и `docs/b.txt`, с абсолютно одинаковым текстом. Сколько объектов с содержимым файла создаст `git add` для них? А если затем изменить один символ в `a.txt` и снова сделать `git add`?
A:
- Первый `git add`: **один** объект. Содержимое одинаково → одинаковый SHA-1 → один файл в `.git/objects`; оба имени ссылаются на него.
- Изменили символ в `a.txt` и добавили снова: у нового содержимого другой хэш, создаётся **второй** объект. Первый остаётся — на него по-прежнему указывает `docs/b.txt` и старые коммиты.

Итого два объекта, а не три: количество объектов зависит от различного содержимого, а не от числа файлов и операций добавления.

@@ id=object-model type=concept src="Что внутри?"
Q: Из каких видов объектов состоит история Git и чем коммит отличается от «набора изменений»?
A:
- **blob** — содержимое одного файла (то, что мы разобрали выше), без имени;
- **tree** — каталог: список «имя → blob или вложенное tree»;
- **commit** — ссылка на корневой tree (снимок всего проекта), ссылки на **родительские коммиты**, автор, дата и сообщение.

```diagram
diagram
K2: round "коммит C2" @ 90, 40
K1: round "коммит C1" @ 90, 170
T2: box "tree (снимок C2)" @ 310, 40
T1: box "tree (снимок C1)" @ 310, 170
B1: db "blob a.txt v1" @ 530, 170
B2: db "blob a.txt v2" @ 530, 40
K2 -> K1 : родитель
K2 -> T2
K1 -> T1
T2 -> B2
T1 -> B1
```

Коммит — **снимок** проекта, а не дифф: хэш коммита зависит от дерева, родителей, автора и сообщения. Поэтому любое изменение «старого» коммита (`--amend`, `rebase`) даёт коммит с **новым хэшем** — это объясняет, почему переписывать отправленную историю опасно.

@@ id=branch-head type=concept src="Что внутри?"
Q: Что такое ветка и что такое `HEAD` в Git? Почему создание ветки происходит мгновенно?
A:
**Ветка** — это просто **указатель на коммит** (файл с хэшем коммита). **`HEAD`** — указатель на то, где мы сейчас: обычно на **текущую ветку**, а через неё — на последний коммит.

При новом коммите Git создаёт коммит с родителем «текущий коммит» и **сдвигает вперёд только текущую ветку**; остальные ветки остаются на месте.

```diagram
diagram
C1: round "C1" @ 60, 110
C2: round "C2" @ 180, 110
C3: round "C3" @ 300, 110
M: note "main" @ 300, 30
H: note "HEAD" @ 420, 30
C2 -> C1
C3 -> C2
M --> C3
H --> M : текущая ветка
```

Создать ветку — записать один указатель, копировать файлы не нужно, поэтому ветки в Git дешёвые и их создают под каждую задачу.

@@ id=init-clone type=compare src="Создание и получение репозитория"
Q: Сравни `git init` и `git clone <url>`: что создаётся и в какой ситуации какая команда нужна.
A:

| Ось              | `git init`                                        | `git clone <git-url>`                                          |
| ---------------- | ------------------------------------------------- | -------------------------------------------------------------- |
| Результат        | в текущем каталоге создаётся скрытая папка `.git` | загружается копия репозитория по URL                           |
| История          | пустая, коммитов нет                              | вся история с сервера                                          |
| Связь с сервером | нет, потом `git remote add origin <url>`          | сразу настроена (удалённый репозиторий `origin`)               |
| Когда            | проект начинается у вас; уже есть папка с файлами | проект уже лежит на сервере и вы подключаетесь к работе        |

После `init` файлы в каталоге остаются **неотслеживаемыми**, пока их не добавят (`git add`) и не закоммитят.

@@ id=dot-git type=pitfall src="Создание и получение репозитория"
Q: Что находится в папке `.git` и что случится, если её удалить?
A:
`.git` — это и есть репозиторий: база объектов `.git/objects` со всеми версиями файлов, указатели веток и `HEAD`, настройки, промежуточная область. Остальное в каталоге — просто рабочие файлы текущей версии.

Если удалить `.git`, каталог перестанет быть репозиторием: файлы останутся как есть, но **история, ветки и неотправленные коммиты пропадут**. Если проект есть на сервере, можно снова `git clone`; если нет, восстановить историю нечем. Поэтому `.git` не копируют и не удаляют случайно, а отправка на сервер (`git push`) — ещё и резервная копия.

@@ id=three-areas type=concept src="Фиксация изменений"
Q: Из каких трёх «мест» состоит локальная работа с Git, какие команды переносят изменения между ними и зачем нужна промежуточная область?
A:
1. **Рабочий каталог** — файлы, с которыми вы работаете.
2. **Промежуточная область** (индекс) — то, что войдёт в следующий коммит.
3. **Репозиторий** — зафиксированные коммиты.

```diagram
diagram
W: box "Рабочий каталог" @ 90, 80
S: box "Промежуточная область" @ 300, 80
L: box "Локальные коммиты" @ 510, 80
W -> S : git add
S -> L : git commit
```

`git add` кладёт файл в промежуточную область (при этом создаётся объект в базе). Область нужна, чтобы **собрать коммит из части изменений**: изменили десять файлов, но к одной задаче относятся три — добавляем их, коммитим, остальные остаются изменёнными, но не зафиксированными. Так история состоит из осмысленных коммитов, а не «всё, что было в каталоге».

@@ id=add-after-edit type=code src="Фиксация изменений"
Q: Какая версия `a.txt` попадёт в коммит и что покажет `git status` в конце?

```bash
echo "v1" > a.txt
git add a.txt
echo "v2" > a.txt
git commit -m "Add a.txt"
git status
```
A:
В коммит попадёт **`v1`**. Коммит берёт содержимое **промежуточной области**, а не рабочего каталога: на момент `git add` в ней зафиксировано `v1`, последующая правка до индекса не дошла.

`git status` в конце сообщит, что `a.txt` изменён и **не добавлен** для коммита (в каталоге `v2`, в последнем коммите `v1`). До коммита файл числился бы сразу в двух списках: «подготовлено к коммиту» (версия `v1`) и «изменено, не подготовлено» (`v2`).

Правило: поправил файл после `git add` — сделай `git add` ещё раз.

@@ id=commit-effect type=concept src="Фиксация изменений"
Q: Что именно делает `git commit -m 'Commit message'` и что остаётся нетронутым? Что будет, если выполнить его, не сделав `git add`?
A:
Команда фиксирует набор изменённых файлов и папок, **подготовленных в промежуточной области**, в новый коммит с сообщением из `-m`. Новый коммит получает родителем прежний текущий коммит, а текущая ветка сдвигается на него.

Нетронутыми остаются изменения вне промежуточной области: неотслеженные файлы и правки, на которые не было `git add`. Если не добавить ничего, коммитить нечего: Git ответит, что нет изменений, подготовленных к коммиту (`nothing added to commit`), и пустого коммита не создаст.

Короткий путь для **уже отслеживаемых** файлов — `git commit -a`, он добавляет их правки сам, но **новые** файлы всё равно надо добавить вручную.

@@ id=amend type=pitfall src="Фиксация изменений"
Q: Что на самом деле делает `git commit --amend` и почему его нельзя использовать после `git push`?
A:
В конспекте описано изменение сообщения последнего коммита. Точнее: `--amend` **заменяет последний коммит новым**. Можно поменять сообщение, а если перед этим сделать `git add`, то и добавить в него забытые изменения.

Раз заменяется весь коммит, у него **новый хэш** (хэш зависит от дерева, родителя и сообщения). Старый коммит остаётся лишь в журнале `git reflog`. Если старый уже отправлен на сервер, у коллег он есть, а у вас история пошла по другому коммиту: обычный `git push` отклонят, а принудительный перепишет общую историю и сломает чужие копии.

Вывод: `--amend` — только для коммитов, **ещё не отправленных** (`git push`); для уже отправленных создают новый коммит или `git revert`.

@@ id=commit-practice type=pitfall src="Фиксация изменений"
Q: Какие типичные ошибки делают при коммитах и как выглядит хороший коммит?
A:
Плохо:

- один огромный коммит «всё сразу», в нём перемешаны несколько задач;
- сообщение `fix`, `123`, `финал` — через месяц непонятно, что и зачем менялось;
- `git add .` вслепую: в коммит уезжают лишние файлы (сборка, личные настройки, пароли и токены), а удалить их из истории потом трудно.

Хорошо: **один коммит — одно логическое изменение** (его можно откатить отдельно), сообщение коротко говорит, **что** сделано и **зачем**, перед коммитом проверен `git status`.

@@ id=status-log type=compare src="Состояние и история"
Q: Чем отличаются `git status` и `git log`, на какой вопрос отвечает каждая и какой командой посмотреть, что именно изменилось в файлах?
A:

| Команда      | Вопрос                              | Что показывает                                                                                      |
| ------------ | ----------------------------------- | --------------------------------------------------------------------------------------------------- |
| `git status` | «что происходит сейчас?»            | текущую ветвь, неотслеженные файлы, изменённые файлы, подготовленные к коммиту                      |
| `git log`    | «что уже зафиксировано?»            | историю коммитов активной ветви от текущего коммита назад, с хэшами и сообщениями                  |
| `git diff`   | «что именно поменялось в строках?»  | правки, ещё не добавленные в индекс; `git diff --staged` — то, что подготовлено к коммиту           |

`status` показывает **файлы**, `diff` — **строки**, `log` — **коммиты**. Удобный вид истории: `git log --oneline --graph --all` (граф всех веток).

@@ id=branch-cmds type=code src="Ветви"
Q: На какой ветви вы окажетесь и что изменится после каждой серии команд?

```bash
# (а)
git branch feature
# (б)
git checkout feature
# (в)
git checkout -b hotfix
```
A:
- (а) `git branch feature` **только создаёт** указатель `feature` на текущий коммит. Вы остаётесь на прежней ветви: `git branch` без аргументов выведет список, текущая помечена `*`.
- (б) `git checkout feature` **переключает** рабочий каталог и `HEAD` на `feature`. Новые коммиты теперь пойдут в неё.
- (в) `git checkout -b hotfix` = создать ветвь `hotfix` от текущей и сразу на неё перейти (в новых версиях Git — `git switch -c hotfix`).

Типичная ошибка: создать ветвь через `git branch`, не переключиться и закоммитить — коммит попадёт в **старую** ветвь.

@@ id=checkout-effect type=concept src="Ветви"
Q: Что делает `git checkout <branch>` с `HEAD`, с файлами и с несохранёнными изменениями?
A:
Команда извлекает ветвь в рабочий каталог:

1. `HEAD` переставляется на указанную ветвь;
2. промежуточная область и файлы в каталоге **заменяются снимком** последнего коммита этой ветви (файлы появляются, исчезают, меняют содержимое).

Несохранённые изменения Git не теряет молча. Если они **не пересекаются** с тем, что меняется при переключении, они переезжают вместе с вами; если пересекаются, Git **откажется переключаться** и попросит сначала закоммитить изменения или временно убрать их (`git stash`). Поэтому перед переключением полезен `git status`.

@@ id=merge-ff type=concept src="Ветви"
Q: Что делает `git merge <branch>`, в какую ветвь вливаются изменения и когда обходится без нового коммита (fast-forward)?
A:
Команда объединяет указанную ветвь с **текущей**: вливаются изменения `<branch>` в ту, что извлечена (`HEAD`), а `<branch>` остаётся как была. Для `git merge feature` из `main` меняется только `main`.

Два исхода:

- **fast-forward** — текущая ветвь **не отходила от `<branch>`**, то есть её последний коммит — предок вливаемой. Git просто **сдвигает указатель** вперёд, нового коммита нет, история остаётся линейной.
- **настоящее слияние** — обе ветви получили свои коммиты после общего предка (разошлись). Git создаёт **коммит слияния** с двумя родителями (см. следующую карточку).

@@ id=merge-three-way type=concept src="Ветви"
Q: Как Git объединяет две разошедшиеся ветви и чем коммит слияния отличается от обычного?
A:
1. Git находит **общего предка** — последний коммит, от которого ветви разошлись.
2. Сравнивает с предком обе вершины. Правки в **разных файлах или разных местах** файла объединяет автоматически.
3. Результат записывает в **коммит слияния** — коммит с **двумя родителями**; текущая ветвь сдвигается на него.

```diagram
diagram
C1: round "C1" @ 60, 100
C2: round "C2 (общий предок)" @ 190, 100
C3: round "C3 (main)" @ 340, 30
F1: round "F1" @ 340, 170
F2: round "F2 (feature)" @ 480, 170
M: round "M (слияние)" @ 620, 100
C2 -> C1
C3 -> C2
F1 -> C2
F2 -> F1
M -> C3 : родитель 1
M -> F2 : родитель 2
```

Стрелки — ссылки на родителя. Ветвь `feature` после слияния остаётся и при желании удаляется отдельно (`git branch -d feature`).

@@ id=conflict-what type=concept src="Ветви"
Q: Когда при слиянии возникает конфликт, почему Git не может решить его сам и значит ли это, что что-то сломалось?
A:
Конфликт — ситуация, где **обе ветви изменили одно и то же место** относительно общего предка (одни и те же строки файла; или один удалил файл, а другой его правил). Автоматически выбрать нельзя: Git не знает, какую версию оставить и как их совместить.

Это **не поломка**, а обычная приостановка: слияние остановлено, файлы с конфликтом помечены в `git status` как `both modified`, остальное объединено. Правки в **разных** местах конфликта не вызывают. Решение принимает человек.

@@ id=conflict-resolve type=code src="Ветви"
Q: После `git merge feature` Git сообщил о конфликте, и в файле появилось такое. Что означают метки и как довести слияние до конца или отменить его?

```text
<<<<<<< HEAD
print("hello")
=======
print("hi")
>>>>>>> feature
```
A:
Метки показывают оба варианта:

- между `<<<<<<< HEAD` и `=======` — версия **текущей ветви** (в которую вливаем);
- между `=======` и `>>>>>>> feature` — версия **вливаемой ветви**.

Порядок решения:

1. `git status` — список файлов с конфликтом (`both modified`).
2. Открыть файл, оставить **итоговый текст** (один из вариантов или их сочетание) и **удалить все три метки**.
3. `git add <файл>` — отметить конфликт решённым.
4. `git commit` — завершить слияние (сообщение уже подставлено).

Передумали — `git merge --abort` вернёт состояние до слияния. Ошибка: закоммитить файл с оставшимися метками `<<<<<<<` — они попадут в код.

@@ id=rebase-idea type=concept src="Ветви"
Q: Что делает `git rebase main`, когда выполнен на ветви `feature`, и почему после него хэши коммитов `feature` другие?
A:
`rebase` **переносит коммиты** текущей ветви: Git берёт коммиты, которых нет в `main` (после общего предка), и **заново применяет их по одному поверх конца `main`**. Ветвь `feature` как будто начата от свежего `main`.

```diagram
diagram
C1: round "C1" @ 60, 100
C2: round "C2" @ 180, 100
C3: round "C3 (main)" @ 300, 100
F1: round "F1′" @ 420, 100
F2: round "F2′ (feature)" @ 540, 100
C2 -> C1
C3 -> C2
F1 -> C3
F2 -> F1
```

До rebase `F1` и `F2` были ответвлены от `C2`. После — копии `F1′` и `F2′` стоят поверх `C3`: у них **новый родитель, значит новые хэши**; старые `F1`, `F2` остаются лишь в `git reflog`. Затем `git checkout main && git merge feature` — это **fast-forward**, история прямая.

@@ id=merge-vs-rebase type=compare src="Ветви"
Q: Сравни `merge` и `rebase`: форма истории, судьба коммитов, конфликты, безопасность для общих веток. Когда что выбирать?
A:

| Ось                 | `git merge`                                                | `git rebase`                                                              |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------- |
| История             | сохраняется как была, появляется коммит слияния с двумя родителями | линейная: коммиты ветви стоят поверх базовой                              |
| Коммиты             | остаются прежними (те же хэши)                             | пересоздаются (новые хэши)                                                |
| Конфликты           | решаются **один раз**, в коммите слияния                   | могут возникать на **каждом** переносимом коммите (`git rebase --continue`) |
| Общие ветви         | безопасен: ничего не переписывает                          | **опасен** для уже отправленных коммитов                                  |
| Когда               | вливаем готовую ветку в общую (`main`), нужен след слияния | привели свою **локальную** ветку к свежему `main` до слияния               |

Правило: **не делай rebase коммитов, которые уже отправлены и на которых могли основать работу другие.** Ветвь, переписанная после `push`, отправляется только принудительно (`git push --force-with-lease`), а у остальных история разойдётся с вашей.

@@ id=fetch-pull type=concept src="Обмен с удалённым репозиторием"
Q: Что делает `git pull` по шагам и чем он отличается от `git fetch`? Когда после него возникает слияние или конфликт?
A:
`git pull` = **`git fetch`** (скачать из удалённого репозитория новые коммиты и подвинуть `origin/<ветвь>`) **+ слияние** этих изменений в текущую ветвь (с настройкой `pull --rebase` вместо слияния — rebase). В итоге в рабочую копию объединяются зафиксированные изменения, которые есть на сервере, но не у вас.

`git fetch` только **скачивает** и не трогает ни вашу ветвь, ни файлы — безопасно посмотреть, что нового, до слияния.

Если ваша ветвь тоже ушла вперёд, `pull` создаст коммит слияния; если те же строки правили и вы, и коллеги, получится **конфликт** — решается так же, как при `git merge`.

@@ id=push-what type=concept src="Обмен с удалённым репозиторием"
Q: Что переносит `git push` и почему сервер может его отклонить?
A:
`git push` упаковывает свободные объекты локальных коммитов активной ветви в файлы пакета (packfile) и переносит их в удалённый репозиторий; ветвь на сервере сдвигается на ваш последний коммит. Отправляются только объекты, которых там ещё нет.

Сервер **отклонит** push, если на нём уже есть коммиты, которых у вас нет: ветвь на сервере ушла вперёд, и сдвинуть её на ваш коммит значило бы потерять чужие. Это выглядит как `rejected … fetch first / non-fast-forward`.

Выход: `git pull` (получить чужие коммиты и объединить), решить конфликты, затем снова `git push`. **Не** «лечить» отказ принудительным `push --force` в общей ветви: чужие коммиты пропадут.

@@ id=remote-tracking type=term src="Обмен с удалённым репозиторием"
Q: Что такое удалённый репозиторий `origin` и ветвь `origin/main`; чем она отличается от локальной `main`?
A:
**`origin`** — короткое имя, под которым запомнен URL удалённого репозитория (при `git clone` оно настраивается само).

**`origin/main`** — **ветвь слежения**: ваша локальная запись о том, где была ветвь `main` на сервере при **последнем обмене** (`fetch`, `pull`, `push`). Она двигается только сетевыми командами, коммитить в неё нельзя. Локальная `main` — ваша собственная ветвь, двигается вашими коммитами.

Сравнение `main` и `origin/main` показывает, сколько коммитов вы не отправили или не получили. После `git fetch` они могут разойтись — это и есть «надо объединить».

@@ id=changes-path type=concept src="Обмен с удалённым репозиторием"
Q: Опиши путь изменённого файла от рабочего каталога до сервера: через какие места и какие команды он проходит. Какой минимальный порядок команд?
A:

```diagram
diagram
W: box "Рабочий каталог" @ 90, 80
S: box "Промежуточная область" @ 290, 80
L: box "Локальные коммиты" @ 490, 80
R: db "Удалённый репозиторий" @ 490, 230
W -> S : git add
S -> L : git commit
L -> R : git push
R -> W : git pull
```

Порядок:

1. `git status` — что изменено;
2. `git add <file>` — в промежуточную область;
3. `git commit -m 'Commit message'` — локальный коммит;
4. `git push` — отправка на сервер.

Если `push` отклонён — сначала `git pull`. Заметь: после `commit` изменения ещё **только у вас**; на сервере они появятся лишь после `push`.

@@ id=reset-modes type=compare src="Если что-то пошло не так"
Q: Чем отличаются `git reset --soft`, `--mixed` (по умолчанию) и `--hard` при переходе на другой коммит? Что происходит с веткой, индексом и файлами?
A:
Во всех режимах **текущая ветвь переставляется** на указанный коммит. Различие — что делают с индексом и файлами.

| Режим               | Ветвь | Промежуточная область | Рабочий каталог           | Куда деваются изменения «отменённых» коммитов |
| ------------------- | ----- | --------------------- | ------------------------- | --------------------------------------------- |
| `--soft`            | да    | не меняется           | не меняется               | остаются подготовленными к коммиту            |
| `--mixed` (по умолч.) | да  | сбрасывается          | не меняется               | остаются в файлах, но не подготовлены         |
| `--hard`            | да    | сбрасывается          | **перезаписывается**      | **удаляются**, как и несохранённые правки     |

`--hard` — единственный, который может **безвозвратно потерять незафиксированную работу**: до коммита её нет ни в истории, ни в `reflog`.

@@ id=reset-hard type=pitfall src="Если что-то пошло не так"
Q: Что в точности делает `git reset --hard HEAD~1`, что с ним нужно знать, и чем его заменить, если нужно отменить коммит, но сохранить изменения?
A:
`HEAD~1` — коммит-родитель текущего. Команда сдвигает ветвь на него и приводит индекс и файлы к его состоянию: последний коммит **пропадает из `git log`** (хотя остаётся в `git reflog`), а все **несохранённые** изменения в отслеживаемых файлах **стираются** без возможности вернуть.

Предупреждения:

- коммит из конспекта отменяется в **локальной** истории; если он уже отправлен на сервер, это переписывание опубликованной истории (для таких случаев — `git revert`);
- перед `--hard` нужен чистый `git status` или `git stash`.

Чтобы отменить коммит, но **оставить изменения**, используют `git reset --soft HEAD~1` (правки останутся подготовленными) или `git reset HEAD~1` (останутся в файлах).

@@ id=revert type=concept src="Если что-то пошло не так"
Q: Что делает `git revert <хэш>`, почему он безопасен для коммитов, уже отправленных на сервер, и откуда взять хэш?
A:
Хэш находят в `git log`. `git revert <хэш>` создаёт **новый коммит**, который применяет изменения указанного коммита **с обратным знаком** (добавленное убирает, убранное возвращает). Старый коммит **остаётся в истории**.

Раз ничего не переписывается, `revert` безопасен для отправленных и общих коммитов: коллеги получают его как обычное обновление. Так можно отменить коммит «из глубины истории» (n коммитов назад), не трогая коммиты после него.

Оговорка: если более поздние коммиты правили те же строки, `revert` даст **конфликт**, и его решают так же, как при слиянии (правка файла → `git add` → продолжение).

@@ id=rollback-choice type=compare src="Если что-то пошло не так"
Q: Какой способ отката выбрать: (а) опечатка в сообщении последнего коммита, он не отправлен; (б) последний коммит локальный и не нужен; (в) плохой коммит отправлен на сервер и после него есть другие; (г) по ошибке выполнен `git reset --hard`, и вы потеряли коммиты?
A:

| Ситуация | Команда | Почему |
| -------- | ------- | ------ |
| (а) опечатка в сообщении, коммит не отправлен | `git commit --amend` | заменяет последний коммит, пока он не ушёл на сервер |
| (б) последний коммит локальный и не нужен | `git reset --hard HEAD~1` (или `--soft`, чтобы оставить правки) | ветвь просто сдвигается назад; история ещё не опубликована |
| (в) плохой коммит уже на сервере, глубоко в истории | `git log` → `git revert <хэш>` | новый коммит с обратными изменениями, история не переписывается |
| (г) потеряли коммиты после `reset` | `git reflog` → вернуться к записи `HEAD@{index}` | коммиты ещё есть в журнале перемещений `HEAD` |

Общее правило: **опубликованную историю не переписывают** (`amend`, `reset`, `rebase` — только для локальной), для неё — `revert`.

@@ id=reflog-recover type=code src="Если что-то пошло не так"
Q: Вы выполнили `git reset --hard HEAD~3` и поняли, что зря. Как вернуть потерянные коммиты и чем `git reflog` отличается от `git log`?
A:

```bash
git reflog                # найти запись «до reset», например HEAD@{1}
git reset --hard HEAD@{1} # вернуть ветвь и файлы в то состояние
```

**`git reflog`** показывает **всё, что вы делали** в Git, **во всех ветках**: каждое перемещение `HEAD` (коммиты, переключения, слияния, `reset`) с индексом `HEAD@{index}`; `HEAD@{0}` — сейчас, `HEAD@{1}` — предыдущее положение. `git log` показывает только историю коммитов **активной ветви**: после `reset` потерянных коммитов в нём уже нет, а в `reflog` они есть.

Нужно найти запись, **перед которой всё сломалось**. В конспекте команда записана как `git reset HEAD@{index}` — без `--hard` это `--mixed`: ветвь вернётся, но файлы в каталоге останутся прежними. Чтобы вернуть и файлы, нужен `--hard`. Журнал локален (на сервер не отправляется) и хранится ограниченное время.
