@@ id=cmake-role type=concept src="Структура CMake-файла"
Q: Что такое `CMakeLists.txt`, зачем в проекте несколько таких файлов и чем корневой отличается от остальных?
A:
`CMakeLists.txt` — файл конфигурации сборки, который читает утилита `cmake`: в нём описано, из каких файлов собирать программу, какие библиотеки подключать, где искать заголовки.

В проекте обычно **иерархия директорий**, и у каждой части свой файл:

```text
.
├── CMakeLists.txt        <- корневой: точка входа всей сборки
├── bin/CMakeLists.txt    <- исполняемый файл
├── lib/CMakeLists.txt    <- библиотека
└── tests/CMakeLists.txt  <- тесты
```
**Корневой** файл запускает сборку проекта и подключает подкаталоги; файлы в `bin`, `lib`, `tests` описывают только свою часть. Так один файл не разрастается, а каждая часть (таргет) собирается и читается отдельно.

@@ id=cmake-minimal-root type=code src="Структура CMake-файла"
Q: Как выглядит минимальный корневой `CMakeLists.txt` для проекта с `lib` и `bin` и какими командами проект настраивают и собирают? (Этого нет в конспекте: стандартный минимум.)
A:
```cmake
cmake_minimum_required(VERSION 3.20)   # какая версия CMake нужна
project(hello LANGUAGES CXX)           # имя проекта и язык
set(CMAKE_CXX_STANDARD 20)             # стандарт C++

add_subdirectory(lib)                  # обработать lib/CMakeLists.txt
add_subdirectory(bin)                  # обработать bin/CMakeLists.txt
```
Настройка и сборка (каталог `build` — «вне исходников», чтобы не засорять проект):

```bash
cmake -S . -B build        # конфигурация: прочитать CMakeLists.txt, подготовить сборку
cmake --build build        # сборка таргетов
```
Сам `cmake` компиляторов не заменяет: он генерирует файлы для системы сборки (Make, Ninja…), которая и запускает компилятор и линкер.

@@ id=build-stages type=concept src="Этапы компиляции"
Q: Из каких этапов состоит сборка программы на C/C++ и почему полезно знать, на каком из них упала ошибка?
A:
Сборка — последовательность **препроцессинг → компиляция → линковка**:

```diagram
diagram
A: box "main.cpp + заголовки"
B: box "Препроцессинг: разворот директив #"
C: box "Компиляция: .cpp -> .o (по одному)"
D: box "Линковка: все .o и библиотеки -> бинарь"
E: round "Исполняемый файл или библиотека"
A -> B
B -> C
C -> D
D -> E
```
Знание этапа подсказывает, что чинить: «undefined reference» — проблема линковки (нет определения), «redefinition» в одном файле — проблема компиляции (двойное определение в одной единице), «file not found» у `#include` — путь поиска заголовков (препроцессинг).

@@ id=error-stages type=pitfall src="Этапы компиляции"
Q: На каком этапе возникнут ошибки: (а) `fatal error: func.h: No such file or directory`, (б) `error: expected ';'`, (в) `undefined reference to 'myfunc()'`, (г) `multiple definition of 'myfunc()'` (определение лежит в двух `.cpp`)?
A:
- (а) **препроцессинг**: `#include` не нашёл файл в путях поиска (исправляют путь: `target_include_directories`);
- (б) **компиляция**: синтаксическая ошибка в `.cpp`;
- (в) **линковка**: вызов есть, а определения нет ни в одном `.o` и ни в одной библиотеке;
- (г) **линковка**: линкер нашёл **два определения** одного имени — их должно быть одно.

@@ id=preprocessor type=term src="1. Препроцессинг"
Q: Что делает препроцессинг и какие директивы препроцессора вы знаете?
A:
**Препроцессинг** — этап, на котором **текстово** обрабатываются директивы препроцессора (строки, начинающиеся с `#`), **до** того как компилятор разбирает язык C++. Препроцессор не знает ни типов, ни синтаксиса — только заменяет текст.

- `#include` — вставляет содержимое указанного файла на место директивы;
- `#pragma` — служебная инструкция компилятору (`#pragma once` — не включать заголовок повторно);
- `#define` — макрос: подставляется текстово везде, где встречается имя.

@@ id=macro-pitfall type=pitfall src="1. Препроцессинг"
Q: Чему равно `SQUARE(1 + 2)` при `#define SQUARE(x) x * x` и почему?
A:
Получается **5**, а не 9. Препроцессор подставляет текст без вычислений: `SQUARE(1 + 2)` превращается в `1 + 2 * 1 + 2`, то есть $1 + 2 + 2 = 5$ (умножение выполняется раньше сложения).

Макрос не знает про приоритеты и типы, поэтому в C++ вместо него обычно используют функции, `constexpr` и `inline`. Если макрос всё же нужен, аргумент и результат заключают в скобки: `#define SQUARE(x) ((x) * (x))`.

@@ id=decl-vs-def type=term src="1. Препроцессинг"
Q: Чем объявление отличается от определения? Какие из строк — определения: `void f();`, `void f() {}`, `extern int x;`, `int x;`, `struct S;`, `struct S { int a; };`?
A:
**Объявление** сообщает компилятору, что сущность (функция, переменная, класс) существует, и задаёт её тип или сигнатуру — «контракт». **Определение** даёт саму сущность: тело функции, место под переменную, состав класса.

- `void f();` — объявление; `void f() {}` — **определение**;
- `extern int x;` — объявление; `int x;` — **определение** (создаёт переменную);
- `struct S;` — объявление; `struct S { int a; };` — **определение**.

Правило проекта: в `.h` — объявления, в `.cpp` — определения. Объявлений может быть сколько угодно, **определение — ровно одно** на программу.

@@ id=header-why type=concept src="1. Препроцессинг"
Q: Зачем объявление функции выносят в `func.h`, а определение — в `func.cpp`, и что делает `#include "func.h"`?
A:
Чтобы **использовать** функцию в другом файле, достаточно знать её объявление — реализация не нужна. Поэтому интерфейс лежит в `func.h`, реализация — в `func.cpp`, а `main.cpp` пишет `#include "func.h"`.

Препроцессор **текстово** вставляет содержимое `func.h` на место директивы, и компилятор в `main.cpp` видит объявление `myfunc` — он знает, что функция существует и как её вызывать (сигнатуру). Где лежит реализация, на этом этапе неважно: вызов связывает с телом уже линковка.

@@ id=definition-in-header type=pitfall src="1. Препроцессинг"
Q: Что будет, если определение `void myfunc() {}` написать прямо в `func.h` и включить его в `a.cpp` и `b.cpp`?
A:
Каждый `.cpp` скомпилируется **успешно** (в каждом по одному определению). Но в двух объектных файлах окажется по определению `myfunc`, и **линковка упадёт**: `multiple definition of 'myfunc()'` — для одного имени два тела.

Объявление в заголовке можно подключать сколько угодно раз, определение — только одно. Исправления: определение перенести в один `.cpp`, а в заголовке оставить объявление (или пометить функцию `inline`).

@@ id=double-include type=code src="1. Препроцессинг"
Q: Что не так в этом коде и на каком этапе возникнет ошибка? Как исправить?
```cpp
// point.h
struct Point { int x; int y; };

// main.cpp
#include "point.h"
#include "point.h"
```
A:
Заголовок включён дважды, и после препроцессинга в одном файле оказывается **два определения** `struct Point` — компиляция падает с `redefinition of 'struct Point'`.

Исправление — защита от повторного включения: `#pragma once` первой строкой `point.h` (или include guard `#ifndef POINT_H / #define POINT_H / … / #endif`). Двойное включение часто происходит косвенно: два разных заголовка включают один и тот же третий.

@@ id=compile-stage type=concept src="2. Компиляция"
Q: Что получается на этапе компиляции и что остаётся «заглушкой»?
A:
Каждый `.cpp` (после препроцессинга) **независимо** превращается в **объектный файл**: `main.cpp` → `main.o`. В нём уже есть машинный код всего, что **определено** в этом файле.

Если в файле вызывается функция, определённая в другом `.cpp` (в этом видно только объявление), компилятор не знает её адреса и оставляет **заглушку** — запись «здесь вызов функции с таким именем, адрес допишется позже». На выходе — набор `.o`-файлов, где часть вызовов ещё не связана.

Раздельная компиляция удобна: изменился один `.cpp` — перекомпилируется только он, остальные `.o` берутся готовыми, потом выполняется линковка.

@@ id=name-mangling type=concept src="2. Компиляция"
Q: Почему заглушка — не просто `myfunc`, а «искажённое» имя вроде `__MyFunc`? Приведи пример.
A:
Имя-заглушка должно **однозначно** идентифицировать функцию среди всех в проекте для **линкера**. В C++ функции перегружаются: `void f(int)` и `void f(double)` имеют одно имя, но это разные функции, поэтому в символ кодируется ещё и информация о параметрах и пространствах имён (**name mangling**). Например, в Itanium ABI (GCC, Clang) это `_Z1fi` и `_Z1fd`.

Из-за этого же в сообщении об ошибке линкера имя может быть «искажённым»; конкретный вид зависит от компилятора и ABI.

@@ id=link-stage type=concept src="3. Линковка"
Q: Что делает линковка и почему она видит то, чего не видел компилятор?
A:
Из готовых объектных файлов (и библиотек) собирается один итоговый бинарь — исполняемый файл или библиотека. Линкер видит **все** `.o` проекта сразу, поэтому каждую заглушку («вызов функции с таким именем») сопоставляет с настоящим определением, найденным в одном из `.o` или в подключённой библиотеке, и подставляет реальный адрес.

Компилятор работает с одним `.cpp` и знает только то, что видно в нём, — отсюда разделение: **объявления проверяет компилятор, определения находит линкер**.

@@ id=undefined-reference type=code src="3. Линковка"
Q: Почему `g++ -c main.cpp` проходит без ошибок, а сборка программы падает с `undefined reference to 'myfunc()'`? Как исправить?
```cpp
// func.h
void myfunc();

// main.cpp
#include "func.h"
int main() { myfunc(); }
// определения myfunc нигде нет
```
A:
Компиляции достаточно объявления: компилятор понял сигнатуру `myfunc`, оставил в `main.o` заглушку для вызова — и успешно закончил. Линковка обошла все объектные файлы и **не нашла определения** для этой заглушки — ошибка `undefined reference`.

Исправления: написать определение `void myfunc() {}` в `.cpp`, **добавить этот `.cpp` в сборку** (в `add_executable`/`add_library`) и убедиться, что таргет, где оно лежит, подключён через `target_link_libraries`. Забытый файл в списке исходников — одна из самых частых причин такой ошибки.

@@ id=targets type=term src="Организация растущего проекта: подкаталоги и таргеты"
Q: Что такое таргет (target) в CMake и зачем логические части проекта выносят в отдельные подкаталоги?
A:
**Таргет** — отдельная собираемая часть проекта: исполняемый файл, библиотека, тесты. В примере три таргета: `bin` (исполняемый файл), `lib` (библиотека), `tests` (тесты).

У маленького проекта достаточно одного `CMakeLists.txt`, но с ростом он становится большим и трудночитаемым. Поэтому каждую часть выносят в свой подкаталог со **своим** `CMakeLists.txt`, отвечающим только за неё, а корневой файл их подключает.

@@ id=add-subdirectory type=concept src="Организация растущего проекта: подкаталоги и таргеты"
Q: Что делает `add_subdirectory(bin)` в корневом `CMakeLists.txt`?
A:
Команда говорит CMake: «зайди в подкаталог `bin`, найди там его `CMakeLists.txt` и обработай его как часть текущей сборки». Так описание таргета подключается в общий процесс конфигурации, а содержимое `bin/CMakeLists.txt` не переписывают в корневой файл.

Для остальных частей — по строке на каждый подкаталог: `add_subdirectory(lib)`, `add_subdirectory(tests)`. Таргеты, объявленные внутри, становятся доступны всему проекту по имени.

@@ id=bin-cmake type=code src="Содержимое bin/CMakeLists.txt"
Q: Допиши `bin/CMakeLists.txt`, чтобы исполняемый файл `hello` собирался из `main.cpp`, находил заголовки из `../lib` и линковался с библиотекой `lib`. Что делает каждая строка?
A:
```cmake
add_executable(hello main.cpp)

target_include_directories(hello
    PUBLIC
    ../lib)

target_link_libraries(hello
    PUBLIC
    lib)
```
- `add_executable(hello main.cpp)` — объявляет таргет `hello` типа «исполняемый файл», собираемый из перечисленных `.cpp` (в конспекте список аргументов опущен многоточием);
- `target_include_directories(hello PUBLIC ../lib)` — добавляет `../lib` в пути поиска заголовков: `#include "func.h"` в коде `hello` будет искаться и там;
- `target_link_libraries(hello PUBLIC lib)` — при линковке `hello` подключить таргет `lib`, чтобы найти определения функций из `func.cpp`.

В конспекте написано `target_link_library` — без `s` такой команды нет, правильно `target_link_libraries`.

@@ id=include-vs-link type=compare src="Содержимое bin/CMakeLists.txt"
Q: Чем `target_include_directories` отличается от `target_link_libraries` и что сломается, если убрать каждую из них?
A:
| | `target_include_directories` | `target_link_libraries` |
| --- | --- | --- |
| Какой этап | препроцессинг / компиляция | линковка |
| Что даёт | где искать **заголовки** (объявления) | какие **библиотеки** подключить (определения) |
| Без неё | `fatal error: func.h: No such file or directory` | `undefined reference to 'myfunc()'` |

`hello` использует функции, **объявленные** в `../lib` и **определённые** в `lib`: заголовки нужны для компиляции `main.cpp`, а код библиотеки — для линковки. Нужны обе строки, и они закрывают разные этапы сборки.

@@ id=public-private type=concept src="Содержимое bin/CMakeLists.txt"
Q: Что означают `PUBLIC` и `PRIVATE` в `target_include_directories(hello PUBLIC ../lib)`?
A:
Это **видимость** настройки для зависимых таргетов:

- `PRIVATE` — настройка нужна **только самому таргету** (`hello`), на зависящие от него таргеты не распространяется;
- `PUBLIC` — нужна и самому таргету, и **всем, кто зависит** от него: они тоже получат `../lib` в пути заголовков;
- `INTERFACE` (в конспекте не разбирался) — нужна только зависящим, самому таргету нет.

Практика: если заголовок библиотеки включается из её **публичного** заголовка — `PUBLIC`; если только из `.cpp` библиотеки — `PRIVATE`.

@@ id=lib-cmake type=code src="Содержимое lib/CMakeLists.txt"
Q: Что делает `add_library(lib func.cpp)`, чем отличается от `add_executable` и что такое архив `func.a`?
A:
`lib` — **имя таргета** (библиотека), `func.cpp` — исходник, который компилируется и входит в таргет. Команда аналогична `add_executable`, но результат — **библиотека**, а не запускаемый файл.

По умолчанию это статическая библиотека — **архив** `.a` (обычно `libимя.a`, здесь `liblib.a`), который просто упаковывает набор объектных файлов (`func.o`, …) так, чтобы линкеру удобно было подключать их как одну библиотеку, а не перечислять каждый `.o`.

```diagram
diagram
H: box "hello (add_executable)"
L: box "lib (add_library: func.cpp)"
H -> L : include: заголовки
H -> L : link: код
```
`hello` зависит от `lib` и по заголовкам (компиляция), и по коду (линковка) — практическое применение всего разбора про этапы сборки.

@@ id=fstream-term type=term src="Файловый ввод-вывод"
Q: Что такое `std::ifstream` и `std::ofstream`, какой для них нужен заголовок и как они связаны с `std::cin`/`std::cout`?
A:
Заголовок `<fstream>`. `std::ifstream` (**i**nput file stream) — поток для **чтения** из файла, `std::ofstream` (**o**utput file stream) — для **записи** в файл.

Работают так же, как стандартные потоки: те же операторы `>>` (извлечение из потока) и `<<`, та же логика «читать значение нужного типа». Разница — только источник и приёмник данных: файл вместо клавиатуры и консоли. Объект создаётся с именем файла и открывает его сразу: `std::ifstream fin("input.txt");` (`fin` — обычное имя переменной).

@@ id=fstream-code type=code src="Файловый ввод-вывод"
Q: Что выведет код, если в `input.txt` записано `42 17`? Что произойдёт, если файла нет?
```cpp
std::ifstream fin("input.txt");
int a;
int b;
fin >> a >> b;
std::cout << a + b << '\n';
```
A:
Вывод: `59` (`42 + 17`): `>>` читает из файла очередное значение по типу `int`, пропуская пробелы.

Если файла нет (или его не удалось открыть), поток переходит в состояние ошибки: `fin >> a` ничего не читает, `a` и `b` остаются **неинициализированными**, а их чтение — неопределённое поведение. Поэтому после открытия проверяют поток: `if (!fin) { /* ошибка открытия */ }`, и после чтения — успех извлечения.
