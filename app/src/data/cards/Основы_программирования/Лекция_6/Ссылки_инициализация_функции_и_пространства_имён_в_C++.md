@@ id=swap-pointers type=code src="Обмен значениями через указатели"
Q: Что выведет программа и почему функции для обмена нужны адреса, а не сами значения?
```cpp
void swap_values(int* left, int* right) {
    int temporary = *left;
    *left = *right;
    *right = temporary;
}

int main() {
    int first = 10;
    int second = 20;
    swap_values(&first, &second);
    std::cout << first << ' ' << second << '\n';
}
```
A:
Вывод: `20 10`.

Если передать значения (`int left, int right`), функция получит **копии** и поменяет их, а `first` и `second` в `main` останутся прежними. Чтобы изменить **исходные** переменные, передают их адреса: `left` указывает на `first`, `right` — на `second`.

1. `temporary = *left` — читаем `10`;
2. `*left = *right` — по адресу `first` записываем `20`;
3. `*right = temporary` — по адресу `second` записываем `10`.

@@ id=null-pointer-swap type=pitfall src="Указатель может быть нулевым"
Q: Что произойдёт при `swap_values(&value, nullptr)` и почему «молча выйти по `return`» — плохое исправление?
A:
Выражение `*right` разыменовывает `nullptr` — **неопределённое поведение**: нельзя рассчитывать ни на конкретное значение, ни на предсказуемое падение.

Для обмена нужны **два существующих объекта**. Проверка с тихим `return` скрыла бы ошибку вызывающего кода: условие задачи нарушено, а программа продолжает работать как ни в чём не бывало. Мотивация для **ссылок**: у них нет «нулевого» состояния, и нарушить это условие просто нельзя.

@@ id=ref-term type=term src="Ссылка — другое имя объекта"
Q: Что такое lvalue-ссылка `T&` и какими четырьмя свойствами она обладает?
A:
**Lvalue-ссылка** — другое имя (**псевдоним**) объекта типа `T`: обращаясь к ссылке, мы работаем с самим объектом.

1. Её **нужно инициализировать** при создании: `int& alias;` не скомпилируется.
2. Привязка **не создаёт копию** объекта.
3. **Перепривязать** ссылку к другому объекту нельзя.
4. **Указателя на ссылку нет**: взятие адреса ссылки даёт адрес объекта, на который она ссылается.

@@ id=ref-code type=code src="Ссылка в коде"
Q: Что выведет программа? Какие две роли у символа `&` в ней?
```cpp
int value = 10;
int& alias = value;
alias = 20;
std::cout << value << '\n';
std::cout << std::boolalpha << (&alias == &value) << '\n';
```
A:
Вывод: `20` и `true`.

- `int& alias = value;` — `alias` становится вторым именем `value`, нового объекта нет;
- `alias = 20;` изменяет сам объект, поэтому `value == 20`;
- `&alias == &value` — адрес «ссылки» — это адрес объекта, поэтому `true` (`std::boolalpha` печатает `true`/`false` словами).

Две роли `&`: в **объявлении** (`int&`) он задаёт ссылочный тип, в **выражении** (`&alias`) — берёт адрес объекта.

@@ id=ref-vs-pointer type=compare src="Ссылка и указатель в памяти"
Q: Сравни ссылку `T&` и указатель `T*`: что это за сущность, нулевое значение, перепривязка, адрес, как обращаться.
A:
| | Ссылка `T&` | Указатель `T*` |
| --- | --- | --- |
| Что это | другое **имя** объекта | **отдельный объект**, хранящий адрес |
| Нулевое состояние | нет | есть (`nullptr`) |
| Инициализация | обязательна | можно не инициализировать (но лучше задать) |
| Перепривязка | нельзя | можно присвоить другой адрес |
| Адрес | `&ref` — адрес **объекта** | `&ptr` — адрес **самого указателя** |
| Обращение к объекту | просто имя: `ref` | разыменование: `*ptr` |
| Размер и память | не гарантирован (зависит от реализации) | `sizeof(ptr)` — размер указателя |

Выбор: объект обязан существовать — ссылка; объект может отсутствовать или нужно менять, на что указываем — указатель.

```diagram
diagram
I: round "имя i"
J: round "имя j"
O: box "Объект int"
P: round "указатель p (отдельный объект)"
I -> O : то же самое
J -> O : то же самое
P -> O : хранит адрес
```

@@ id=no-rebind type=code src="Ссылку нельзя перепривязать"
Q: Что выведет программа и привязывает ли `alias = second;` ссылку к `second`?
```cpp
int first = 10;
int second = 20;
int& alias = first;
alias = second;
alias = 30;
std::cout << first << ' ' << second << '\n';
```
A:
Вывод: `30 20`.

`alias = second;` — это **присваивание**, а не новая привязка: значение `second` (`20`) копируется в объект `first`, а `alias` по-прежнему ссылается на `first`. Затем `alias = 30;` снова меняет `first`. `second` не менялась.

**Присваивание через ссылку меняет объект, а не связь ссылки с ним.**

@@ id=const-ref type=code src="Чтение через const-ссылку"
Q: Что выведет код? Гарантирует ли `const int&`, что объект никогда не изменится?
```cpp
int value = 10;
const int& view = value;
// view = 20;
value = 20;
std::cout << view << '\n';
```
A:
Вывод: `20`.

`const T&` запрещает изменять объект **через эту ссылку** (`view = 20;` — ошибка), но не делает сам объект константным: другое имя того же объекта (`value`) по-прежнему позволяет его менять, и `view` видит новое значение. `const`-ссылка — ограничение на **способ доступа**, а не обещание неизменности.

@@ id=swap-references type=code src="Обмен значениями через ссылки"
Q: Перепиши `swap_values` через ссылки. Что изменится в теле функции и при вызове?
A:
```cpp
void swap_values(int& left, int& right) {
    int temporary = left;
    left = right;
    right = temporary;
}

swap_values(first, second);   // вызов: сами переменные
```
Ни `*` в теле, ни `&` при вызове: `left` и `right` — другие имена `first` и `second` внутри функции. Результат тот же: `20 10`.

У ссылки нет корректного «нулевого» состояния, передать «ничего» нельзя; зато объект должен оставаться **живым**, пока на него ссылаются.

@@ id=copy-or-original type=trace src="Копия или исходный объект?"
Q: Что напечатает программа и в чём разница `increment_copy` и `increment_original`?
```cpp
void increment_copy(int value) { ++value; std::cout << value << '\n'; }
void increment_original(int& value) { ++value; }

int main() {
    int count = 10;
    increment_copy(count);
    std::cout << count << '\n';
    increment_original(count);
    std::cout << count << '\n';
}
```
A:
Вывод: `11`, `10`, `11`.

- `increment_copy`: параметр `value` — **отдельный объект**, в него скопировано `10`; `++value` меняет копию, печатается `11`, а `count` остаётся `10`;
- `increment_original`: параметр — **ссылка** на `count`, `++value` увеличивает саму `count`, она становится `11`.

@@ id=dangling-ref type=pitfall src="Ссылка не владеет объектом"
Q: Что не так с этим кодом и почему ссылка не спасает объект?
```cpp
int& local_value() {
    int value = 20;
    return value;
}

int main() {
    int& result = local_value();
    std::cout << result << '\n';
}
```
A:
Ссылка **не владеет** объектом и не продлевает ему жизнь. `value` — automatic-объект, он уничтожается при выходе из `local_value`, а функция вернула ссылку на него. `result` — **висячая** ссылка, и чтение через неё — неопределённое поведение: нельзя рассчитывать ни на `20`, ни на падение.

Предупреждение компилятора не заменяет контроль времени жизни. Правильно — вернуть результат **по значению** (`int local_value()`).

@@ id=return-by-value type=concept src="Локальный результат возвращаем по значению"
Q: Почему локальный результат функции возвращают по значению, а не по ссылке?
A:
Локальная переменная умирает при выходе из функции, а ссылка на неё стала бы висячей. При возврате **по значению** вызывающий код получает сам результат (значение), и локальной переменной после этого уже не нужно жить: `int result = make_value();` корректно печатает `20`.

Правило: новый результат — через `return` по значению; ссылку возвращают лишь на объект, который заведомо переживёт вызов.

@@ id=bind-rules type=code src="Какие привязки ссылок допустимы?"
Q: Какие строки допустимы и что выведет программа? Что происходит в `const int& c = 42;`?
```cpp
int x = 10;
int& a = x;
const int& b = x;
const int& c = 42;
// int& d = 42;
std::cout << a << ' ' << b << ' ' << c << '\n';
```
A:
Вывод: `10 10 42`; закомментированная строка — **ошибка компиляции**.

- `int& a = x;`, `const int& b = x;` — ссылки на `x`;
- `const int& c = 42;` — `42` не лежит ни в какой переменной, поэтому создаётся **временный** `int`, и `c` привязывается к нему; его время жизни **продлевается до конца блока**;
- `int& d = 42;` — неконстантная ссылка не привязывается к временному объекту.

@@ id=lvalue-temp type=concept src="Какие привязки ссылок допустимы?"
Q: Почему `const int&` можно привязать к `42`, а `int&` — нельзя? Что такое lvalue и временный объект?
A:
**lvalue** — выражение, обозначающее конкретный объект с адресом (имя переменной `x`). Литерал `42` или результат вычисления — **временное значение**: объекта, к которому можно «подвязаться», нет, поэтому компилятор создаёт временный и привязывает ссылку к нему.

Через `int&` пришлось бы **менять** такой временный объект, а он исчезнет в конце выражения — запись была бы потеряна, чаще всего это ошибка программиста, и язык её запрещает. `const T&` только **читает**, поэтому привязка допустима и продлевает жизнь временному до конца блока. Это и позволяет принимать `const T&` в функциях и вызывать их с литералами и результатами вычислений.

@@ id=temp-const-ref type=pitfall src="Временный объект в аргументе const&"
Q: Что происходит при `greet("world")` для `void greet(const std::string& name)` и когда ссылка `name` становится висячей?
A:
Параметр `const&` не копирует готовую `std::string`, но аргумент здесь — **строковый литерал**, а не `std::string`. Поэтому для вызова создаётся **временная строка** из литерала, и `name` ссылается на неё.

Временный объект живёт **до конца полного выражения** с вызовом — до `;`. Если сохранить на него ссылку или указатель и использовать позже, обращение — к уничтоженному объекту:

```cpp
const std::string* saved = nullptr;
void remember(const std::string& name) { saved = &name; }

remember("world");        // временная строка уничтожена после ';'
// *saved здесь — висячий указатель, UB
```

@@ id=param-choice type=compare src="Как передавать аргумент?"
Q: Какие бывают способы передачи параметра (`T`, `const T&`, `T&`, `const T*`, `T*`), что значит каждый и когда его выбирать?
A:
| Параметр | Смысл | Когда |
| --- | --- | --- |
| `T value` | отдельный объект-копия | дёшево копируемое: `int`, `double` |
| `const T& value` | чтение **без копирования** | большая структура или строка |
| `T& value` | работа с **исходным** изменяемым объектом | изменить переданный объект |
| `const T* value` | чтение через указатель | объект **может отсутствовать** |
| `T* value` | изменение через указатель | объект может отсутствовать |

Допустимость `nullptr` задаёт **договорённость функции**, а не тип. Указатель может также означать начало массива. Выбор по вопросам: меняет существующий объект? (да: может отсутствовать — `T*`, иначе `T&`); нет: дёшево копировать? (да — `T`); иначе может отсутствовать — `const T*`, иначе `const T&`.

@@ id=result-vs-out-param type=concept src="Как передавать аргумент?"
Q: Как лучше вернуть из функции новый результат: через `return` или через ссылочный параметр? Когда нужен `T&`?
A:
Если функция **вычисляет новый результат**, возвращают его через `return`: так читается проще (`int x = f();`) и не требует заранее заведённой переменной. Ссылочный параметр `T&` оставляют для **изменения существующего** объекта (`blur(Image&)`, `swap_values(int&, int&)`).

Возврат результата через `T*`-параметр или глобальную переменную — худшие варианты; возврат ссылки на локальную переменную — ошибка (висячая ссылка).

@@ id=what-function-gets type=concept src="Что получает функция"
Q: Что получает функция при передаче по значению, по ссылке и по указателю?
A:
- **по значению** (`T value`) — **копию** (собственный объект);
- **по ссылке** (`T&`) — **тот же** объект (другое имя);
- **по указателю** (`T*`) — **копию адреса**: указатель передаётся по значению, объект общий.

```diagram
I: db "Исходное изображение"
V -> C : владеет копией
R -> I : то же изображение
P -> I : по адресу
```

@@ id=image-params type=code src="Параметры для работы с изображением"
Q: Выбери типы параметров и обоснуй: `show` — показать изображение, не меняя; `blur` — размыть существующее; `set_logo` — использовать как логотип без изменения (отсутствие — «убрать логотип»); `set_zoom` — масштаб целым числом процентов.
A:
```cpp
void show(const Image& image);    // читаем, копировать большое изображение не нужно
void blur(Image& image);          // меняем исходное изображение
void set_logo(const Image* logo); // nullptr — логотипа нет
void set_zoom(int percent);       // дёшево копировать — по значению
```
- `show` — большой объект, менять нельзя: `const Image&`;
- `blur` — нужно изменить **исходное**: `Image&`;
- `set_logo` — читается, а «нет логотипа» — допустимое состояние; у ссылки нулевого состояния нет, значит указатель: `const Image*`;
- `set_zoom` — число процентов дёшево копировать: `int`.

@@ id=nullable-pointer type=code src="Когда отсутствие объекта допустимо"
Q: Что выведет программа? Чем эта обработка `nullptr` отличается от `swap_values`?
```cpp
void print_value(const int* value) {
    if (value == nullptr) {
        std::cout << "No value\n";
        return;
    }
    std::cout << *value << '\n';
}

int main() {
    int value = 42;
    print_value(&value);
    print_value(nullptr);
}
```
A:
Вывод: `42` и `No value`.

Здесь `nullptr` имеет **осмысленное значение** («значения нет»), которое функция явно проверяет перед разыменованием. В `swap_values` нулевой указатель был бы ошибкой вызывающего кода: объекты обязательны, поэтому там уместна ссылка.

@@ id=overload-term type=term src="Перегрузка: одно имя, разные параметры"
Q: Что такое перегрузка функций и как компилятор выбирает версию? Что выведет `print(20); print(20.1);` для `print(int)` и `print(double)`?
A:
**Перегрузка** — несколько функций с одним именем, но разными списками параметров (по типам или по количеству). Компилятор сначала находит имя, затем выбирает версию **по аргументам**: лучшая — с **точным совпадением** типов.

`print(20)` — `20` это `int`, вызов `print(int)` (`int: 20`); `print(20.1)` — `20.1` это `double`, вызов `print(double)` (`double: 20.1`).

@@ id=overload-count type=code src="Перегрузки с разным числом параметров"
Q: Какие версии вызовут `print()`, `print(10)`, `print(10, 20)` при `print()`, `print(int)`, `print(int, int)`? Что будет с `print(1, 2, 3)`?
A:
Каждый вызов подходит **ровно одной** функции по числу аргументов: `print()` — версия без параметров, `print(10)` — с одним, `print(10, 20)` — с двумя; выбор очевиден.

`print(1, 2, 3)` — **ошибка компиляции**: нет ни одной подходящей функции (три аргумента не принимает ни одна перегрузка).

@@ id=implicit-conversion type=code src="Что напечатает print(value)?"
Q: Что выведет программа и почему вызов допустим?
```cpp
void print(int value) { std::cout << value << '\n'; }

int main() {
    double value = 20.1;
    print(value);
}
```
A:
Вывод: `20`.

Перегрузки для `double` нет, есть только `print(int)`. Но `double` неявно преобразуется в `int`, поэтому вызов допустим; при преобразовании **дробная часть отбрасывается** (`20.1` → `20`). Отсутствие подходящего точного совпадения не ошибка, если есть допустимое преобразование.

@@ id=ambiguous-float type=pitfall src="А если добавить перегрузку для float?"
Q: Почему вызов `print(20.1)` при `print(int)` и `print(float)` не компилируется?
A:
`20.1` имеет тип `double`. Точного совпадения нет; доступны два преобразования — `double` → `int` и `double` → `float`, и **ни одно не лучше другого**. Компилятор не может выбрать — **вызов неоднозначен**, ошибка компиляции. Добавление перегрузки сделало **хуже**: раньше версия была единственной.

@@ id=overload-suffix type=code src="Как выбрать нужную перегрузку"
Q: Как однозначно выбрать `print(float)` и что выведет `print(20); print(20.1F);`?
A:
Нужно, чтобы тип аргумента совпал точно. Суффикс `F` делает литерал `float`: `20.1F`.

`print(20)` — точное совпадение `int` (`int: 20`), `print(20.1F)` — точное совпадение `float` (`float: 20.1`). Неоднозначности нет. Альтернатива суффиксу — явное приведение `print(static_cast<float>(20.1))`.

@@ id=return-type-overload type=pitfall src="Возвращаемый тип не различает перегрузки"
Q: Почему конфликтуют `int convert(int)` и `float convert(int)` и поможет ли тип переменной, куда присваивается результат?
A:
Списки параметров **одинаковые** (`int`), функции отличаются лишь возвращаемым типом — это **одно и то же объявление с разными результатами**, ошибка компиляции. Перегрузка выбирается по **параметрам** (типы, число), но не по возвращаемому типу и не по тому, во что записывается результат (`float x = convert(10);` ничего не меняет).

@@ id=nullptr-vs-zero type=code src="nullptr вместо числового нуля"
Q: Что выведет программа и почему `0` и `nullptr` ведут себя по-разному?
```cpp
void print(int) { std::cout << "int\n"; }
void print(const char*) { std::cout << "const char*\n"; }

int main() {
    print(0);
    print("hello");
    print(nullptr);
}
```
A:
Вывод: `int`, `const char*`, `const char*`.

`0` — число, точное совпадение с `int`. `"hello"` — указатель (массив символов распался). `nullptr` — нулевой указатель, выбирает указательную перегрузку. Макрос `NULL` имеет **зависящее от реализации** определение, поэтому при выборе перегрузки на него полагаться нельзя — для нулевого указателя пишут `nullptr`.

@@ id=nullptr-ambiguous type=pitfall src="nullptr не выбирает тип указателя"
Q: Почему `print(nullptr)` при `print(const char*)` и `print(int*)` не компилируется и как это исправить на месте вызова?
A:
`nullptr` подходит к **обеим** указательным перегрузкам одинаково хорошо — вызов неоднозначен.

Нулевой указатель **конкретного типа** выберет свою перегрузку: `int* p = nullptr; print(p);` вызовет `print(int*)`, `print(static_cast<const char*>(nullptr))` — версию для `const char*`. Либо добавить перегрузку для типа самого `nullptr` (следующая карточка).

@@ id=nullptr-type type=concept src="У nullptr есть собственный тип"
Q: Какой тип у `nullptr` и как он помогает выбрать перегрузку?
A:
У `nullptr` собственный тип `std::nullptr_t` (объявлен в `<cstddef>`). Сам он не указательный, но его значения **преобразуются в любые указательные типы**. Если добавить перегрузку `void print(std::nullptr_t)`, вызов `print(nullptr)` получает **точное совпадение** с ней и перестаёт быть неоднозначным.

@@ id=default-args type=code src="Аргументы по умолчанию"
Q: Что выведут вызовы и что значит «подставляются справа»?
```cpp
Point make_point(int x = 0, int y = 0) { return {x, y}; }

print(make_point(10, 20));
print(make_point(10));
print(make_point());
```
A:
Вывод: `(10, 20)`, `(10, 0)`, `(0, 0)`.

Пропущенные аргументы берутся по умолчанию: в `make_point(10)` `x = 10`, пропущенный `y = 0`; в `make_point()` оба по умолчанию. Пропускать можно только **правые** аргументы: передать лишь второй (`make_point(, 5)`) нельзя.

@@ id=default-args-rules type=pitfall src="Где указывать значение по умолчанию"
Q: Найди ошибки и объясни правила:
```cpp
void f(int a, int b = 0);      // объявление
void f(int a, int b = 0) {}    // (1) определение
void g(int a = 1, int b);      // (2)
void h(int a);
void h(int a, int b = 0);
// h(1);                        // (3)
```
A:
- (1) **ошибка**: значение по умолчанию задают **один раз**, обычно в объявлении (там, где его видит место вызова); в определении повторять нельзя;
- (2) **ошибка**: после параметра со значением по умолчанию **все остальные** тоже должны его иметь;
- (3) `h(1)` **неоднозначен**: подходят и `h(int)`, и `h(int, int = 0)` — значения по умолчанию **не создают новых перегрузок**, но делают вызовы с меньшим числом аргументов допустимыми для нескольких функций.

@@ id=init-vs-assign type=term src="Инициализация и присваивание"
Q: Чем инициализация отличается от присваивания? Покажи на примерах, где это различие важно.
A:
**Инициализация** задаёт начальное состояние объекта **при его создании**, **присваивание** меняет значение уже существующего.

```cpp
int value = 10;   // инициализация: объект создан сразу со значением
value = 20;       // присваивание: объект уже есть
```
Различие принципиально там, где присваивания нет или оно запрещено: `const int c = 1;` — корректно, `const int c; c = 1;` — ошибка; ссылка `int& r = x;` — привязка при создании, а `r = y;` присваивание меняет сам объект (не перепривязка). Знак `=` в объявлении — инициализация, а не оператор присваивания.

@@ id=vexing-parse type=pitfall src="Пустые скобки: () и {}"
Q: Чем отличаются `int value();` и `int value{};`? Что будет с `value = 42;` после каждого?
A:
- `int value();` объявляет **функцию** без параметров, возвращающую `int` (известная ловушка most vexing parse). `value = 42;` — ошибка компиляции: `value` не переменная.
- `int value{};` создаёт **переменную** `int` со значением **`0`**.

Поэтому для «пустой» инициализации переменной пишут фигурные скобки.

@@ id=init-kinds type=compare src="Виды инициализации"
Q: Какие бывают виды инициализации и как их различать? Почему эти названия пересекаются?
A:
| Вид | Пример | Смысл |
| --- | --- | --- |
| Default | `int x;` | объявление **без инициализатора** (у `int` значения нет) |
| Value | `int x{};` | пустой инициализатор; для `int` — `0` |
| Direct | `int x(2);`, `int x{2};` | аргументы в `()` или `{}` **без `=`** |
| Copy | `int x = 2;` | инициализация через `=` при объявлении |
| List | `int x{2};` | инициализация списком в `{}` |
| Aggregate | `Point p{1, 2};`, `int a[3]{1, 2, 3}` | поэлементно для массива или простой структуры |

Названия описывают **разные стороны** инициализации — есть ли инициализатор, как он записан, какой тип у объекта, — а не взаимоисключающие категории: `int x{};` — одновременно list и value, `Point p{1, 2}` — list и aggregate.

@@ id=no-initial-value type=pitfall src="Есть ли начальное значение?"
Q: Что выведет код и что не так, если убрать строку `uninitialized = 7;`?
```cpp
int uninitialized;
int zero{};
uninitialized = 7;
std::cout << uninitialized << ' ' << zero << '\n';
```
A:
Вывод: `7 0`.

`int uninitialized;` для **локальной** переменной значения не задаёт. Без присваивания чтение — **неопределённое поведение** (в C++20 так же): печатался бы мусор или что угодно. Правило: инициализировать при объявлении или присваивать до первого чтения. У **глобальных и `static`** переменных действуют дополнительные правила нулевой инициализации — они начинаются с нуля.

@@ id=init-forms-code type=code src="Несколько форм инициализации"
Q: Что выведет код и какая форма инициализации в каждой строке?
```cpp
int copy = 2;
int direct(2);
int list{2};
int zero{};
std::cout << copy << ' ' << direct << ' ' << list << ' ' << zero;
```
A:
Вывод: `2 2 2 0`.

- `int copy = 2;` — copy-initialization;
- `int direct(2);` — direct-initialization;
- `int list{2};` — direct-list-initialization;
- `int zero{};` — пустой список, value-initialization: `0`.

Во всех строках создаётся переменная `int`, различается способ записи инициализатора; категории пересекаются.

@@ id=narrowing type=code src="Фигурные скобки запрещают сужение"
Q: Какие строки не скомпилируются и почему?
```cpp
double source = 3.5;
int rounded = source;     // (1)
int checked{source};      // (2)
int exact{3};             // (3)
char small{65};           // (4)
char big{300};            // (5)
```
A:
- (1) допустимо: неявное преобразование `double` → `int`, дробная часть отбрасывается, `rounded == 3`;
- (2) **ошибка**: фигурные скобки **запрещают сужающее преобразование** (потеря информации);
- (3) допустимо: тип совпадает;
- (4) допустимо: константа `65` помещается в `char` — сужения нет;
- (5) **ошибка**: константа `300` в `char` не помещается.

Если потеря дробной части задумана, пишут явно: `static_cast<int>(source)` — читатель видит намерение.

@@ id=aggregate-init type=code src="Инициализация агрегата"
Q: Чему равны поля `circle` и как вложенные скобки разбираются по полям?
```cpp
struct Point { int x; int y; };
struct Circle { Point center; int radius; };

Circle circle{{1, 2}, 3};
```
A:
`circle.center.x == 1`, `circle.center.y == 2`, `circle.radius == 3`; печать `1 2 3`.

Значения задаются **в порядке объявления полей**: первое значение — полю `center`, а так как `center` — структура, оно само инициализируется вложенным списком `{1, 2}` (`x = 1`, `y = 2`); `3` достаётся `radius`.

```tree
circle{{1, 2}, 3}
  center = {1, 2}
    x = 1
    y = 2
  radius = 3
```

@@ id=init-choice type=concept src="Выбор формы инициализации"
Q: Как выбирать форму инициализации? Почему для классов `()` и `{}` — не одно и то же?
A:
- Инициализируйте переменную **при объявлении** и не читайте её до получения корректного значения.
- Для чисел `{}` удобно, когда нужна проверка сужения; пустые скобки дают ноль.
- Для простых структур — список значений полей.
- Для классов `()` и `{}` могут выбирать **разные конструкторы**. Пример из стандартной библиотеки: `std::vector<int> a(3);` — три элемента (нули), а `std::vector<int> b{3};` — один элемент со значением `3`.

@@ id=namespace-term type=term src="Что такое пространство имён?"
Q: Что такое пространство имён и какими свойствами оно обладает?
A:
**Пространство имён** (`namespace`) — область, в которой объединяют объявления функций, типов и переменных.

- Одинаковые имена в разных пространствах **не конфликтуют** сами по себе;
- **квалифицированное имя** с `::` указывает, где искать сущность (`screen::print`);
- одно пространство можно **дополнять** несколькими блоками;
- пространства могут быть **вложенными**; для длинного имени задают **псевдоним**.

@@ id=namespace-conflicts type=code src="Пространства имён предотвращают конфликты"
Q: Что выведет программа и почему две функции `print` не конфликтуют?
```cpp
namespace screen { void print() { std::cout << "screen\n"; } }
namespace file   { void print() { std::cout << "file\n"; } }

int main() {
    screen::print();
    file::print();
}
```
A:
Вывод: `screen`, `file`.

Квалифицированное имя `screen::print` явно указывает, какую функцию вызвать. Две `print` живут в **разных пространствах** и друг другу не мешают. Перед выбором перегрузки компилятору нужно **найти имя** функции — квалификация говорит, где искать.

@@ id=using-forms type=compare src="using: одно имя или всё пространство?"
Q: Чем using-объявление отличается от using-директивы? Какая строка не скомпилируется?
```cpp
namespace screen { void print() {} void clear() {} }

int main() {
    using screen::print;
    print();
    screen::clear();
    clear();   // ?
}
```
A:
- `using screen::print;` — **using-объявление**: вводит **одно конкретное имя**. `print()` можно вызывать без квалификации.
- `using namespace screen;` — **using-директива**: неквалифицированные имена ищутся **во всём пространстве**.

Последняя строка `clear();` — **ошибка**: объявление ввело только `print`, `clear` нужно писать как `screen::clear()`. Область действия `using` здесь — блок `main`.

@@ id=using-ambiguity type=pitfall src="Директивы using могут создать неоднозначность"
Q: Что будет при `using namespace screen; using namespace file; print();` (в обоих есть `print()`) и почему `using namespace` нельзя ставить в заголовке?
A:
Вызов `print()` **неоднозначен**: подходят обе функции, порядок директив ничего не решает — ошибка компиляции. Решение: квалифицировать (`screen::print()`) или ввести одно имя using-объявлением.

`using namespace` в **глобальной области заголовка** влияет на весь код, который заголовок включает: чужие файлы получают скрытые конфликты имён, которые невозможно отключить.

@@ id=nested-namespaces type=concept src="Вложенные пространства имён"
Q: Как называется функция `draw`, объявленная в `namespace course { namespace graphics { void draw(); } }`, и как её вызвать?
A:
Полное имя — `course::graphics::draw`: пространство `graphics` лежит внутри `course`, имена перечисляются через `::`. Вызов: `course::graphics::draw();`. Просто `draw()` без `using` не найдётся.

```tree
course
  graphics
    draw
    clear
```

@@ id=namespace-reopen-alias type=code src="Продолжение пространства и псевдоним"
Q: Что значит запись `namespace course::graphics { … }`, сколько раз можно открывать пространство и что делает `namespace gfx = course::graphics;`?
A:
- `namespace course::graphics { … }` — сокращение вложенных блоков, доступное **начиная с C++17**;
- второй блок `namespace course::graphics` **дополняет то же самое** пространство: после двух блоков в нём есть и `draw`, и `clear`;
- `namespace gfx = course::graphics;` — **псевдоним** для длинного имени: `gfx::clear()` и `gfx::draw()` вызывают те же функции.

@@ id=anonymous-namespace type=code src="Безымянное пространство имён"
Q: Что выведет программа и в каком смысле `counter` — деталь «этой единицы трансляции»?
```cpp
namespace {
    int counter = 0;
}

void increment() { ++counter; }

int main() {
    increment();
    std::cout << counter << '\n';
}
```
A:
Вывод: `1`.

Сущности из безымянного пространства видны во всём файле, где объявлены, но недоступны другим единицам трансляции. Одноимённый `counter` в безымянном пространстве другого `.cpp` — **отдельный объект**, и состояние между файлами не разделяется. Действует примерно как `static` на уровне файла (внутреннее связывание).

@@ id=anonymous-namespace-use type=pitfall src="Где применять безымянное пространство?"
Q: Для чего применяют безымянное пространство в `.cpp` и почему в заголовке оно создаст проблемы? Обеспечивает ли оно защиту данных?
A:
**Единица трансляции** — исходный файл после обработки `#include` и остальных директив препроцессора.

- В `.cpp` безымянное пространство нужно для вспомогательных функций и переменных, которые **не должны предоставляться другим единицам трансляции**.
- Это **не запрет доступа** из `main` в том же файле и не механизм защиты данных.
- В **заголовке** такие объявления создадут **отдельные сущности в каждой включающей единице трансляции** — общее состояние так не получить (у каждого `.cpp` будет свой `counter`).
