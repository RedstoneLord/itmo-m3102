@@ id=why-struct type=concept src="Точки: зачем нужны структуры"
Q: Почему вместо отдельных `int first_x, first_y, second_x, second_y` лучше завести структуру `Point`? Какую ошибку она отсекает?
A:
Что `first_x` и `first_y` — координаты **одной** точки, знает только программист, компилятор видит просто независимые `int`. Поэтому `PrintPoint(first_x, second_y)` (координаты разных точек) компилируется и даёт логическую ошибку.

Структура объединяет связанные поля в **один тип**: функция принимает `Point`, и чтобы смешать точки, нужно явно взять `x` от одной и `y` от другой, а не случайно подставить не тот аргумент. Меньше параметров, понятнее код, а тип выражает смысл данных.

@@ id=struct-term type=term src="1. Структуры"
Q: Что такое структура (`struct`) и чем тип отличается от его объектов?
A:
**Структура** — пользовательский тип, объединяющий несколько **именованных полей** (одного или разных типов) в единый объект.

`struct Point { int x; int y; };` описывает **тип** `Point`; `Point first{10, 20};` и `Point second{200, 300};` — два независимых **объекта** (экземпляра) этого типа, у каждого свои `x` и `y`. Описание типа памяти под данные не занимает, память выделяется под объекты.

@@ id=init-forms type=code src="Инициализация структур"
Q: Что выведет программа и что хранят поля каждого объекта?
```cpp
struct Point { int x; int y; };

Point first{};
Point second{200, 300};
Point third{.x = 10, .y = 20};
Point fourth;
fourth = {30, 40};
std::cout << first.x << first.y << ' ' << second.x << ' ' << third.y << ' ' << fourth.x << '\n';
```
A:
Вывод: `00 200 20 30`.

- `first{}` — пустые скобки: поля получают значение по умолчанию, для `int` это `0`;
- `second{200, 300}` — позиционно, в порядке объявления полей: `x = 200`, `y = 300`;
- `third{.x = 10, .y = 20}` — по именам полей (designated initializers, C++20);
- `fourth` без скобок — поля **не инициализированы** (мусор), поэтому значения заданы присваиванием `fourth = {30, 40}` раньше первого чтения.

@@ id=init-designated type=pitfall src="Инициализация структур"
Q: Какие из инициализаций `Point` (поля `x`, затем `y`) не скомпилируются в C++20 и почему? (а) `Point{.y = 20, .x = 10}` (б) `Point{10, .y = 20}` (в) `Point{.y = 5}` (г) `Point{.x = 1}`
A:
- (а) **ошибка**: именованные инициализаторы нужно перечислять **в порядке объявления** полей, а `y` объявлен после `x`;
- (б) **ошибка**: нельзя смешивать позиционные и именованные инициализаторы в одном выражении;
- (в), (г) допустимы: **пропускать** поля можно, пропущенное поле получает значение по умолчанию (`Point{.y = 5}` даёт `x == 0`).

@@ id=uninit-fields type=pitfall src="Инициализация структур"
Q: Что не так с этим кодом и как это исправить?
```cpp
Point point;
std::cout << point.x << '\n';
point.x = 200;
```
A:
`Point point;` без `{}` оставляет поля неинициализированными: в них «мусор», оставшийся в памяти. Чтение `point.x` до присваивания — неопределённое поведение (в лучшем случае печатается случайное число).

Исправления: инициализировать сразу (`Point point{};` — нули, или `Point point{200, 250};`), либо записывать поля **до** первого чтения (`point.x = 200; point.y = 250;`).

@@ id=field-access type=code src="Доступ к полям"
Q: Что выведет программа и для чего нужен оператор `.`?
```cpp
Point point;
point.x = 200;
point.y = 250;
std::cout << point.x << ' ' << point.y << '\n';
```
A:
Вывод: `200 250`.

Оператор `.` выбирает **поле конкретного объекта** (не указателя): `point.x` — это и читаемое, и записываемое значение поля `x` объекта `point`. Сначала поля записаны, потом прочитаны, поэтому чтение корректно.

Для **указателя** на объект нужна стрелка `->` (см. карточки об указателях на структуры).

@@ id=nested-struct type=code src="Вложенные структуры"
Q: Что значит выражение `rectangle.left_top.x` и что выведет код?
```cpp
struct Rectangle { Point left_top; Point right_bottom; };

Rectangle rectangle{
    .left_top = {0, 100},
    .right_bottom = {200, 0},
};
rectangle.left_top.x = 10;
std::cout << rectangle.left_top.x << ' ' << rectangle.right_bottom.x << '\n';
```
A:
Вывод: `10 200`.

`rectangle.left_top.x` — **цепочка обращений к полям**, слева направо: у `rectangle` выбирается поле `left_top` (объект `Point`), у него — поле `x` (`int`). Присваивание меняет только `x` левого верхнего угла; `right_bottom.x` остаётся `200`.

Вложенность позволяет собрать сложный тип из уже готовых (`Point` не описывается заново).

@@ id=grouping-fields type=concept src="Группировка полей"
Q: Зачем в `Button` вместо четырёх полей `x, y, width, height` делают подструктуры `Position` и `Size`?
A:
Это группировка по смыслу: `Button{.position = {0, 100}, .size = {400, 80}}` сразу показывает, какие значения — положение, а какие — размер, и их нельзя перепутать (разные типы `Position` и `Size`). Подобъект можно целиком передать в функцию (`Move(button.position)`) или переиспользовать в другой структуре. Лишних байт при этом нет: поля те же, меняется только структура кода.

@@ id=struct-copy type=trace src="2. Операции со структурами"
Q: Что лежит в `first` и `second` после каждой строки?
```cpp
Point first{1, 2};
Point second = first;
second.x = 10;
first = second;
```
A:
Для структуры компилятор сам создаёт копирование и присваивание, которые копируют **каждое поле**.

| Строка | `first` | `second` |
| --- | --- | --- |
| `Point first{1, 2};` | `{1, 2}` | — |
| `Point second = first;` | `{1, 2}` | `{1, 2}` (копия) |
| `second.x = 10;` | `{1, 2}` | `{10, 2}` — изменилась только копия |
| `first = second;` | `{10, 2}` | `{10, 2}` |

Структуру можно копировать, передавать и возвращать по значению, как `int`, если копируемы все её поля.

@@ id=struct-by-value type=code src="Структуры в функциях"
Q: Что выведет программа и копируются ли аргументы в `Add`?
```cpp
Point MakePoint(int x, int y) { return Point{.x = x, .y = y}; }
Point Add(Point left, Point right) {
    return Point{.x = left.x + right.x, .y = left.y + right.y};
}

int main() {
    Point first = MakePoint(239, 1);
    Point second{1, 2};
    Point sum = Add(first, second);
    std::cout << sum.x << ' ' << sum.y << ' ' << first.x << '\n';
}
```
A:
Вывод: `240 3 239`.

`Add` принимает точки **по значению**: `left` и `right` — собственные копии, поэтому `first` не меняется (`first.x == 239`). Результат — новая точка с покомпонентной суммой: `239 + 1 = 240`, `1 + 2 = 3`.

Копирование больших структур дорого; чтобы его избежать, передают по константной ссылке (отдельная тема — ссылки).

@@ id=struct-array type=concept src="Массивы структур"
Q: Что представляет собой `Record phonebook[200]{};` (где `Record` — структура из двух `std::string` и `long`) и что делает `{}`?
A:
Это массив из 200 **независимых** объектов `Record`, у каждого свои `name`, `surname` и `phone`. Структуры хранятся подряд, как любые элементы: `sizeof(phonebook) = 200 · sizeof(Record)`.

`{}` инициализирует массив «по умолчанию»: каждый элемент получает нулевое/пустое состояние (`phone == 0`, строки пустые). Без `{}` числовые поля остались бы неопределёнными.

@@ id=arrow-operator type=concept src="Указатели на структуры"
Q: Как обратиться к полю структуры через указатель? Почему `pointer->name` и `(*pointer).name` — одно и то же и почему нельзя написать `*pointer.name`?
A:
`pointer->name` — сокращение для `(*pointer).name`: сначала указатель разыменовывается (получаем объект), затем выбирается поле.

Скобки в `(*pointer).name` обязательны: оператор `.` связывается **сильнее** `*`, поэтому `*pointer.name` читается как `*(pointer.name)` — это попытка взять поле у указателя (у него полей нет) и разыменовать его, то есть ошибка компиляции. Стрелка `->` избавляет от этих скобок.

@@ id=find-record type=algo src="Указатели на структуры"
Q: Как работает `Record* FindRecord(long phone, Record* records, std::size_t count)`, что она возвращает и как правильно использовать результат?
A:
Линейный поиск: для `index = 0…count-1` сравнивается `records[index].phone` с `phone`; при совпадении возвращается адрес `&records[index]`, если ничего не нашлось — `nullptr`. Время $O(n)$, память $O(1)$.

Возвращён **указатель на элемент массива**, а не копия: через него можно изменить запись, и нет затрат на копирование.

Использование: **обязательно** проверить на `nullptr`, прежде чем применять `->`:
```cpp
Record* record = FindRecord(22345, phonebook, 200);
if (record != nullptr) {
    std::cout << record->name << ' ' << record->surname << '\n';
}
```
Обращение к полю по нулевому указателю — неопределённое поведение.

@@ id=dangling-element type=pitfall src="Указатели на структуры"
Q: Когда указатель на элемент массива (как `record` из `FindRecord`) перестаёт быть безопасным?
A:
Указатель на элемент действителен, пока существует сам массив **и** сам элемент остаётся на том же месте. Опасно:

- массив вышел из области видимости/уничтожен — указатель «висячий» (dangling), обращение — UB;
- элементы переставили местами (например, сортировка): указатель остаётся прежним, а по адресу теперь другая запись;
- в контейнере с перевыделением памяти (например, `std::vector` при росте) старые адреса недействительны.

Правило: не хранить указатель на элемент дольше, чем гарантирована его неподвижность; при сомнении — хранить индекс и получать адрес заново.

@@ id=struct-layout-calc type=calc src="Размещение структуры в памяти"
Q: Найди смещения полей, итоговые `sizeof` и `alignof` (`sizeof(int) = 4`, `alignof(int) = 4`, `short` — 2, `double` — 8):
(а) `struct A { char a; int b; char c; };`
(б) `struct B { int b; char a; char c; };`
(в) `struct C { char a; short s; int i; };`
(г) `struct D { double d; char c; };`
A:
Поле кладётся по ближайшему адресу, кратному его выравниванию; в конце размер округляется вверх до кратного выравниванию структуры (оно равно наибольшему выравниванию поля).

- (а) `a`@0, 3 байта padding, `b`@4, `c`@8, 3 байта завершающего padding → `sizeof = 12`, `alignof = 4`;
- (б) `b`@0, `a`@4, `c`@5, 2 байта завершающего padding → `sizeof = 8`, `alignof = 4`;
- (в) `a`@0, 1 байт padding, `s`@2, `i`@4 → `sizeof = 8`, `alignof = 4`;
- (г) `d`@0, `c`@8, 7 байт завершающего padding → `sizeof = 16`, `alignof = 8`.

Наивная сумма размеров полей даёт меньше: для (а) $1 + 4 + 1 = 6$, а не 12.

@@ id=padding-term type=term src="Размещение структуры в памяти"
Q: Что такое выравнивание (`alignof`) и padding? Чем выравнивание отличается от размера?
A:
**Выравнивание** `alignof(T)` — требование к адресу объекта типа `T`: если `alignof(T) == 8`, адрес должен делиться на 8. Это **не размер**: у `char` оба равны 1, у `int` — 4 и 4, а у структуры `char a; std::int64_t b;` выравнивание 8, а размер 16.

**Padding** — байты-пустышки, которые компилятор вставляет **между полями и в конце структуры**, чтобы каждое поле стояло по адресу, удовлетворяющему его выравниванию. Они не хранят значений полей, но входят в `sizeof`.

@@ id=poor-layout type=concept src="Размещение структуры в памяти"
Q: Почему `struct PoorLayout { char a; std::int64_t b; char c; };` занимает 24 байта, а не 10, и в каком порядке лежат байты?
A:
`b` требует адрес, кратный 8, поэтому после `a`@0 вставляется **7 байт** padding и `b` начинается со смещения 8 (8–15); `c` стоит на смещении 16. Ещё нужен **завершающий padding** в 7 байт, чтобы размер стал кратным 8: итого $1 + 7 + 8 + 1 + 7 = 24$.

```array
title: PoorLayout по байтам (p — padding)
["a","p","p","p","p","p","p","p","b","b","b","b","b","b","b","b","c","p","p","p","p","p","p","p"] highlight: 8
```

@@ id=tail-padding type=concept src="Размещение структуры в памяти"
Q: Зачем нужен завершающий padding в конце структуры? Что сломалось бы без него в массиве `PoorLayout[2]`?
A:
Размер структуры должен быть кратен её выравниванию, чтобы **каждый элемент массива** тоже был выровнен. Без завершающего padding `PoorLayout` занимала бы 17 байт, и во втором элементе поле `b` лежало бы по смещению $17 + 8 = 25$ — не кратно 8, выравнивание нарушено.

С округлением до 24 второй элемент начинается со смещения 24, а его `b` — со смещения 32; оба кратны 8 (при условии, что начало массива выровнено по 8).

@@ id=reorder-fields type=compare src="Размещение структуры в памяти"
Q: Сравни `PoorLayout { char a; int64 b; char c; }` и `CompactLayout { int64 b; char a; char c; }`: размер, где `b`, где padding. Какое практическое правило отсюда следует?
A:
| | `PoorLayout` | `CompactLayout` |
| --- | --- | --- |
| Порядок | `a`, `b`, `c` | `b`, `a`, `c` |
| `offsetof(b)` | 8 | 0 |
| Padding | 7 между `a` и `b`, 7 в конце | 6 в конце |
| `sizeof` / `alignof` | 24 / 8 | 16 / 8 |

Набор полей одинаков, размер различается на 8 байт: в `CompactLayout` `b` уже на выровненном смещении 0, `a` и `c` — на 8 и 9, остаются 6 байт хвоста.

**Правило:** располагать поля от самых «широких» (наибольшее выравнивание) к самым «узким» — меньше padding и меньше размер. Конкретные значения определяются компилятором и ABI платформы, а не стандартом.

@@ id=pack-term type=calc src="Уплотнение"
Q: Что даёт `#pragma pack(push, 1)` для `struct { char tag; std::int32_t value; }`? Найди размер, выравнивание и смещение `value` с ним и без него.
A:
| | обычная `Data` | `#pragma pack(push, 1)` `PackedData` |
| --- | --- | --- |
| `tag` | смещение 0 | смещение 0 |
| `value` | смещение 4 (3 байта padding) | смещение 1 |
| `sizeof` | 8 | $1 + 4 = 5$ |
| `alignof` | 4 | 1 |

`pragma pack` отключает padding: выравнивание полей становится 1. Экономия памяти — 3 байта на объект; `push`/`pop` ограничивают действие директивы нужной структурой. Это **расширение компилятора**, а не часть стандарта.

@@ id=pack-pitfall type=pitfall src="Уплотнение"
Q: Какие риски у уплотнённых структур, кроме выигрыша в размере?
A:
- Многобайтовые поля оказываются по адресам, **не кратным естественному выравниванию** (невыровненными): на части процессоров это медленнее, а на некоторых вовсе ошибка. Указатель на такое поле (`&packed.value`) может быть невыровненным — использовать его осторожно.
- `#pragma pack` — не стандарт C++, поведение зависит от компилятора.
- При работе с бинарными форматами (файлы, сетевые пакеты) отдельно нужно учитывать **порядок байтов** платформы — уплотнение решает только вопрос лишних байт, но не endianness.

@@ id=packed-speed type=concept src="Меньше памяти — медленнее обработка?"
Q: Станет ли суммирование поля `value` по массиву `PackedData` медленнее, чем по `Data`? Какие факторы тянут в разные стороны?
A:
Не обязательно. Факторы:

- **Против уплотнения:** невыровненное `value` может пересечь границу **кеш-линии** — тогда процессору нужны две линии вместо одной, что дороже.
- **За уплотнение:** массив занимает меньше памяти (4096 элементов: $4096 \cdot 8 = 32$ КиБ против $4096 \cdot 5 = 20$ КиБ) и лучше помещается в кеш, значит, меньше обращений к основной памяти.
- Влияет и то, как компилятор векторизует цикл.

Итог зависит от процессора и параметров сборки: «меньше памяти — медленнее» не гарантировано, это проверяют **измерением**. Кеш-линия — блок фиксированного размера, которым кеш обменивается с памятью (не побайтово).

@@ id=benchmark-method type=concept src="Выравнивание: сравниваем скорость"
Q: Зачем в бенчмарках `DoNotOptimize`, `ClobberMemory` и создание вектора **вне** цикла `for (auto _ : state)`?
A:
Меряется только время суммирования, поэтому:

- массив создаётся и заполняется **до** измеряемого цикла — иначе в результат попало бы время его построения;
- `benchmark::DoNotOptimize(data.data())` и `(sum)` сообщают оптимизатору, что значения используются, — иначе он может выбросить весь «бесполезный» подсчёт;
- `benchmark::ClobberMemory()` не даёт считать память неизменной между итерациями, заставляя перечитывать данные, как в реальной работе.

Оба теста суммируют одинаковые 4096 значений — отличие только в **расположении** данных в памяти (`Data` и `PackedData`). Результат — суммарный эффект выравнивания, плотности данных и векторизации.

@@ id=alignas-calc type=calc src="alignas: зачем увеличивать выравнивание"
Q: Что выведет программа и почему `sizeof(AlignedData)` вырос с 4 до 64?
```cpp
struct Data { std::int32_t value; };
struct alignas(64) AlignedData { std::int32_t value; };

AlignedData items[2]{};
std::cout << sizeof(Data) << ' ' << alignof(Data) << '\n';
std::cout << sizeof(AlignedData) << ' ' << alignof(AlignedData) << '\n';
std::cout << sizeof(items) << '\n';
```
A:
Вывод:
```text
4 4
64 64
128
```
`Data` — обычный `int32_t`: размер и выравнивание 4. `alignas(64)` задаёт выравнивание 64, а размер должен быть кратен выравниванию (чтобы каждый элемент массива тоже стоял на границе 64), поэтому добавляется padding: `sizeof = 64`, массив из двух — $2 \cdot 64 = 128$. Адрес каждого элемента делится на 64: $\text{address} \bmod 64 = 0$.

@@ id=false-sharing type=concept src="alignas: зачем увеличивать выравнивание"
Q: Что такое false sharing и как `alignas(64)` с ним борется? Почему это платное решение?
A:
**False sharing** — два **независимых** объекта, которые меняют **разные потоки**, оказались в одной кеш-линии. Кеши ядер согласуются целыми линиями, поэтому запись одним потоком инвалидирует линию целиком и у другого ядра — хотя оно трогало другой объект. Получается постоянный лишний обмен между ядрами.

`alignas(64)` разносит такие объекты по **разным** кеш-линиям (если линия 64 байта): каждый элемент массива лежит в своей линии и не мешает соседям.

Цена: 64 байта вместо 4 полезных (в 16 раз больше памяти); выигрыш не гарантирован, применять стоит, только когда false sharing — реальная проблема.

@@ id=alignas-where type=concept src="alignas: зачем увеличивать выравнивание"
Q: Откуда взять значение для `alignas` и зачем ещё увеличивать выравнивание, кроме false sharing?
A:
- Размер кеш-линии зависит от платформы: `64` в примере — выбор для иллюстрации, не константа языка. С C++17 в `<new>` есть `std::hardware_destructive_interference_size` — рекомендуемое реализацией расстояние между независимо изменяемыми объектами. Оно вычисляется **во время компиляции**, а не измеряется при запуске; есть ли оно в библиотеке, проверяют макросом `__cpp_lib_hardware_interference_size`, иначе выравнивание подбирают вручную.
- **SIMD-инструкции** (несколько чисел за одну команду) часто требуют, чтобы данные лежали по границе определённого размера; значение зависит от инструкции.

@@ id=union-term type=term src="4. Объединения"
Q: Что такое `union` и чем он отличается от структуры по размещению в памяти? Чему равен `sizeof(Value)` для `union Value { std::int64_t integer; double real; char text[16]; }`?
A:
**Объединение** — тип, **все поля которого занимают одну и ту же память** (начинаются с одного адреса). Осмысленно («активно») в каждый момент только то поле, что записано последним.

Размер структуры — примерно сумма полей плюс padding, а размер объединения — **максимум** из размеров полей с учётом выравнивания: для `Value` это $\max(8, 8, 16) = 16$ (выравнивание 8 — 16 кратно ему), и `sizeof(Value) == 16`.

```diagram
diagram
M: db "16 байт общей памяти"
I: box "integer (int64_t, 8 байт)"
R: box "real (double, 8 байт)"
T: box "text (char[16], 16 байт)"
I -> M : с начала
R -> M : с начала
T -> M : с начала
```

@@ id=union-active-ub type=code src="Активное поле объединения"
Q: Какие строки в этом коде корректны, а какая — неопределённое поведение?
```cpp
Value value{};
value.integer = 239;
std::cout << value.integer << '\n';
value.real = 3.14;
std::cout << value.real << '\n';
std::cout << value.integer << '\n';
```
A:
- `value.integer = 239;` и первая печать `value.integer` — корректны: `integer` активно.
- `value.real = 3.14;` записывает ту же память как `double` и делает активным `real`; печать `value.real` корректна и даст `3.14`.
- Последняя строка — **UB**: читается `integer`, но активно `real`, и значение `239` уже перезаписано.

Чтение неактивного поля обычного `union` в стандартном C++ — неопределённое поведение: `union` хранит **альтернативные** значения, а не служит способом переинтерпретировать биты.

@@ id=bit-cast type=code src="Активное поле объединения"
Q: Как честно, без UB, получить битовое представление `double` как 64-битное целое? Допиши два варианта:
```cpp
double real = 3.14;
std::uint64_t bits;
// 1) до C++20: ...
// 2) C++20: ...
```
A:
```cpp
double real = 3.14;
std::uint64_t bits;
std::memcpy(&bits, &real, sizeof(bits));              // 1) <cstring>
auto bits2 = std::bit_cast<std::uint64_t>(real);      // 2) C++20, <bit>
```
- `std::memcpy` копирует **байты** между объектами — легальный способ переинтерпретации, оптимизатор обычно сводит его к одной инструкции.
- `std::bit_cast<To>(from)` (C++20) — явный и безопасный аналог для типов **одинакового размера** (иначе ошибка компиляции).

Не годятся: `union`-трюк (UB) и `*reinterpret_cast<std::uint64_t*>(&real)` (нарушает правила доступа по типу).

@@ id=tagged-union type=concept src="Tagged union: данные и тег"
Q: Что такое tagged union и зачем нужен тег? Что нужно, чтобы читать поле безопасно?
A:
`union` сам **не помнит**, какое поле активно, — это должен отслеживать программист. **Tagged union** — объединение вместе с отдельным полем-**тегом**, которое сообщает, какое поле сейчас активно:

```cpp
struct Figure {
    FigureType type;    // тег: Triangle / Rectangle / Circle
    FigureData data;    // union из triangle, rectangle, circle
};
```
Безопасное чтение — сначала проверить тег (`switch (figure.type)`), затем читать **ровно то поле**, которое ему соответствует (`case Circle:` → `figure.data.circle`). Тогда не читается неактивное поле. Так в одном массиве `Figure figures[]` хранятся разнородные фигуры.

@@ id=tagged-union-code type=trace src="Tagged union: данные и тег"
Q: Что выведет цикл и какие поля объединения при этом читаются?
```cpp
Figure figures[]{
    {FigureType::Circle, {.circle = {{0, 0}, 10}}},
    {FigureType::Rectangle, {.rectangle = {{0, 10}, {20, 0}}}},
    {FigureType::Triangle, {.triangle = {{0, 0}, {4, 0}, {0, 3}}}},
};
for (Figure figure : figures) {
    switch (figure.type) {
    case FigureType::Circle:    std::cout << "Radius: " << figure.data.circle.radius << '\n'; break;
    case FigureType::Rectangle: std::cout << "Left x: " << figure.data.rectangle.left_top.x << '\n'; break;
    case FigureType::Triangle:  std::cout << "Vertex A x: " << figure.data.triangle.a.x << '\n'; break;
    }
}
```
A:
Вывод:
```text
Radius: 10
Left x: 0
Vertex A x: 0
```
Для круга по тегу читается `data.circle.radius` (`10`), для прямоугольника — `data.rectangle.left_top.x` (`0`), для треугольника — `data.triangle.a.x` (`0`). Остальные поля `data` в каждой итерации не трогаются. `for (Figure figure : figures)` копирует элементы по значению.

@@ id=tagged-union-pitfall type=pitfall src="Tagged union: данные и тег"
Q: Что не так с этим кодом? Что гарантирует смена тега?
```cpp
Figure f{FigureType::Circle, {.circle = {{0, 0}, 5}}};
f.type = FigureType::Rectangle;
std::cout << f.data.rectangle.left_top.x << '\n';
```
A:
Тег и активное поле объединения — **две независимые переменные**. Присваивание `f.type = Rectangle` активное поле не меняет: оно по-прежнему `circle`, а читается `rectangle` — неактивное поле, **UB**.

Согласованность обеспечивает только программист: менять тег и **одновременно** записывать соответствующее поле (`f.data.rectangle = {...}`; `f.type = Rectangle`). Забыть одно из двух — типичная ошибка ручного tagged union.

@@ id=tagged-union-size type=calc src="Tagged union: данные и тег"
Q: Найди `sizeof(Figure)` (`sizeof(float) == 4`, `enum class` занимает 4 байта) и сравни с хранением всех трёх фигур одновременно в структуре.
A:
Размеры вариантов: `Point` — 2 `float` = 8; `Triangle` — 3 точки = 24; `Rectangle` — 2 точки = 16; `Circle` — точка и радиус = 12.

- `sizeof(FigureData) = max(24, 16, 12) = 24`, выравнивание 4;
- `sizeof(Figure) = 4 (тег) + 24 = 28`.

Если бы все три фигуры лежали в обычной структуре, понадобилось бы $24 + 16 + 12 = 52$ байта (плюс тег). Объединение экономит память, пока нужен **только один** вариант за раз.

@@ id=variant type=concept src="Tagged union: данные и тег"
Q: Какие проблемы ручного tagged union решает `std::variant` и как с ним работать?
A:
Вручную легко забыть обновить тег или прочитать не то поле. `std::variant<Triangle, Rectangle, Circle>` **хранит тег внутри себя** и сам управляет временем жизни активного объекта — отдельные `enum` и `union` не нужны:

```cpp
using Figure = std::variant<Triangle, Rectangle, Circle>;
Figure figure = Circle{.center = {0.0F, 0.0F}, .radius = 10.0F};
```
Читают через `std::get<T>` (бросает исключение при неверном типе), `std::get_if<T>` (вернёт `nullptr`) и `std::visit` (вызов по активному типу). Рассинхронизации тега и данных быть не может.

@@ id=type-punning type=concept src="Tagged union: данные и тег"
Q: Что такое type punning через `union Name { struct {char name[13]; char code[3];} text; struct {int32 i1, i2, i3, i4;} words; }` и почему так писать нельзя «по стандарту»?
A:
**Type punning** — намеренный «взгляд» на одни и те же байты через разные поля: те же 16 байт читаются то как две строки (`text.name`, `text.code`), то как четыре 32-битных числа (`words.i1…i4`). Идея — сравнивать имена четырьмя целыми вместо `strcmp`.

Но запись через `text` и чтение через `words` — это чтение **неактивного** поля: UB в ISO C++. Код работает только как **расширение компилятора** (GCC его допускает). Переносимо — `std::memcpy`/`std::bit_cast` или сравнение байтов `std::memcmp`.

@@ id=name-compare type=concept src="Tagged union: данные и тег"
Q: Когда сравнение четырёх `int32` (`IntCompare`) эквивалентно сравнению двух строк (`NameCompare`) и почему первое быстрее?
A:
Сравнение всех 16 байт совпадает со сравнением строк, **только если** у обеих строк одинаковое содержимое **после** завершающего `'\0'` (мусор после терминатора для `strcmp` не важен, а для побайтового сравнения важен). В примере массивы `name` и `code` заполнены целиком, включая терминатор, поэтому условие выполняется.

`IntCompare` — это четыре простые машинные операции сравнения; `strcmp` идёт **байт за байтом**, ища `'\0'` в каждой строке, и вызывается дважды. Поэтому на тех же данных целочисленное сравнение быстрее.

@@ id=bench-results type=pitfall src="Tagged union: данные и тег"
Q: Можно ли по результату «`IntCompare` быстрее `NameCompare`» сделать вывод, что так всегда надо писать?
A:
Нет. Выигрыш зависит от входных данных, компилятора, платформы и флагов оптимизации. Главное — `IntCompare` читает неактивное поле `union`: это UB в ISO C++ и работает только как расширение GCC, значит, код **непереносим** (Quick Bench для опыта выбирают именно GCC).

Практический вывод: ускорение нужно подтверждать измерением на своих данных, а тот же приём реализовывать законно — через `memcmp` или `bit_cast`, а не через чтение неактивного поля.
