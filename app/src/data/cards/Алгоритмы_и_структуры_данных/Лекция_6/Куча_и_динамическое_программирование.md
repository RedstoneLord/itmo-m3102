@@ id=heap-two-levels type=concept src="Что такое куча"
Q: Как устроена куча логически и физически и что даёт такое устройство? За какое время доступен экстремум?
A:
**Логически** куча — бинарное дерево, **физически** — обычный массив, в котором элементы дерева лежат подряд. В корне всегда самый «главный» элемент: минимум или максимум (по виду кучи).

Следствия: экстремум берётся из первой ячейки за $O(1)$; родителя и детей находят вычислением по индексу (без указателей). Нумерация узлов — сверху вниз и слева направо с нуля; она и есть индекс в массиве.

@@ id=heap-index-calc type=calc src="Что такое куча"
Q: Для кучи $[105, 81, 95, 65, 75, 55, 45, 25]$ найди индексы детей узла $2$ и родителей узлов $7$ и $5$ и проверь, что это макс-куча.
A:
```tree
tree
105
  81
    65
      25
    75
  95
    55
    45
```

Дети узла $2$ (значение $95$): $2\cdot2+1 = 5$ и $2\cdot 2 + 2 = 6$ — значения $55$ и $45$. Родитель узла $7$ (значение $25$): $\lfloor (7-1)/2 \rfloor = 3$ (значение $65$). Родитель узла $5$ (значение $55$): $\lfloor 4/2 \rfloor = 2$ (значение $95$).

Свойство макс-кучи: $105 \ge 81, 95$; $81 \ge 65, 75$; $95 \ge 55, 45$; $65 \ge 25$ — каждый родитель не меньше детей, поэтому максимум в корне.

@@ id=taxi-analogy type=concept src="Аналогия: Яндекс Такси"
Q: Какую идею очереди с приоритетом иллюстрирует аналогия с заявками на такси?
A:
Заявки выстраиваются в **очередь**, и порядок обслуживания определяется признаком — километражем, временем ожидания и т. п. То есть место в очереди задаёт не момент поступления, а *приоритет*, и из очереди нужно быстро доставать «самую главную» заявку. Именно такую задачу (быстро получить лучший элемент и поддерживать порядок при изменениях) решает пирамида.

@@ id=heap-pattern type=concept src="Пирамида как паттерн"
Q: Какому общему паттерну учит пирамида и что общего у кучи и мемоизации?
A:
Пирамида — первый паттерн, показывающий, как **использовать предыдущие вычисления**: результат уже проделанной работы (упорядоченность элементов) сохраняется в структуре и участвует в следующих операциях, а не вычисляется заново. Мемоизация — тот же принцип: хранить результаты и не повторять работу. В пирамиде сохраняются результаты сравнений (следующий максимум за $O(\log n)$, а не $O(n)$), в динамическом программировании — ответы на подзадачи.

@@ id=pq-def type=term src="Очередь с приоритетом"
Q: Что такое приоритет и очередь с приоритетом и как они связаны с кучей?
A:
**Приоритет** — динамический признак объекта, по которому определяется его место в очереди; «динамический» значит, что он может меняться со временем (пример — положение абитуриента в конкурсном списке). **Очередь с приоритетом** — очередь, в которой порядок элементов определяется приоритетами.

Очередь реализуется как **надстройка над кучей**; сама очередь — массив, в котором хранятся элементы кучи. Поэтому операции очереди сводятся к sift up и sift down.

@@ id=pq-insert type=algo src="Очередь с приоритетом"
Q: Как добавить элемент в кучу (максимум в корне)? Напиши sift up, объясни инвариант и сложность.
A:
Новый элемент записывается в **конец** массива (размер $+1$, форма дерева сохраняется), затем «всплывает» (sift up): пока он больше родителя, меняется с ним местами.

```python
def sift_up(a, i):
    while i > 0:
        p = (i - 1) // 2
        if a[p] < a[i]:
            a[p], a[i] = a[i], a[p]
            i = p
        else:
            break
```

Инвариант: кроме, возможно, элемента `i` (нарушившего порядок только с родителем), остальные пары «родитель — ребёнок» корректны. Каждый обмен поднимает элемент на уровень выше, а высота $O(\log n)$, поэтому добавление стоит $O(\log n)$.

@@ id=pq-insert-trace type=trace src="Очередь с приоритетом"
Q: Добавь $100$ в макс-кучу $[105, 81, 95, 65, 75, 55, 45, 25]$. Какой массив получится?
A:
Элемент записывается в конец — индекс $8$: $[105, 81, 95, 65, 75, 55, 45, 25, 100]$.

- Родитель индекса $8$ — $\lfloor 7/2 \rfloor = 3$ (значение $65$). $65 < 100$ — обмен: индекс $3$ теперь $100$, индекс $8$ — $65$.
- Родитель индекса $3$ — $1$ (значение $81$). $81 < 100$ — обмен: индекс $1$ — $100$, индекс $3$ — $81$.
- Родитель индекса $1$ — $0$ (значение $105$). $105 \ge 100$ — стоп.

Результат: $[105, 100, 95, 81, 75, 55, 45, 25, 65]$. Три сравнения, два обмена — не больше высоты дерева.

@@ id=inc-priority type=algo src="Повышение приоритета"
Q: Что делает операция повышения приоритета элемента кучи? Выполни её для узла $5$ в $[105, 81, 95, 65, 75, 55, 45, 25]$ при повышении $55 \to 96$.
A:
Меняем значение в узле и запускаем **sift up**: пока значение больше родителя, меняем с ним местами. Для узла $5$:

1. Записываем $96$ вместо $55$.
2. Родитель — узел $2$ ($95$). $96 > 95$ — обмен, $96$ теперь в узле $2$.
3. Родитель — узел $0$ ($105$). $96 < 105$ — стоп.

Результат: $[105, 81, 96, 65, 75, 95, 45, 25]$; элемент поднялся с позиции $5$ на $2$.

```array
title: Подъём элемента (sift up) после повышения приоритета
[105, 81, 95, 65, 75, 55, 45, 25]
pointers: i, p
print: last
code:
let i = 5;
let p = 0;
a[i] = 96;
say("Приоритет элемента с индексом 5 увеличен с 55 до 96");
while (i > 0) {
  p = Math.floor((i - 1) / 2);
  if (a[p] < a[i]) {
    swap(a, p, i);
    i = p;
  } else {
    break;
  }
}
```

@@ id=dec-priority type=algo src="Понижение приоритета"
Q: Что нужно сделать после понижения приоритета элемента в макс-куче? Покажи на понижении корня $105 \to 60$ в $[105, 81, 95, 65, 75, 55, 45, 25]$.
A:
Элемент становится «менее важным» и опускается: запускаем **sift down** (обмен с **большим** ребёнком, пока узел меньше него).

Корень $60$: дети $81$ и $95$, больший $95 > 60$ — обмен: $[95, 81, 60, 65, 75, 55, 45, 25]$. Теперь $60$ в узле $2$, дети — узлы $5, 6$ ($55$, $45$); больший $55 < 60$ — стоп. Итог: $[95, 81, 60, 65, 75, 55, 45, 25]$ — снова макс-куча.

@@ id=up-down-rule type=pitfall src="Понижение приоритета"
Q: Сформулируй правило «повысили — sift up, понизили — sift down» и скажи, как оно меняется для мин-кучи и что будет, если применить не ту операцию.
A:
Для **макс-кучи**: приоритет *увеличили* → sift up; *уменьшили* → sift down.

В **мин-куче** главный элемент — наименьший, поэтому всё наоборот: значение *уменьшили* → элемент становится «важнее» → sift up; *увеличили* → sift down. Правило на самом деле формулируется через важность элемента: стал важнее — вверх, менее важен — вниз.

Если применить не ту операцию, куча останется нарушенной: например, повысили $55 \to 96$ и запустили sift down — у листа детей нет, обмена не будет, а $96 > 95$ у родителя остаётся.

@@ id=heap-delete type=algo src="Удаление элемента"
Q: Как удалить произвольный элемент из кучи и зачем после этого нужны и sift down, и sift up?
A:
```diagram
title: Удаление элемента из кучи
A: round "Элемент выбран для удаления"
B: box "Переместить его в конец массива"
C: box "size = size - 1"
D: box "sift down"
E: box "sift up"
A -> B
B -> C
C -> D
D -> E
```

На место удалённого попадает бывший последний элемент. Он может оказаться **больше родителя** (тогда сработает sift up) или **меньше детей** (тогда sift down). Какой из случаев, заранее неизвестно, поэтому выполняют обе операции; фактически сдвинет элемент только одна. Стоимость $O(\log n)$: не перестраиваем всю кучу, порядок восстанавливается локально, вдоль одного пути.

@@ id=heap-delete-calc type=calc src="Удаление элемента"
Q: Удали корень из $[105, 81, 95, 65, 75, 55, 45, 25]$. Потом удали элемент $40$ (индекс $3$) из макс-кучи $[100, 50, 90, 40, 30, 80, 70]$. Какая операция сработала в каждом случае?
A:
**Корень.** Меняем с последним ($25$) и уменьшаем размер: $[25, 81, 95, 65, 75, 55, 45]$. Sift down: дети корня $81, 95$ → обмен с $95$: $[95, 81, 25, 65, 75, 55, 45]$; у $25$ в узле $2$ дети $55, 45$ → обмен с $55$: $[95, 81, 55, 65, 75, 25, 45]$. Сработал **sift down**.

**Элемент $40$.** Последний элемент $70$ ставится на индекс $3$, размер $6$: $[100, 50, 90, 70, 30, 80]$. Родитель индекса $3$ — узел $1$ ($50$), $70 > 50$ — обмен: $[100, 70, 90, 50, 30, 80]$. Сработал **sift up** (вниз двигаться некуда: у узла $3$ дети с индексами $7, 8$ вне кучи).

@@ id=heap-find type=concept src="Поиск элемента в куче"
Q: Почему найти произвольный элемент в куче нетривиально и как искать его за $O(1)$?
A:
Куча упорядочена только вдоль веток (родитель — дети), между разными ветками порядка нет, поэтому произвольный элемент приходится искать перебором за $O(n)$. Бинарное дерево поиска дало бы $O(\log n)$, но платить за поиск логарифм не хочется.

За $O(1)$: поиск идёт **по уникальному значению**, а для каждого значения хранится **указатель** на место элемента в куче (например, таблица «значение → индекс»). Так можно сразу найти элемент, чтобы изменить приоритет или удалить его.

@@ id=heap-find-pitfall type=pitfall src="Поиск элемента в куче"
Q: Почему поиск по указателю работает только для уникальных значений и что нужно делать с указателями при каждом обмене в куче?
A:
По неуникальному значению нельзя однозначно сказать, о каком элементе речь: указатель один, а подходящих элементов несколько.

Ещё одна ловушка: sift up, sift down и удаление **перемещают** элементы, поэтому при каждом обмене нужно обновлять сохранённые указатели (индексы), иначе таблица «значение → место» устареет и поиск вернёт чужую ячейку. Это добавляет $O(1)$ к каждому обмену, асимптотика $O(\log n)$ сохраняется.

@@ id=pq-summary type=compare src="Итог по очереди с приоритетом"
Q: Сравни реализацию очереди с приоритетом на куче с неупорядоченным и отсортированным массивами по основным операциям. Что делать, если приоритет неизменяемый или задан классами?
A:
| Операция | Куча | Неупорядоченный массив | Отсортированный массив |
|---|---|---|---|
| Получить максимум | $O(1)$ | $O(n)$ | $O(1)$ |
| Добавить | $O(\log n)$ (sift up) | $O(1)$ | $O(n)$ (сдвиг) |
| Извлечь максимум | $O(\log n)$ | $O(n)$ | $O(1)$ |
| Изменить приоритет | $O(\log n)$ (с указателем на место) | $O(1)$ (с указателем) | $O(n)$ |

Куча — компромисс: все операции не хуже $O(\log n)$. Если приоритет **неизменяемый** или задаётся **классами приоритетов**, используют другие структуры, например «коробочки» — по одной обычной очереди на каждый класс приоритета.

@@ id=fib-naive type=algo src="Числа Фибоначчи и наивная рекурсия"
Q: Как определяются числа Фибоначчи, как выглядит наивная рекурсия и почему в её дереве вызовов видны повторы?
A:
$F_1 = F_2 = 1$, $F_n = F_{n-1} + F_{n-2}$ при $n \ge 3$.

```python
def fib(n):
    if n <= 2:
        return 1
    else:
        return fib(n - 1) + fib(n - 2)
```

Абстрактное дерево значений для $n = 4$:

```tree
tree
4
  3
    2
      1
    1
  2
    1
```

Поддерево с вершиной $2$ встречается **дважды** — одна и та же подзадача считается несколько раз. Число вызовов растёт как само $F(n)$, то есть $O(F(n))$ — экспоненциально.

@@ id=fib-calls type=proof src="Числа Фибоначчи и наивная рекурсия"
Q: Выведи формулу числа вызовов $C_n = 2F(n) - 1$ для наивной рекурсии и проверь для $n = 3, 4, 5$.
A:
Вызов `fib(n)` при $n \ge 3$ — это он сам плюс вызовы `fib(n-1)` и `fib(n-2)`:
$$C_n = C_{n-1} + C_{n-2} + 1, \qquad C_1 = C_2 = 1.$$
Прибавим $1$ к обеим частям: $C_n + 1 = (C_{n-1} + 1) + (C_{n-2} + 1)$ — последовательность $C_n + 1$ подчиняется правилу Фибоначчи. Начало: $C_1 + 1 = C_2 + 1 = 2 = 2F_1 = 2F_2$. Значит, $C_n + 1 = 2F(n)$, то есть $C_n = 2F(n) - 1$.

Проверка: $C_3 = 3 = 2\cdot 2 - 1$, $C_4 = 5 = 2\cdot 3 - 1$, $C_5 = 9 = 2\cdot 5 - 1$.

@@ id=fib-growth type=calc src="Числа Фибоначчи и наивная рекурсия"
Q: Оцени число вызовов наивной рекурсии для $n = 50$ и объясни, почему рост экспоненциальный.
A:
$F(n) \approx \dfrac{\varphi^n}{\sqrt 5}$, где $\varphi = \dfrac{1+\sqrt5}{2} \approx 1{,}618$. Для $n = 50$: $F(50) = 12\,586\,269\,025 \approx 1{,}26\cdot10^{10}$, а число вызовов $C_{50} = 2F(50) - 1 \approx 2{,}5\cdot 10^{10}$. Столько операций интерпретатор Python за разумное время не выполнит. Рост показательный, потому что при увеличении $n$ на $1$ число вызовов умножается на $\varphi \approx 1{,}6$. Память стека при этом — глубина $O(n)$, не число вызовов.

@@ id=memoization type=term src="Мемоизация"
Q: Что такое мемоизация, как она исправляет рекурсию Фибоначчи и какие две ошибки в реализации типичны?
A:
**Мемоизация** — запоминание вычисленных результатов: при повторном обращении с тем же аргументом возвращается сохранённое значение вместо нового вычисления.

```python
mem = [-1] * (n + 1)
mem[1] = mem[2] = 1

def fib(n):
    if mem[n] != -1:
        return mem[n]
    mem[n] = fib(n - 1) + fib(n - 2)
    return mem[n]
```

`-1` значит «ещё не вычислено». Ошибки: (1) размер массива меньше $n + 1$ — индекс $n$ недопустим; (2) не заданы базовые значения ($n \le 2$) заранее — рекурсия не остановится (дойдёт до `fib(0)` и ниже).

@@ id=memo-count type=calc src="Мемоизация"
Q: Сколько вызовов и сколько сложений делает мемоизированная `fib(5)`? Сравни с $C_5$ и оцени время для общего $n$.
A:
Порядок: `fib(5)` → `fib(4)` → `fib(3)` → `fib(2)` и `fib(1)` (оба в `mem`) → `mem[3] = 2`; затем `fib(2)` (из `mem`) → `mem[4] = 3`; затем `fib(3)` (из `mem`) → `mem[5] = 5`.

Вызовов $7$ (против $C_5 = 9$ без мемоизации), сложений $3 = n - 2$. В общем случае каждое значение `mem[i]` считается один раз, а каждый вызов либо считает значение, либо возвращает готовое: вызовов порядка $2n$, время $O(n)$ вместо $O(F(n))$ — экспонента сменилась линейной функцией.

@@ id=dp-overlap type=concept src="Подход top-down (сверху вниз)"
Q: Что лежит в основе динамического программирования и чем top-down отличается от «разделяй и властвуй»? Когда мемоизация бесполезна?
A:
Суть ДП — **подзадачи могут пересекаться**: одна и та же подзадача встречается в разных ветках рекурсии, поэтому её результат стоит запомнить. **Top-down** — рекурсия с запоминанием, идём от исходной задачи к подзадачам.

В «разделяй и властвуй» (сортировка слиянием) подзадачи независимы: каждая встречается один раз, запоминать нечего, мемоизация только тратит память. В ДП подзадач мало, но они пересекаются — и именно запоминание превращает экспоненциальное дерево в таблицу из полиномиального числа состояний.

@@ id=dp-recipe type=algo src="Подход top-down (сверху вниз)"
Q: Из каких шагов состоит решение задачи динамическим программированием?
A:
1. **Состояние**: что значит $dp[i]$ (какую подзадачу описывает) — точно, словами.
2. **Переход**: как $dp[i]$ выражается через подзадачи меньшего размера (рекуррентность).
3. **База**: значения, которые заданы напрямую (не требуют перехода).
4. **Порядок вычисления**: рекурсия с запоминанием (top-down) или цикл так, чтобы нужные значения были готовы (bottom-up).
5. **Ответ**: какое $dp$ (или сочетание) является искомым.

На числах Фибоначчи: состояние $F_i$, переход $F_i = F_{i-1} + F_{i-2}$, база $F_1 = F_2 = 1$, ответ $F_n$.

@@ id=bottom-up type=algo src="Подход bottom-up (снизу вверх)"
Q: Что такое подход bottom-up (табуляция) и почему для чисел Фибоначчи массив не нужен? Оцени время и память.
A:
Идём от базовых значений к искомому («от индукции к дедукции»), заполняя значения в порядке, при котором нужные уже готовы.

```python
def fib(n):
    if n <= 2:
        return 1
    prev2, prev1 = 1, 1
    for i in range(3, n + 1):
        cur = prev1 + prev2
        prev2, prev1 = prev1, cur
    return prev1
```

Для нового значения нужны только два предыдущих, поэтому достаточно хранить **три значения** (`prev2`, `prev1`, `cur`) вместо массива. Время $O(n)$, память $O(1)$ (у мемоизации — $O(n)$ под `mem` и $O(n)$ стека рекурсии).

@@ id=td-vs-bu type=compare src="Подход bottom-up (снизу вверх)"
Q: Сравни top-down (мемоизацию) и bottom-up (табуляцию): порядок вычислений, считаемые состояния, стек, память. Когда что выбирать?
A:
| | Top-down | Bottom-up |
|---|---|---|
| Идея | рекурсия + запоминание, от задачи к подзадачам | цикл от базовых значений к ответу |
| Какие состояния считаются | только достижимые из ответа | обычно все по порядку |
| Рекурсия | да: глубина стека (риск переполнения при глубине $\sim n$) | нет |
| Память | таблица + стек | таблица, часто можно хранить только последние значения |
| Запись | близка к определению | нужно придумать порядок обхода |

Top-down удобен, когда порядок обхода неочевиден или нужна малая часть состояний (пример — $f(k) = f(k/2) + f(k/3)$); bottom-up — когда порядок прост и можно сэкономить память (Фибоначчи, Кузнечик).

Q: Сформулируй задачу «Кузнечик», задай состояние $dp[i]$, переход и базу. Почему именно сумма?
A:
Клетки $0, 1, 2, \dots$; кузнечик стоит в клетке $0$ и прыгает на $1$ или $2$ клетки (в обобщении — на $1\ldots k$). Нужно найти **число способов** добраться до клетки $i$.

$dp[i]$ — число способов дойти до клетки $i$. Последний прыжок был из клетки $i - j$ ($j = 1\ldots k$, $i - j \ge 0$). Способы, различающиеся последним прыжком, не пересекаются и покрывают все, поэтому
$$dp[i] = \sum_{j=1}^{k} dp[i - j], \qquad dp[0] = 1.$$
$dp[0] = 1$ — в клетке $0$ кузнечик уже стоит (один «пустой» способ).

```python
dp[0] = 1
for i in range(1, n + 1):
    for j in range(1, k + 1):
        if i - j >= 0:
            dp[i] += dp[i - j]
```

Q: Заполни $dp[0..5]$ для $k = 2$ и для $k = 3$.
A:
**$k = 2$:** $dp[0] = 1$; $dp[1] = dp[0] = 1$ (прыжок на 2 невозможен); $dp[2] = dp[1] + dp[0] = 2$; $dp[3] = 3$; $dp[4] = 5$; $dp[5] = 8$.

```array
title: Кузнечик: число способов дойти до клетки (k = 2)
[1, 0, 0, 0, 0, 0]
pointers: i, j
print: last
code:
let k = 2;
for (let i = 1; i < a.length; i++) {
  for (let j = 1; j <= k; j++) {
    if (i - j >= 0) a[i] += a[i - j];
  }
  done(i);
}
```

**$k = 3$:** $dp[1] = 1$; $dp[2] = dp[1] + dp[0] = 2$; $dp[3] = dp[2] + dp[1] + dp[0] = 4$; $dp[4] = 4 + 2 + 1 = 7$; $dp[5] = 7 + 4 + 2 = 13$.

Q: Почему при $k = 2$ в Кузнечике получаются числа Фибоначчи и какой именно сдвиг индекса?
A:
При $k = 2$ рекуррентность $dp[i] = dp[i-1] + dp[i-2]$ совпадает с рекуррентностью Фибоначчи. Начало: $dp[0] = dp[1] = 1$, поэтому $dp[i] = F_{i+1}$ (при $F_1 = F_2 = 1$): $1, 1, 2, 3, 5, 8, \dots$ Последний прыжок на 1 или на 2 разбивает пути на две непересекающиеся группы — так же, как $F_n$ разлагается на $F_{n-1}$ и $F_{n-2}$.

@@ id=hopper-pitfalls type=pitfall src="Задача «Кузнечик» (Climbing stairs)"
Q: Какие ошибки типичны в реализации Кузнечика: база, границы, размер массива?
A:
- Забыли `dp[0] = 1` (или поставили `0`): все значения станут нулями — суммировать нечего.
- Нет проверки `i - j >= 0`: индекс уходит в отрицательные (в Python — тихо читает конец массива, в C++ — выход за границу).
- Массив размера $n$ вместо $n + 1$: клетка $n$ без ячейки.
- Заполнение не слева направо: при `dp[i]` значения `dp[i-j]` должны быть уже готовы.

@@ id=hopper-window type=calc src="Задача «Кузнечик» (Climbing stairs)"
Q: Как ускорить Кузнечика при больших $k$ с помощью скользящего окна? Оцени время до и после и покажи шаг на $k = 3$.
A:
Внутренний цикл считает сумму $k$ последних значений: $W_i = dp[i-1] + \dots + dp[i-k]$ (недостающие слагаемые считаем нулями), время $O(nk)$. Окно можно сдвигать: прибавлять новое значение и вычитать выпавшее:
$$W_{i+1} = W_i + dp[i] - dp[i-k], \qquad dp[i] = W_i.$$
Каждый шаг $O(1)$, всего $O(n)$ (то же получается через префиксные суммы $S$: $W_i = S[i-1] - S[i-k-1]$).

Для $k = 3$: $dp[0..4] = 1, 1, 2, 4, 7$. Окно для $dp[4]$: $W_4 = dp[1] + dp[2] + dp[3] = 1 + 2 + 4 = 7$. Сдвиг к $dp[5]$: $W_5 = W_4 + dp[4] - dp[1] = 7 + 7 - 1 = 13 = dp[5]$ (прямой подсчёт: $2 + 4 + 7 = 13$).

@@ id=directions type=concept src="Направления разбиения"
Q: Какие бывают направления обхода подзадач в динамическом программировании? Покажи «слева направо» и «справа налево» на Кузнечике.
A:
Кроме разбиения **сверху вниз** (top-down) и **снизу вверх** (bottom-up) существует порядок **слева направо** и **справа налево** — по какому краю данных идёт заполнение.

Пример для Кузнечика (иллюстрация): *слева направо* — $dp[i]$ = способов дойти до клетки $i$ от начала, $dp[0] = 1$, ответ $dp[n]$. *Справа налево* — $g[i]$ = способов дойти от клетки $i$ до конца $n$: $g[n] = 1$, $g[i] = g[i+1] + g[i+2]$, ответ $g[0]$. Оба порядка дают один и тот же ответ ($dp[n] = g[0]$), но заполняются от разных концов; выбирают тот, при котором переход записывается проще.

@@ id=fk-topdown type=algo src="Пример: $f(k) = f(k/2) + f(k/3)$"
Q: Почему рекуррентность $f(k) = f(k/2) + f(k/3)$ удобно решать top-down и как выглядит решение? Что за пересечение подзадач в её дереве?
A:
```tree
tree
f(k)
  f(k/2)
    f(k/4)
    f(k/6)
  f(k/3)
    f(k/6)
    f(k/9)
```

Значение $f(k/6)$ встречается в двух ветках — подзадачи пересекаются, значит, нужна мемоизация:

```python
def f(k):
    if k in mem:
        return mem[k]
    mem[k] = f(k // 2) + f(k // 3)
    return mem[k]
```

Деление целочисленное, словарь `mem` заранее содержит базовые значения. Задача не решается bottom-up «подряд»: аргументы — не последовательные числа, а значения вида $\lfloor k/(2^a3^b)\rfloor$, а top-down вычисляет только реально достижимые.

@@ id=fk-calc type=calc src="Пример: $f(k) = f(k/2) + f(k/3)$"
Q: Пусть $f(0) = 1$, а для $k \ge 1$ действует $f(k) = f(\lfloor k/2 \rfloor) + f(\lfloor k/3 \rfloor)$. Вычисли $f(12)$ и сравни число вызовов с мемоизацией и без неё.
A:
Нужные аргументы: $12 \to 6, 4$; $6 \to 3, 2$; $4 \to 2, 1$; $3 \to 1, 1$; $2 \to 1, 0$; $1 \to 0, 0$. Снизу: $f(0) = 1$; $f(1) = f(0) + f(0) = 2$; $f(2) = f(1) + f(0) = 3$; $f(3) = f(1) + f(1) = 4$; $f(4) = f(2) + f(1) = 5$; $f(6) = f(3) + f(2) = 7$; $f(12) = f(6) + f(4) = 12$.

Различных аргументов всего $7$ ($12, 6, 4, 3, 2, 1, 0$) — каждый считается один раз. Без мемоизации число вызовов $T$: $T(0) = 1$, $T(1) = 3$, $T(2) = 5$, $T(3) = 7$, $T(4) = 9$, $T(6) = 13$, $T(12) = 1 + 13 + 9 = 23$ — больше втрое, и разрыв растёт с $k$. Различных состояний $O(\log^2 k)$ (пары $(a, b)$ с $2^a3^b \le k$).
