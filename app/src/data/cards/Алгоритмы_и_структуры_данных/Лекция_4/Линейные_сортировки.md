@@ id=cs-idea type=algo src="Сортировка подсчётом (Counting sort) :: Идея алгоритма"
Q: В чём идея сортировки подсчётом, что такое массив-алфавит $C$ и почему алгоритм не использует сравнения элементов?
A:
Сортировка подсчётом упорядочивает массив $A$ **целых чисел из известного диапазона** (алфавита), подсчитывая, сколько раз встречается каждое значение. Для этого заводится вспомогательный массив-алфавит $C$: его индексы — возможные значения элементов $A$, а $C[i]$ — сколько раз число $i$ встречается в $A$.

Сравнений элементов нет: значение элемента сразу используется как **индекс** в $C$. Алгоритм «знает» порядок значений заранее — по их числовому порядку в индексах.

@@ id=cs-vs-lower-bound type=concept src="Сортировка подсчётом (Counting sort) :: Идея алгоритма"
Q: Почему сортировка подсчётом может работать быстрее $\Omega(n\log n)$, если сортировки сравнением быстрее не умеют?
A:
Нижняя граница $\Omega(n\log n)$ доказывается для алгоритмов, которые получают информацию об элементах **только сравнениями** (дерево решений с $n!$ листьями). Подсчёт сравнений не делает: он использует структуру ключа — что это целое число из небольшого диапазона, — и обращается к ячейке $C[a_j]$ прямо по значению. Расплата — ограничения: нужны целые ключи из известного ограниченного диапазона и память под массив размера алфавита.

@@ id=cs-v1 type=algo src="Первая версия алгоритма: простой подсчёт"
Q: Как работает первая (простая) версия сортировки подсчётом? Выполни её для $A = [4, 2, 2, 8, 3, 3, 1]$ (значения от $1$ до $8$).
A:
1. Обнуляем $C$ (размер алфавита), проходим по $A$ и для каждого $a_j$ делаем $C[a_j]{+}{+}$.
2. Проходим по $C$ по возрастанию индекса $i$ и записываем в $A$ значение $i$ ровно $C[i]$ раз подряд.

Для примера: после первого прохода $C = [1, 2, 2, 0, 1, 0, 0, 1]$ (индексы $1..8$: одна единица, две двойки, две тройки, одна четвёрка, одна восьмёрка). Выписываем: $1, 2, 2, 3, 3, 4, 8$ — отсортировано.

@@ id=cs-v1-problem type=pitfall src="Проблема первой версии: массив становится неустойчивым"
Q: Какой недостаток у первой версии сортировки подсчётом при сортировке записей по ключу и почему ей нельзя говорить об устойчивости?
A:
Первая версия по сути сортирует **числа**, а не объекты. Выписывая значения из $C$ в $A$, мы восстанавливаем лишь сами ключи: объекты (записи), которые за ними стояли, нигде не запоминаются и теряются. Поэтому для записей она неприменима вовсе — они не сохраняют даже связь с другими полями.

Строго говоря, для голых чисел вопрос об устойчивости не стоит (равные числа неразличимы); в конспекте формулировка «вообще не является устойчивой» означает, что сохранить порядок записей с равными ключами здесь невозможно. Чтобы работать с объектами и получить устойчивость, нужна вторая версия — с префиксными суммами.

@@ id=prefix-sum type=term src="Вторая версия: массив префиксных сумм"
Q: Что такое массив префиксных сумм $P$ для $C$ и что значит $P[i]$ для позиции в отсортированном массиве?
A:
$$P[i] = C[0] + C[1] + \dots + C[i]$$
— количество элементов $A$, значения которых **не превышают** $i$. Следовательно, элементы со значением $i$ в отсортированном массиве занимают позиции (с $1$) от $P[i-1] + 1$ до $P[i]$, и $P[i]$ — это позиция, на которую встанет **последний** по порядку элемент со значением $i$ (с нуля — $P[i] - 1$).

@@ id=cs-v2 type=algo src="Вторая версия: массив префиксных сумм"
Q: Изложи по шагам вторую версию сортировки подсчётом (с префиксными суммами) и объясни, как расставляются объекты.
A:
1. Строим $C$: $C[i]$ — число элементов, равных $i$.
2. Строим префиксные суммы $P[i] = \sum_{k \le i} C[k]$.
3. Заводим результирующий массив той же длины, что $A$.
4. Идём по $A$ **справа налево**. Для $a_j = i$: кладём объект $a_j$ целиком на позицию $P[i] - 1$ (индексация с нуля) и уменьшаем $P[i]$ на $1$ — позиция освобождается для следующего (более раннего) элемента с тем же ключом.

Так каждый объект попадает на своё окончательное место за одно действие.

@@ id=cs-v2-trace type=trace src="Вторая версия: массив префиксных сумм"
Q: Выполни вторую версию для записей с ключами из $\{1, 2, 3\}$: $A = [(3,a), (1,b), (3,c), (2,d), (1,e)]$. Покажи $C$, $P$, ход расстановки и результат.
A:
$C[1] = 2$, $C[2] = 1$, $C[3] = 2$. Префиксные суммы $P[1] = 2$, $P[2] = 3$, $P[3] = 5$.

Идём справа налево (позиции с нуля):

| Элемент | $P[\text{ключ}]$ до | Позиция $P-1$ | $P[\text{ключ}]$ после |
|---|---|---|---|
| $(1,e)$ | 2 | 1 | 1 |
| $(2,d)$ | 3 | 2 | 2 |
| $(3,c)$ | 5 | 4 | 4 |
| $(1,b)$ | 1 | 0 | 0 |
| $(3,a)$ | 4 | 3 | 3 |

Результат: $[(1,b), (1,e), (2,d), (3,a), (3,c)]$. Порядок равных ключей сохранён ($b$ перед $e$, $a$ перед $c$) — сортировка устойчива.

```array
title: Сортировка подсчётом (вторая версия) для чисел
[4, 2, 2, 8, 3, 3, 1]
pointers: i
print: last
code:
let mx = a[0];
for (let i = 1; i < a.length; i++) {
  if (a[i] > mx) mx = a[i];
}
let c = [];
for (let v = 0; v <= mx; v++) { c.push(0); }
for (let i = 0; i < a.length; i++) { c[a[i]] = c[a[i]] + 1; }
for (let v = 1; v <= mx; v++) { c[v] = c[v] + c[v - 1]; }
let res = [];
for (let i = 0; i < a.length; i++) { res.push(0); }
for (let i = a.length - 1; i >= 0; i--) {
  c[a[i]] = c[a[i]] - 1;
  res[c[a[i]]] = a[i];
}
for (let i = 0; i < a.length; i++) { a[i] = res[i]; }
done(0, a.length - 1);
```

@@ id=right-to-left type=concept src="Почему идём справа налево: свойство устойчивости"
Q: Почему обход исходного массива в сортировке подсчётом идёт справа налево и как это обеспечивает устойчивость?
A:
$P[i]$ указывает на позицию **последнего** элемента с ключом $i$. Идя справа налево, мы встречаем первым тот элемент ключа $i$, который в $A$ стоял позже всех, — и ставим его на последнюю отведённую позицию $P[i] - 1$, затем уменьшаем $P[i]$. Следующие, более ранние элементы с тем же ключом ложатся на позиции **левее**. Итог: кто раньше стоял в $A$, тот раньше и в результате — относительный порядок равных ключей сохранён.

@@ id=left-to-right-bug type=pitfall src="Почему идём справа налево: свойство устойчивости"
Q: Что произойдёт на примере $[(3,a), (1,b), (3,c), (2,d), (1,e)]$, если идти по массиву слева направо при тех же $P$?
A:
Префиксные суммы те же: $P[1] = 2$, $P[2] = 3$, $P[3] = 5$.

- $(3,a)$: позиция $P[3]-1 = 4$, $P[3] = 4$;
- $(1,b)$: позиция $1$, $P[1] = 1$;
- $(3,c)$: позиция $3$, $P[3] = 3$;
- $(2,d)$: позиция $2$;
- $(1,e)$: позиция $0$.

Результат: $[(1,e), (1,b), (2,d), (3,c), (3,a)]$. Сортировка по ключу верна, но равные ключи **развернулись** ($e$ перед $b$, $c$ перед $a$): первый встреченный элемент занимает последнюю позицию, а не первую. Устойчивость потеряна.

@@ id=cs-time type=proof src="Доказательство временной сложности"
Q: Докажи, что сортировка подсчётом работает за $O(n + k)$, и оцени память. Что в этой оценке означают $n$ и $k$?
A:
$n$ — число элементов $A$, $k$ — размер алфавита (диапазон значений).

1. Поиск минимума и максимума — проход по $A$: $O(n)$.
2. Подсчёт вхождений в $C$ — проход по $A$: $O(n)$.
3. Префиксные суммы — проход по $C$: $O(k)$.
4. Расстановка справа налево — проход по $A$: $O(n)$.

Сумма: $O(n) + O(n) + O(k) + O(n) = O(n + k)$. Память: $C$ ($k$), результат ($n$) — $O(n + k)$. Алгоритм эффективен, когда $k$ сравним с $n$; при $k \gg n$ (например, произвольные 32-битные числа) невыгоден — отсюда потребность в поразрядной сортировке.

@@ id=cs-when type=compare src="Доказательство временной сложности"
Q: Когда сортировка подсчётом выгоднее сортировки сравнением, а когда проигрывает? Сравни на $n = 1000$ при диапазоне значений $10^3$ и $10^9$.
A:
Подсчёт: $O(n + k)$, сравнение (слиянием/быстрая): $O(n\log n)$.

- $n = 1000$, $k = 10^3$: подсчёт $\approx n + k = 2000$ шагов, сравнением $\approx n\log_2 n \approx 10^4$ — подсчёт выигрывает.
- $n = 1000$, $k = 10^9$: подсчёт $\approx 10^9$ шагов и массив $C$ в миллиард ячеек, сравнением всё те же $\approx 10^4$ — подсчёт проигрывает на пять порядков и ещё требует гигабайты памяти.

Итог: подсчёт хорош при $k = O(n)$ (или $k \lesssim n\log n$); при большом диапазоне берут сортировки сравнением или поразрядную.

@@ id=alphabet-def type=algo src="Определение алфавита сортировки"
Q: Как определить размер алфавита $k$ и как работать с отрицательными числами? Приведи пример для $A = [-3, 5, 0, 5, -1]$.
A:
Один проход по $A$ находит $\min$ и $\max$ за $O(n)$. Размер алфавита
$$k = \max - \min + 1.$$
Индексы $C$ сдвигают на $-\min$: значение $x$ хранится в $C[x - \min]$, так что $\min$ соответствует индексу $0$, а $\max$ — индексу $k - 1$. Это позволяет работать и с отрицательными числами.

Пример: $\min = -3$, $\max = 5$, $k = 5 - (-3) + 1 = 9$. Индексы: $-3 \to 0$, $-1 \to 2$, $0 \to 3$, $5 \to 8$. Массив подсчёта $C = [1, 0, 1, 1, 0, 0, 0, 0, 2]$, результат: $[-3, -1, 0, 5, 5]$.

@@ id=alphabet-pitfall type=pitfall src="Определение алфавита сортировки"
Q: Почему размер алфавита нельзя брать равным $\max$ и что станет с алгоритмом, если $n$ мало, а разброс значений огромен?
A:
Если $\min \ne 0$, то $\max$ ячеек либо не хватит (отрицательные значения даже не получат индекс), либо часть будет бесполезна (для $A = [1000, 1001]$ нужны две ячейки, а не $1001$). Верная формула $k = \max - \min + 1$ учитывает сдвиг.

Размер $k$ зависит от **разброса значений**, а не от $n$: для $A = [0, 10^9]$ при двух элементах нужно $10^9 + 1$ ячейка. Время и память $O(n + k)$ становятся огромными (к тому же разность $\max - \min$ может переполнить `int`), поэтому перед применением подсчёта оценивают $k$.

@@ id=cs-code type=code src="Пример кода (C++)"
Q: Разбери четвёртый шаг кода: почему `c[key]--` стоит *до* записи в `result`, как массив `c` меняет смысл и что будет при обходе слева направо?
A:
```cpp
for (int i = n - 1; i >= 0; i--) {
    int key = a[i] - mn;
    c[key]--;
    result[c[key]] = a[i];
}
```

После цикла префиксных сумм `c[key]` равен числу элементов с ключом $\le$ `key`, то есть позиции (с единицы) последнего такого элемента. Позиция с нуля — `c[key] - 1`; поэтому сначала уменьшаем `c[key]`, а затем пишем в `result[c[key]]` — это то же, что «положить на $P[i]-1$ и уменьшить $P$». Дальше `c[key]` указывает на следующую свободную позицию слева для того же ключа.

Один массив `c` сначала хранит **количества вхождений**, после префиксных сумм — «указатели» на позиции; отдельный массив $P$ не нужен, это экономит память. При обходе слева направо ключи всё равно отсортируются, но равные поменяются местами (потеря устойчивости).

@@ id=cs-code-shift type=code src="Пример кода (C++)"
Q: Что произойдёт в коде `countingSort`, если для массива с отрицательными числами писать `c[x]++` вместо `c[x - mn]++`? А если массив пуст?
A:
Отрицательный `x` даёт отрицательный индекс: выход за границы вектора (неопределённое поведение), а для положительных — индекс может выйти за размер `k = mx - mn + 1`, если `mn < 0`. Сдвиг `x - mn` переводит диапазон $[\min, \max]$ в $[0, k-1]$.

Пустой массив: `a[0]` недоступно, поэтому в начале стоит проверка `if (n == 0) return a;` — без неё чтение `a[0]` для инициализации `mn`, `mx` было бы ошибкой.

@@ id=radix-idea type=term src="Поразрядная (цифровая) сортировка :: Идея алгоритма"
Q: Зачем нужна поразрядная сортировка, если есть сортировка подсчётом, и чем MSD отличается от LSD?
A:
Подсчёт неэффективен, когда алфавит $k$ велик (диапазон значений огромен — массив $C$ слишком большой). Поразрядная сортировка сортирует числа **не целиком, а по разрядам (цифрам)** последовательно, применяя на каждом шаге **устойчивую** сортировку (обычно подсчётом) с маленьким алфавитом одной цифры.

- **LSD** (Least Significant Digit) — разряды от младшего к старшему;
- **MSD** (Most Significant Digit) — от старшего к младшему.

@@ id=lsd-algo type=algo src="Radix sort (LSD)"
Q: Изложи алгоритм LSD radix sort по шагам.
A:
```diagram
title: Схема алгоритма LSD Radix Sort
A: round "Вход: массив чисел"
B: box "Найти макс. число разрядов d"
C: box "Разряд = 1 (младший)"
D: box "Устойчивая сортировка подсчётом по текущему разряду"
E: diamond "Разряд < d?"
F: box "Перейти к следующему разряду"
G: round "Выход: отсортированный массив"
A -> B
B -> C
C -> D
D -> E
E -> F : Да
F -> D
E -> G : Нет
```

1. Находим $d$ — число разрядов у числа с наибольшим количеством цифр.
2. Для разрядов от младшего ($1$-го) до старшего ($d$-го): устойчиво сортируем весь массив подсчётом, используя ключом только текущую цифру.
3. После $d$ проходов массив отсортирован.

@@ id=lsd-trace type=trace src="Radix sort (LSD)"
Q: Выполни LSD radix sort для $[170, 45, 75, 90, 802, 24, 2, 66]$ ($d = 3$): массив после каждого разряда.
A:
- **Единицы.** Ключи: $0, 5, 5, 0, 2, 4, 2, 6$. Устойчиво: $[170, 90, 802, 2, 24, 45, 75, 66]$.
- **Десятки.** Ключи: $170{\to}7,\ 90{\to}9,\ 802{\to}0,\ 2{\to}0,\ 24{\to}2,\ 45{\to}4,\ 75{\to}7,\ 66{\to}6$. Устойчиво: $[802, 2, 24, 45, 66, 170, 75, 90]$ — равные ключи ($802$ и $2$ с цифрой $0$; $170$ и $75$ с цифрой $7$) остались в порядке предыдущего шага.
- **Сотни.** Ключи: $8, 0, 0, 0, 0, 1, 0, 0$. Устойчиво: $[2, 24, 45, 66, 75, 90, 170, 802]$.

Короткие числа дополняются нулями слева ($2$ — это $002$), поэтому цифра сотен у $2$ равна $0$.

@@ id=lsd-correct type=proof src="Radix sort (LSD)"
Q: Докажи корректность LSD radix sort и укажи, где используется устойчивость.
A:
Индукция по числу обработанных разрядов $j$: после $j$ проходов массив упорядочен по числу, составленному из $j$ младших цифр.

- *База* $j = 1$: один проход сортирует по последней цифре.
- *Шаг*: пусть массив упорядочен по $j$ младшим цифрам. Устойчиво сортируем по цифре $j + 1$. Числа с **разными** цифрами $j + 1$ расставлены верно по этой цифре (она важнее младших). Числа с **равной** цифрой $j+1$ в силу **устойчивости** остаются в прежнем взаимном порядке, а он уже упорядочен по $j$ младшим цифрам.

После $d$ проходов упорядочено по всем цифрам, то есть по числу.

@@ id=lsd-unstable type=pitfall src="Radix sort (LSD)"
Q: Покажи на небольшом примере, что при неустойчивой сортировке на шаге по разряду LSD radix sort даст неверный результат.
A:
Возьмём $[13, 12]$ и сначала отсортируем по единицам: $[12, 13]$ (ключи $2 < 3$). Теперь шаг по десяткам: у обоих цифра десятков равна $1$, ключи равны. Устойчивая сортировка оставит $[12, 13]$ — верно. Неустойчивая вправе поменять равные местами и выдать $[13, 12]$ — неверно: порядок по младшим разрядам, установленный на предыдущем шаге, разрушен.

Поэтому на каждом шаге обязательно использовать устойчивую сортировку (например, подсчётом по второй версии).

@@ id=radix-pitfalls type=pitfall src="Radix sort (LSD)"
Q: Как обрабатывать числа разной длины и отрицательные числа в LSD radix sort?
A:
Число разрядов $d$ определяют по максимальному числу — у более коротких недостающие старшие цифры считаются нулями (дополнение нулями слева). Для отрицательных чисел можно сдвинуть все значения на $-\min$, чтобы все стали неотрицательными (как в определении алфавита для подсчёта), отсортировать и вернуть обратно; другой способ — отдельно обработать знак. Без этого цифры отрицательных чисел сравниваются неверно.

Q: Сравни LSD и MSD сортировку по порядку разрядов, роли устойчивости и реализации. Почему LSD проще?
A:
| Признак | LSD | MSD |
|---|---|---|
| Порядок разрядов | младший → старший | старший → младший |
| Устойчивость | обязательна на каждом шаге — на ней держится корректность | не нужна для упорядочения по ключу: после разбиения по старшему разряду группы («корзины») сортируются по следующему разряду отдельно |
| Реализация | итеративная: простой цикл по разрядам | рекурсивная: внутри каждой корзины запускается сортировка по следующему разряду |

LSD проще: один цикл и по одному проходу по **всему** массиву на разряд, тогда как MSD разбивается на множество мелких рекурсивных подзадач.

@@ id=radix-time type=calc src="Временная сложность Radix Sort"
Q: Выведи сложность radix sort $O(d(n+k))$ и оцени, сколько проходов и какая сложность для 32-битных чисел в системе счисления с основанием $256$.
A:
Один проход — устойчивая сортировка подсчётом одной цифры с алфавитом $k$: $O(n + k)$. Проходов $d$ (по числу разрядов), поэтому
$$T = d\cdot O(n + k) = O\big(d(n + k)\big).$$
При константных $d$ и $k$ время линейно: $O(n)$.

Для 32-битных чисел с цифрой в 8 бит (основание $256$): $k = 256$, $d = 32/8 = 4$ прохода, $T = O(4(n + 256)) = O(n)$ и память $O(n + 256)$. Применять подсчёт напрямую пришлось бы с $k = 2^{32} \approx 4{,}3\cdot10^9$. Выбирая основание порядка $n$, для чисел до $n^c$ получают $d = c$ проходов и $O(c\cdot n)$.

@@ id=radix-compare type=compare src="Временная сложность Radix Sort"
Q: Сравни подсчёт, поразрядную сортировку и сортировки сравнением (слиянием) по времени, ограничениям и памяти. Что выбрать для миллиона 32-битных чисел?
A:
| | Подсчёт | Radix (LSD) | Сравнением (слиянием) |
|---|---|---|---|
| Время | $O(n + k)$ | $O(d(n + k))$ | $O(n\log n)$ |
| Ограничение | целые ключи, малый диапазон $k$ | целые (или строки одинаковой длины), конечное число разрядов | любые сравнимые элементы |
| Память | $O(n + k)$ | $O(n + k)$ | $O(n)$ |
| Устойчивость | да (вторая версия) | да (если проходы устойчивы) | да |

Для $10^6$ 32-битных чисел подсчёт с $k = 2^{32}$ невозможен; radix по 4 байта даёт $\approx 4\cdot(10^6 + 256)$ шагов против $\approx 2\cdot10^7$ у сортировки сравнением — линейный алгоритм выигрывает, но требует целых ключей и дополнительную память.
