# Методологии разработки

## Waterfall

### История

В 1970 году Ройс в своей статье описал в виде концепции то, что сейчас принято называть **«каскадной моделью»** (*Waterfall*, «водопад»). При этом он не только представил саму модель, но и обсуждал её недостатки.

:::meaning
**Каскадная модель (Waterfall)** — последовательная модель разработки, в которой работа разбита на этапы, идущие один за другим: результат каждого этапа передаётся на следующий, как вода по ступеням каскада. Именно поэтому на схеме этапы нарисованы «лестницей» со стрелками вниз.
:::

### Этапы каскадной модели

1. **Определение требований** — выясняется, что именно должен делать создаваемый продукт.
2. **Проектирование** — продумывается, как продукт будет устроен.
3. **Конструирование** (также «реализация» либо «кодирование») — написание кода.
4. **Воплощение** — превращение спроектированного решения в работающий продукт.
5. **Тестирование и отладка** (также «верификация») — проверка продукта и исправление найденных ошибок.
6. **Инсталляция** — установка продукта.
7. **Поддержка** — сопровождение продукта после запуска.

```diagram
title: Каскадная модель (Waterfall)
R: box "Требования" @ 70, 40
D: box "Проектирование" @ 195, 100
I: box "Реализация" @ 320, 160
V: box "Верификация" @ 445, 220
M: box "Поддержка" @ 570, 280
R -> D
D -> I
I -> V
V -> M
```

:::note
Схема показывает укрупнённые блоки на английском: *Requirements* (определение требований), *Design* (проектирование), *Implementation* (реализация), *Verification* (верификация — то же, что тестирование и отладка), *Maintenance* (поддержка). Для одного и того же этапа в литературе встречается несколько названий: «конструирование», «реализация» и «кодирование» — синонимы.
:::

:::warning
Обратите внимание на синонимы: «верификация» — это не отдельный этап, а другое название этапа тестирования и отладки. Не путайте их с проектированием: на этапе проектирования продукта ещё нет, проверять нечего.
:::

:::note
**Мем про сову.** На двух рисунках показана одна и та же шутка — инструкция «Как нарисовать сову». Шаг 1: нарисовать два овала (маленький сверху, большой снизу). Шаг 2: на первом рисунке — готовая детальная сова, сидящая на ветке; на втором (подпись «Рисуем остаток совы») — неуклюже нарисованная сова с крыльями и лапами, сопровождаемая возмущённым восклицанием. Смысл шутки: между простым первым шагом и итогом пропущена вся основная работа.
:::

## SCRUM

### История SCRUM

Scrum формировался постепенно: его вобрали в себя статьи и книги, выходившие на протяжении почти четверти века.

| Год | Источник |

| 1998 | Книга «Pattern Languages of Program Design» |

### Базовые принципы SCRUM

1. **Работа короткими циклами (спринтами).** Проект делится на части, и каждая часть реализуется поэтапно — в своём спринте. Спринт — короткий цикл фиксированной длительности, по итогам которого готова определённая часть продукта.
2. **Гибкость.** После окончания каждого спринта проводится тестирование. Если найдены ошибки, меняется стратегия реализации или пересматривается список текущих задач (бэклог) по продукту.
3. **Пользователи и заказчик участвуют в разработке.** В любой скрам-команде есть «владелец продукта» — заказчик или его представитель. Через него команда взаимодействует с пользователями, которые тестируют проект по окончании каждого спринта. Владелец продукта собирает обратную связь (фидбэк), передаёт её команде, и на основе этих данных принимаются решения о дальнейшем развитии продукта.
4. **Взаимодействие команды.** Scrum-команда — это несколько человек, которые общаются друг с другом и стремятся к достижению общей цели.

:::meaning
**Бэклог (backlog)** — список текущих задач по продукту. После каждого спринта он может быть пересмотрен.
:::

:::meaning
**Спринт** — короткий цикл работы, в котором реализуется одна часть продукта. Вся работа над проектом складывается из последовательности спринтов.
:::

```diagram
title: Цикл одного спринта
caption: Что происходит после каждого спринта
A: round "Бэклог продукта"
B: box "Спринт: реализация части продукта"
C: box "Тестирование пользователями"
D: diamond "Есть ошибки?"
E: box "Смена стратегии или пересмотр бэклога"
F: round "Следующая часть продукта"
A -> B
B -> C
C -> D
D -> E : Да
E -> B
D -> F : Нет
```

```diagram
title: Как идёт обратная связь
U: round "Пользователи"
P: box "Владелец продукта"
T: box "Scrum-команда"
U -> P : Фидбэк по итогам спринта
P -> T : Передаёт фидбэк
T -> P : Решения о развитии продукта
```

:::warning
Спринт не длится «до тех пор, пока работа не будет закончена»: это именно короткий цикл. Если часть продукта не получилась идеальной, исправления и изменение стратегии происходят уже по итогам спринта — через пересмотр бэклога.
:::

### Основные роли

1. **Владелец продукта (Product Owner)** — заказчик или его представитель; связующее звено между пользователями и командой.
2. **Скрам-мастер (Scrum Master).**
3. **Разработчики (Delivery Team)** — участники, непосредственно создающие продукт.

:::note
На фотографии: большая группа людей сидит по кругу на скамьях вокруг костра в круглом помещении с деревянными стенами. Иллюстрация к идее командной работы: все участники находятся рядом и видят друг друга.
:::

### Принципы работы Scrum-команды

- **Постоянное самосовершенствование.** Опытные разработчики говорят, что довести продукт до идеального состояния невозможно без самосовершенствования каждого члена команды.
- **Автономность.** Каждый сотрудник отвечает не только за общий результат и умеет работать в коллективе, но и многие обязанности выполняет самостоятельно.
- **Кросс-функциональность.** Команда самодостаточна: в неё входят специалисты с разными навыками.

:::remember
Три принципа работы Scrum-команды: **самосовершенствование**, **автономность**, **кросс-функциональность**.
:::

:::note
**Рисунки с совой по шагам.** Два набора иллюстраций показывают, как сова рисуется постепенно. Слева — детская сова на ветке: сначала дуга, затем контур туловища, уши и клюв, глаза, крылья, перья на груди и лапы, в конце — ветка и раскраска (на заключительном кадре — яркая сова на тёмном фоне со звёздами). Справа — другая сова: овальная голова и овальное тело, затем уши, клюв, глаза, брови, оперение; на последних кадрах появляются детали перьев и пушистых ушей. Идея: сложный результат складывается из небольших последовательных шагов.
:::

:::note
На рисунке: два белых мультяшных мышонка. Один держит большую зелёную зажигалку и тянется к верёвке, другой стоит с огромной красной ракетой, пристёгнутой ремнём к спине, и широко разводит руки.
:::

## Incremental Model

Инкрементная модель строится на повторяющихся циклах: каждый цикл заканчивается новой версией продукта.

:::meaning
**Инкрементная модель (Incremental Model)** — модель, в которой продукт создаётся и выпускается версиями. Центр схемы — «Версия N»: именно её создаёт один проход цикла.
:::

Работа начинается с **начального планирования**, после чего запускается цикл, состоящий из следующих шагов:

1. **Планирование.**
2. **Требования.**
3. **Проектирование.**
4. **Исполнение.**
5. **Развёртывание** — выпуск версии наружу (стрелка уходит за пределы цикла).
6. **Тестирование.**
7. **Оценка** — после неё цикл начинается заново с планирования.

```diagram
title: Цикл инкрементной модели
S: round "Начальное планирование"
P: box "Планирование"
R: box "Требования"
D: box "Проектирование"
I: box "Исполнение"
Y: round "Развёртывание"
T: box "Тестирование"
O: box "Оценка"
V: note "Версия N"
S -> P
P -> R
R -> D
D -> I
I -> Y
I -> T
T -> O
O -> P : Следующий цикл
I -> V
```

:::note
Развёртывание на схеме изображено стрелкой, уходящей из цикла вправо: версия выпускается, а работа продолжается новым циклом, начинающимся с планирования после оценки.
:::

:::note
**Рисунок слона по шагам.** Четыре кадра: сначала прямоугольник с закруглёнными углами; затем к нему добавляются овал головы и две ноги; потом — ухо, хобот, бивень, хвост и ступни; в конце слон закрашивается серым. Как и в схеме выше, результат появляется постепенно, версия за версией.
:::

## Повышение эффективности

### Бережливое производство

:::meaning
**Бережливое производство (Lean)** — концепция управления производственным предприятием, основанная на постоянном стремлении к устранению всех видов потерь.
:::

Из этого определения следуют два дополнительных принципа:

- в оптимизацию бизнеса вовлекается **каждый сотрудник**;
- максимальная **ориентация на потребителя**.

### Kanban

Kanban — это доска, на которой путь задачи от идеи до выпуска разбит на колонки-этапы: **Ещё**, **Анализ**, **Разработка**, **Приёмка**, **Выпуск**. Задачи — карточки, которые перемещаются слева направо. Колонки «Анализ», «Разработка» и «Приёмка» разделены на две части: **«Делаем»** (задача в работе) и **«Готово»** (этап завершён, задача ждёт перехода дальше).

```diagram
title: Движение задачи по доске Kanban
A: round "Ещё" @ 70, 120
B: box "Анализ" @ 190, 120
C: box "Разработка" @ 320, 120
D: box "Приёмка" @ 450, 120
E: round "Выпуск" @ 570, 120
A -> B
B -> C
C -> D
D -> E
```

:::note
Под названиями колонок красным написаны числа: «Ещё» — 2, «Анализ» — 3, «Разработка» — 3, «Приёмка» — 2. Это ограничение на количество задач, одновременно находящихся в колонке: нельзя брать в работу больше, чем указано. В колонке «Выпуск» цифры нет, туда складываются уже завершённые карточки. На доске также нарисованы фигурки людей, работающих над задачами, цветные стикеры и звёздочка, выделяющая одну из карточек.
:::

Для каждой колонки заданы **критерии готовности** — условия, при выполнении которых задачу можно передать дальше:

| Колонка | Критерии готовности |
|---|---|
| Анализ | Цель ясна; есть первая задача; истории разбиты (если это необходимо) |
| Разработка | Чистый код добавлен в рабочую ветку; завершено интеграционное и регрессионное тестирование; всё работает в тестовой среде |
| Приёмка | Заказчик утвердил; готово к работе в реальной системе |

:::remember
Карточка переходит в следующую колонку только тогда, когда выполнены **критерии готовности** текущей колонки.
:::

:::warning
Не путайте критерии разных колонок: «Заказчик утвердил» относится к приёмке, а не к разработке; «Цель ясна» — это условие завершения анализа.
:::

## Agile

### Agile манифест

Манифест Agile формулирует четыре ценностных предпочтения:

| Ценим больше | Ценим меньше |
|---|---|
| Люди и взаимодействие | Процессы и инструменты |
| Работающий продукт | Исчерпывающая документация |
| Сотрудничество с заказчиком | Согласование условий контракта |
| Готовность к изменениям | Следование первоначальному плану |

:::remember
Читать манифест нужно так: «Люди и взаимодействие **важнее** процессов и инструментов», и так по каждой строке.
:::

:::warning
Манифест не отрицает важность правой колонки. Он говорит лишь о том, что то, что слева, ценится **больше**. Это не отказ от процессов, документации, контрактов и планов.
:::

## Fin

:::note
На рисунке — комикс из трёх рядов, сравнивающий подходы на примере полёта на Марс.

**The Waterfall Method:** «You want to go to Mars» (вы хотите на Марс) → «You build a rocket» (вы строите ракету) → «You test the rocket» (вы тестируете ракету) → «You go Mars» (вы летите на Марс).

**Agile Development:** «You want to go to Mars, probably» (вы, возможно, хотите на Марс) → «You start building a rocket» (вы начинаете строить ракету) → «You then want to go to Uranus» (потом вы хотите на Уран) → «You go to the Moon» (вы летите на Луну).

**The Kanban Method:** «You want to go to Mars» (вы хотите на Марс) → «You split the work into thousands of tiny pieces» (вы разбиваете работу на тысячи мелких частей) → «One year later you are still waiting for the armrests to be done» (год спустя вы всё ещё ждёте, пока доделают подлокотники).
:::
