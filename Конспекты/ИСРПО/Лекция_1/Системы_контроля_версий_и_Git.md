# Системы контроля версий (Version control)

## Хронология

:::meaning
**Система контроля версий (VCS, Version Control System)** — инструмент, который отслеживает изменения в файлах проекта и хранит их версии. Развитие таких систем принято делить на три поколения: от локальных систем для одного пользователя до Git, самой популярной системы в мире.
:::

```diagram

C: round "1986 CVS" @ 300, 140
D: round "2000 BitKeeper, SVN" @ 420, 60

```

### Первое поколение

Системы контроля версий первого поколения обладали двумя ограничениями:

- отслеживали изменения только в **отдельных файлах** (а не в проекте целиком);
- редактирование поддерживалось **только локально и одним пользователем за раз**.

**SCCS (Source Code Control System)** считается одной из первых успешных систем управления версиями. Её разработал в 1972 году Марк Рочкинд в Bell Labs. Система написана на C и создана для отслеживания версий исходного файла.

**RCS (Revision Control System)** написана в 1982 году Уолтером Тихи на языке C как альтернатива SCCS: на тот момент SCCS не была опенсорсной.

### Второе поколение

Главное нововведение систем второго поколения — **поддержка сети**. Благодаря ей появились **централизованные хранилища** с «официальными» версиями проектов.

**CVS (Concurrent Versions System)** создана Диком Груном в 1986 году с целью добавить в систему управления версиями поддержку сети. Впервые CVS позволила **нескольким разработчикам одновременно работать с одними и теми же файлами**. Это реализовано с помощью модели централизованного репозитория.

**SVN (Subversion)** создана в 2000 году компанией Collabnet Inc., а в настоящее время поддерживается Apache Software Foundation. Система написана на C и разработана как более надёжное централизованное решение, чем CVS. Как и CVS, Subversion использует модель централизованного репозитория.

:::note
В 2000 году появилась и система BitKeeper (создана компанией Bitmover Inc), вместе с SVN отмеченная на хронологической шкале.
:::

### Третье поколение

Систему **Git** разработал в 2005 году Линус Торвальдс, создатель Linux. Она написана в основном на C в сочетании с некоторыми сценариями командной строки. Git отличается от предыдущих систем по функциям, гибкости и скорости.

Торвальдс изначально написал систему для кодовой базы Linux, но со временем сфера её использования расширилась, и сегодня это **самая популярная в мире система управления версиями**. В том же 2005 году Мэтт Макколл создал систему Mercurial.

:::remember
Три поколения VCS:
1. **Первое** (SCCS, RCS) — отдельные файлы, локальная работа, один пользователь за раз.
2. **Второе** (CVS, SVN) — поддержка сети, централизованный репозиторий, одновременная работа нескольких разработчиков.
3. **Третье** (Git) — 2005 год, Линус Торвальдс, самая популярная система сегодня.
:::

## Что внутри?

Когда файл добавляется для отслеживания в Git, происходят две вещи с его содержимым:

1. Содержимое **сжимается** алгоритмом **zlib**.
2. Для содержимого вычисляется хэш с помощью хэш-функции **SHA-1**.

Хэш получается **уникальным**: он соответствует именно содержимому этого файла. Git хранит данные в **базе объектов**, расположенной в скрытой папке `.git/objects`. Имя файла в ней — это сгенерированный хэш, а внутри файла лежит сжатый контент.

```diagram
title: Как Git сохраняет файл
F: box "Содержимое файла" @ 100, 110
H: box "SHA-1" @ 290, 50
Z: box "zlib" @ 290, 170
O: db ".git/objects" @ 490, 110
F -> H : хэш
F -> Z : сжатие
H -> O : имя файла
Z -> O : содержимое файла
```

Такие файлы создаются **каждый раз**, когда в репозиторий добавляется новый файл или изменённая версия существующего файла.

:::meaning
**База объектов** — хранилище в папке `.git/objects`. Каждый объект — отдельный файл: его имя — хэш содержимого, а содержимое файла — сжатые данные.
:::

:::warning
Хэш — это имя объекта, он вычисляется по содержимому файла. Имя исходного файла и хэш — разные вещи: в базе объектов файл называется именно хэшем.
:::

## Основные команды

### Создание и получение репозитория

- `git init` — инициализировать текущий каталог как репозиторий Git. Создаётся скрытая папка `.git` и её содержимое.
- `git clone <git-url>` — загрузить копию репозитория Git по указанному URL.

### Фиксация изменений

- `git add <filename.ext>` — добавить неотслеженный или изменённый файл в **промежуточную область**. При этом создаются соответствующие записи в базе данных объектов.
- `git commit -m 'Commit message'` — зафиксировать набор изменённых файлов и папок вместе с сообщением о коммите.
- `git commit --amend` — отредактировать текст сообщения к последнему коммиту.

:::warning
Команду `git commit --amend` можно использовать только если коммит **ещё не был отправлен на сервер** (`git push`).
:::

### Состояние и история

- `git status` — показать статус рабочего каталога, текущей ветви, неотслеженных файлов, изменённых файлов и т. д.
- `git log` — показать историю коммитов и соответствующие сообщения для активной ветви.

### Ветви

- `git branch <new-branch>` — создать новую ветвь на основе текущей извлечённой ветви.
- `git checkout <branch>` — извлечь указанную ветвь в рабочий каталог.
- `git merge <branch>` — объединить указанную ветвь с текущей, извлечённой в рабочий каталог.

### Обмен с удалённым репозиторием

- `git pull` — обновить рабочую копию: объединить в неё зафиксированные изменения, которые существуют в удалённом репозитории, но не в рабочей копии.
- `git push` — упаковать свободные объекты для локальных коммитов активной ветви в файлы пакета и перенести их в удалённый репозиторий.

```diagram
title: Путь изменений в Git
W: box "Рабочий каталог" @ 90, 80
S: box "Промежуточная область" @ 280, 80
L: box "Локальные коммиты" @ 480, 80
R: db "Удалённый репозиторий" @ 480, 230
W -> S : git add
S -> L : git commit
L -> R : git push
R -> W : git pull
```

:::example
Типичная последовательность, чтобы изменённый файл попал на сервер:
1. `git status` — посмотреть, какие файлы изменены.
2. `git add <filename.ext>` — добавить файл в промежуточную область.
3. `git commit -m 'Commit message'` — зафиксировать изменения с сообщением.
4. `git push` — отправить локальные коммиты в удалённый репозиторий.
:::

## Если что-то пошло не так

Чтобы вернуться к рабочему состоянию, есть несколько способов.

**Через `git reflog`.** Эта команда показывает список всего, что вы сделали в Git, **во всех ветках**. У каждого элемента есть индекс `HEAD@{index}`. Нужно найти элемент, перед которым всё сломалось, и выполнить:

```bash
git reset HEAD@{index}
```

**Отменить последний коммит:**

```bash
git reset --hard HEAD~1
```

**Отменить коммит, который был $n$ коммитов назад.** Сначала найдите нужный коммит в истории, затем отмените его по хэшу:

```bash
git log
git revert [хэш того самого коммита]
```

```diagram
title: Выбор способа отката
S: round "Что-то пошло не так" @ 320, 30
A1: box "git reflog" @ 110, 130
A2: box "git reset HEAD@{index}" @ 110, 240
B1: box "git reset --hard HEAD~1" @ 320, 170
C1: box "git log" @ 530, 130
C2: box "git revert хэш" @ 530, 240
S -> A1 : все действия
A1 -> A2
S -> B1 : последний коммит
S -> C1 : коммит n назад
C1 -> C2
```

:::remember
- Нужно найти момент перед поломкой — смотрите `git reflog` и откатывайтесь через `git reset HEAD@{index}`.
- Отменить последний коммит — `git reset --hard HEAD~1`.
- Отменить коммит из глубины истории — найти хэш через `git log` и выполнить `git revert` с этим хэшем.
:::
