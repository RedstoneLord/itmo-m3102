# Лекция 7. Компилятор и препроцессор

## План лекции

В лекции рассматриваются семь ключевых тем:

- **Программы состоят из файлов**: логика модульности, повторное использование кода и ускорение сборки.
- **Этапы трансляции**: конвейер преобразования исходного кода в исполняемый файл и флаги компилятора.
- **Объявление и определение**: разграничение интерфейса и реализации, структура заголовочных файлов.
- **Препроцессор**: директивы `#include`, макросы с параметрами, побочные эффекты, условная компиляция и стражи включения.
- **Компилятор**: трансляция в ассемблер, декорирование имён (name mangling), ассемблирование и структура объектных файлов.
- **Компоновщик (линковщик)**: связывание объектных файлов, разрешение символов, разграничение ошибок компиляции и компоновки.
- **Linkage и storage duration**: связывание имён, правило одного определения (ODR), спецификатор `inline` и продолжительность хранения в памяти.

## 1. Программы состоят из файлов

В реальной разработке на C++ программы практически никогда не пишутся в одном монолитном файле. Исходный код разделяют на множество связанных файлов по нескольким фундаментальным причинам:

- **Логическое разбиение на модули**: связанные функции, структуры данных и классы объединяются в смысловые блоки (например, математические вычисления, сетевое взаимодействие, пользовательский интерфейс). Это делает кодовую базу обозримой и поддерживаемой.
- **Повторное использование кода**: однажды написанный и отлаженный модуль (например, модуль геометрии или алгоритмов сортировки) можно подключать к десяткам других программ без дублирования исходного текста.
- **Ускорение сборки (раздельная компиляция)**: компилятор обрабатывает каждый файл с исходным кодом независимо. Если разработчик изменил функцию в одном `.cpp`-файле, перекомпилировать придётся только его, а не всю программу целиком.
- **Читаемость и командная работа**: файлы небольшого размера гораздо легче рецензировать (code review), анализировать и параллельно редактировать разным разработчикам, избегая конфликтов слияния (merge conflicts) в системах контроля версий.

### Общепринятые расширения файлов

В проектах на C++ принято чёткое разделение ролей между файлами:

- **Заголовочные файлы (headers)** — расширения `.h` или `.hpp`. Содержат интерфейс: объявления функций, объявления внешних переменных, определения пользовательских типов (структур, классов, перечислений) и константы.
- **Файлы с исходным кодом (source files)** — расширение `.cpp` (встречаются также `.cc` или `.cxx`). Содержат реализацию: определения функций и логику выполнения.

:::note
Расширение `.h` традиционно пришло из языка C, тогда как `.hpp` подчеркивает наличие конструкций C++. Оба расширения корректно воспринимаются современными компиляторами.
:::

## 2. Этапы трансляции

Преобразование исходного текста программы на C++ в готовый бинарный исполняемый файл — это многоступенчатый процесс. Каждый исходный файл `.cpp` обрабатывается независимо, проходя через конвейер из трёх этапов, после чего все полученные объектные файлы объединяются компоновщиком.

:::meaning
**Единица трансляции (Translation Unit)** — это текст одного исходного файла `.cpp` после того, как препроцессор выполнил все включения файлов (`#include`), раскрыл все макросы (`#define`) и применил директивы условной компиляции (`#ifdef`). Именно единица трансляции подаётся на вход компилятору.
:::

### Этапы по отдельности

Для вызова каждого шага трансляции вручную компиляторы семейства Clang и GCC предоставляют специальные флаги командной строки:

| Команда | Выполняемый этап | Результат работы |
| :--- | :--- | :--- |
| `clang++ -std=c++20 -E main.cpp` | Препроцессор | Текст единицы трансляции выводится в терминал (консоль) |
| `clang++ -std=c++20 -S main.cpp` | Препроцессор + компиляция | Текстовый файл с кодом на ассемблере `main.s` |
| `clang++ -std=c++20 -c main.cpp` | Препроцессор + компиляция + ассемблирование | Бинарный объектный файл `main.o` |
| `clang++ main.o math.o -o program` | Компоновка (линковка) | Бинарный исполняемый файл `program` |

:::remember
Компоновщик не требуется запускать отдельной утилитой (например, `ld`): драйвер компилятора `clang++` сам вызывает компоновщик с необходимыми системными библиотеками и параметрами среды выполнения.

Если компоновщику требуется передать специфический аргумент напрямую, используется флаг `-Xlinker <arg>` (например, `-Xlinker -v` для подробного вывода версий и путей поиска).
:::

## 3. Объявление и определение

Основой модульности в C++ является строгое разделение понятий объявления и определения сущностей.

:::meaning
**Объявление (declaration)** вводит имя в программу и сообщает компилятору его тип и свойства (например, сигнатуру функции: имя, типы параметров и тип возвращаемого значения). Объявление позволяет использовать сущность до того, как станет известна её полная реализация. Согласованные объявления одной и той же сущности можно повторять многократно.

**Определение (definition)** предоставляет исчерпывающую информацию о сущности: для функции — её тело `{ ... }`, для переменной — выделение памяти под неё, для класса — список полей и методов. Любое определение одновременно является объявлением.
:::

```cpp
// declaration-and-definition.cpp

int Add(int a, int b); // Объявление функции (declaration)

int Add(int a, int b) { // Определение функции (definition)
    return a + b;
}
```

### Определение в другом файле

Благодаря объявлению компилятор может проверить корректность типов аргументов и возвращаемого значения в месте вызова, даже если само тело функции реализовано в другом файле.

```cpp
// math.cpp
int Add(int a, int b) {
    return a + b;
}
```

```cpp
// main.cpp
#include <iostream>

int Add(int a, int b); // Только объявление!

int main() {
    std::cout << Add(10, 2) << '\n';
    return 0;
}
```

Сборка программы из двух файлов выполняется одной командой:
```bash
clang++ -std=c++20 main.cpp math.cpp -o program
```

:::example
Разберём процесс сборки по шагам:
1. При компиляции `main.cpp` компилятору достаточно видеть сигнатуру `int Add(int a, int b);`. Он проверяет, что передано два аргумента типа `int`, и генерирует машинный код вызова с временным пустым адресом.
2. Файл `math.cpp` компилируется независимо и порождает машинный код тела функции `Add`.
3. На этапе компоновки компоновщик связывает вызов из `main.o` с адресом функции `Add` из `math.o`.
:::

### Заголовочный файл

Писать объявления вручную в начале каждого `.cpp`-файла неудобно и чревато ошибками: если сигнатура изменится в одном месте, остальные файлы перестанут быть согласованы. Для распространения объявлений служат **заголовочные файлы**.

Что **помещают** в заголовочный файл:
- Объявления функций: `void Increment(int& value);`
- Объявления внешних переменных: `extern int total;`
- Определения типов: `struct`, `class`, `enum`
- Константы (`const`, `constexpr`)

Что **не помещают** в заголовочный файл (за исключением `inline` и шаблонов):
- Определения обычных функций (с телом `{ ... }`)
- Определения обычных глобальных переменных (без спецификатора `extern`)

:::remember
Заголовок описывает публичный интерфейс модуля для других единиц трансляции. Внутренние вспомогательные функции и переменные, необходимые только конкретному `.cpp`, должны оставаться внутри этого `.cpp` и не выноситься в заголовок.
:::

### Объявления в заголовке, определения в .cpp

Организуем код правильно: вынесем объявления в заголовок `math.hpp`, а реализацию — в `math.cpp`.

```cpp
// math.hpp
#pragma once

void Increment(int& value);
int Add(int a, int b);
```

```cpp
// math.cpp
#include "math.hpp"

void Increment(int& value) {
    ++value;
}

int Add(int a, int b) {
    return a + b;
}
```

:::note
Обратите внимание: файл `math.cpp` сам включает заголовок `#include "math.hpp"`. Это критически важно: компилятор одновременно видит и объявленную сигнатуру, и тело функции, проверяя их полную согласованность между собой.
:::

### Использование заголовка

В файле `main.cpp` достаточно подключить интерфейс через директиву `#include "math.hpp"`:

```cpp
// main.cpp
#include <iostream>
#include "math.hpp"

int main() {
    int x = 1;
    int y = 2;
    Increment(y);
    std::cout << Add(x, y) << '\n'; // 1 + 3 = 4
    return 0;
}
```

При компиляции `main.cpp` видит объявления из `math.hpp`. Затем на этапе компоновки объектные файлы `main.o` и `math.o` объединяются, образуя рабочую программу.

## 4. Препроцессор

Препроцессор — это инструмент предварительной текстовой обработки исходного кода, который запускается до начала синтаксического и семантического анализа C++. Препроцессор не анализирует типы данных, не знает правил областей видимости и оперирует исключительно потоком токенов и текстовыми строками.

Все команды препроцессора называются **директивами** и начинаются с символа `#`.

### Директивы препроцессора

Основные директивы можно разделить на группы:

- **Подключение файлов**: `#include <...>` и `#include "..."`.
- **Макроподстановки**: `#define` (создать макрос), `#undef` (отменить определение макроса).
- **Условная компиляция**: `#if`, `#ifdef`, `#ifndef`, `#elif`, `#else`, `#endif`.
- **Предопределённые макросы**: `__FILE__` (имя текущего файла в виде строки), `__LINE__` (номер текущей строки исходного файла в виде целого числа).
- **Операторы макросов**: `#` (стрингификация — превращение токена аргумента в строковый литерал) и `##` (склейка токенов).
- **Управление сборкой и диагностика**: `#error` (принудительно прерывает трансляцию с сообщением об ошибке), `#pragma once` (страж включения файла), `#pragma pack` (управление выравниванием структур).

:::note
Угловые скобки `#include <filename>` служат для поиска в стандартных и системных путях сборки. Двойные кавычки `#include "filename"` сначала начинают поиск в каталоге рядом с текущим файлом, а затем переходят к стандартным путям (точные правила зависят от компилятора и флагов вроде `-I`).
:::

### Что делает #include

Директива `#include` выполняет прямолинейную текстовую операцию: препроцессор полностью удаляет строку директивы и вставляет на её место всё содержимое указанного файла.

```diagram
title: Текстовая подстановка директивы include
SRC: box "main.cpp (с директивами include)"
HDR: box "math.hpp (объявления функций)"
PP: round "Препроцессор"
RES: box "Единица трансляции: код заголовков и main.cpp"
SRC -> PP : передача исходного файла
HDR -> PP : считывание содержимого
PP -> RES : подстановка содержимого на место директив
```

После раскрытия всех `#include` даже небольшой файл с одной строкой `#include <iostream>` разрастается в огромную единицу трансляции размером в десятки тысяч строк (в зависимости от реализации стандартной библиотеки).

### Этап препроцессора на практике

Сохранить вывод препроцессора в отдельный файл можно с помощью флага `-E`:

```bash
clang++ -std=c++20 -E main.cpp -o main.ii
```

Если открыть получившийся файл `main.ii`, в конце (после содержимого заголовков) будет виден фрагмент:

```cpp
// Фрагмент вывода clang++ -E (текст <iostream> опущен)
# 1 "./math.hpp" 1
void Increment(int& value);
int Add(int a, int b);
# 4 "main.cpp" 2
int main() {
    int x = 1;
    int y = 2;
    Increment(y);
    std::cout << Add(x, y) << '\n';
    return 0;
}
```

:::meaning
Строки вида `# 4 "main.cpp" 2` называются **маркерами строк (line markers)**. Они генерируются препроцессором, чтобы последующие этапы компилятора могли сопоставлять генерируемый код и возможные сообщения об ошибках с исходными файлами и номерами строк на диске.
:::

### Макросы

Директива `#define` задаёт макроподстановку: идентификатор заменяется заданной последовательностью токенов.

```cpp
// macro-max.cpp
#include <iostream>

#define MAXIMUM(x, y) ((x) > (y) ? (x) : (y))

int main() {
    std::cout << MAXIMUM(10, 20) << '\n';
    return 0;
}
```

Посмотрим на результат работы препроцессора (`clang++ -E macro-max.cpp`):
```cpp
// macro-max-preprocessed.txt
# 2 "macro-max.cpp" 2
int main() {
    std::cout << ((10) > (20) ? (10) : (20)) << '\n';
    return 0;
}
```

:::remember
В макросах аргументы обязательно окружают круглыми скобками как в теле выражения, так и вокруг каждого аргумента: `((x) > (y) ? (x) : (y))`. Это предотвращает искажение приоритета операций при подстановке сложных выражений вида `MAXIMUM(1 + 2, 3 * 4)`.
:::

### Побочные эффекты макросов

Поскольку макрос выполняет текстовую подстановку токенов, аргументы с побочными эффектами вычисляются столько раз, сколько раз они встречаются в теле макроса.

```cpp
// macro-double-evaluation.cpp
#include <iostream>

#define MAXIMUM(x, y) ((x) > (y) ? (x) : (y))

int main() {
    int i = 1;
    int j = 2;
    int m = MAXIMUM(i++, j++);
    std::cout << m << ' ' << i << ' ' << j << '\n';
    return 0;
}
```

:::example
Разберём пошагово, почему вывод программы равен `3 2 4`:
1. Макрос разворачивается в выражение:
   $$((i++) > (j++) \mathbin{?} (i++) : (j++))$$
2. Сначала вычисляется условие тернарного оператора: `(i++) > (j++)`. Сравниваются текущие значения `1 > 2`. Условие ложно (`false`).
3. В результате постфиксных инкрементов переменная `i` становится равной `2`, а `j` — равной `3`.
4. Поскольку условие ложно, вычисляется только вторая ветвь тернарного оператора — выражение `(j++)`.
5. Текущее значение `j` (которое равно `3`) возвращается как результат всего выражения и присваивается переменной `m` (значит, `m = 3`).
6. После возврата значения срабатывает второй инкремент `j++`, и переменная `j` увеличивается до `4`.
7. Переменная `i++` из первой ветви не вычислялась. Итог: `m = 3`, `i = 2`, `j = 4`.
:::

:::warning
Если бы вместо макроса использовалась обычная функция `int Maximum(int x, int y)`, каждый аргумент гарантированно вычислился бы строго один раз до входа в тело функции, а компилятор выполнил бы строгую проверку типов.
:::

### Препроцессор не знает C++

Препроцессор работает до компилятора и не имеет представления о пространствах имён, классах или областях видимости.

```cpp
// macro-name-collision.cpp (намеренно не компилируется)
#include <cmath>
#include <cstdio>

#define log(level, message) std::printf("[%s] %s\n", level, message)

int main() {
    log("INFO", "start");
    double x = std::log(2.718); // Ошибка компиляции!
    return x > 0 ? 0 : 1;
}
```

Компилятор выдаст ошибку:
```text
error: too few arguments provided to function-like macro invocation
    double x = std::log(2.718);
                       ^
```

Препроцессор встретил токен `log` и попытался подставить макрос, требующий два аргумента. Префикс `std::` не защищает идентификатор от препроцессора!

:::remember
Имена макросов принято писать исключительно `ЗАГЛАВНЫМИ_БУКВАМИ_С_ПОДЧЁРКИВАНИЕМ`, чтобы избежать случайных коллизий с именами функций, переменных и методов.
:::

### Условная компиляция

Директивы условной компиляции позволяют включать или исключать фрагменты кода из обработки в зависимости от наличия макроопределений.

```cpp
// conditional-log.cpp
#include <cstdio>

#ifdef DEBUG
#define ERROR_LOG(format, ...) \
    std::printf("[ERROR] (%s:%d) " format "\n", \
        __FILE__, __LINE__ __VA_OPT__(, ) __VA_ARGS__)
#else
#define ERROR_LOG(format, ...)
#endif

int main() {
    ERROR_LOG("fatal error no: %d", 1);
    return 0;
}
```

#### Определение макросов при сборке

Макросы можно объявлять без изменения исходного кода, передавая флаг компилятору:
```bash
clang++ -std=c++20 -DDEBUG conditional-log.cpp -o program
```

- Флаг `-DDEBUG` эквивалентен записи `#define DEBUG 1` перед первой строкой файла.
- Можно явно передать значение: `-DDEBUG=1` или `-DLEVEL=3`.
- С флагом `-DDEBUG` программа выведет сообщение об ошибке; без флага вызов `ERROR_LOG(...)` раскроется в пустую строку.

:::warning
Директива `#ifdef DEBUG` проверяет факт **определения** имени. Даже если передать `-DDEBUG=0`, условие `#ifdef DEBUG` будет истинным! Если требуется проверять именно численное значение, используют директиву `#if DEBUG`.
:::

#### Определение макросов в CMake

В современных проектах на C++ сборкой управляет CMake. Для передачи макросов в компилятор используется команда `target_compile_definitions`:

```cmake
cmake_minimum_required(VERSION 3.16)
project(conditional_log LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(conditional-log conditional-log.cpp)

# Определение макроса DEBUG для конкретной цели сборки:
target_compile_definitions(conditional-log PRIVATE DEBUG)
```

- Ключевое слово `PRIVATE` означает, что макрос применяется только при компиляции исходных файлов самой цели `conditional-log`.
- Имя пишется без префикса `-D`: CMake сам подставит нужный флаг под конкретный компилятор.
- Обратите внимание: флаг командной строки `cmake -DDEBUG=ON` задаёт переменную внутри самого файла CMake, но автоматически **не** создаёт макрос в C++. Стандартная конфигурация сборки Debug также не объявляет пользовательский макрос `DEBUG` по умолчанию.

### Макрос с переменным числом аргументов

В макросе `ERROR_LOG` используются специальные возможности работы со списком аргументов:

| Синтаксис | Назначение |
| :--- | :--- |
| `\` в конце строки | Экранирование перевода строки: директива продолжается на следующей строке |
| `...` | Вариадический макрос (принимает переменное число аргументов) |
| `__VA_ARGS__` | Вставляет переданные дополнительные аргументы через запятую |
| `__VA_OPT__(, )` | Появился в C++20: генерирует запятую **только если** `__VA_ARGS__` не пуст |
| `__FILE__`, `__LINE__` | Предопределённые макросы: имя текущего файла и номер строки вызова |

:::note
В макросе `"[ERROR] (%s:%d) " format "\n"` используется автоматическая склейка соседних строковых литералов в C++. Поэтому первый аргумент `format` обязан быть строковым литералом (например, `"value: %d"`), а не переменной типа `const char*`.
:::

### Макрос через другой макрос

Макросы могут вызывать другие макросы:

```cpp
// macro-log-levels.cpp
#include <cstdio>

#define LOG(level, format, ...) \
    std::printf("[" level "] (%s:%d) " format "\n", \
        __FILE__, __LINE__ __VA_OPT__(, ) __VA_ARGS__)

#define LOG_ERROR(...) LOG("ERROR", __VA_ARGS__)
#define LOG_INFO(...)  LOG("INFO", __VA_ARGS__)

int main() {
    LOG_INFO("started");
    LOG_ERROR("error code: %d", 1);
    return 0;
}
```

Макрос `LOG_ERROR` сначала раскрывается в вызов `LOG`, подставляя уровень `"ERROR"`, а затем в вызов `std::printf`. При этом `__FILE__` и `__LINE__` соответствуют строке в функции `main`, где был вызван `LOG_ERROR`.

### Переносимость и соглашения об именовании

- В старом коде (до C++20) для удаления висячей запятой при пустом `__VA_ARGS__` использовалось расширение GNU: `, ##__VA_ARGS__`. Начиная с C++20 стандартным переносимым способом является оператор `__VA_OPT__(, )`.
- Имена, начинающиеся с двух подчёркиваний (`__DEBUG__`) или подчёркивания с заглавной буквы (`_Debug`), **зарезервированы** за компилятором и стандартной библиотекой: программистам запрещено создавать такие макросы.
- Стандартный макрос `NDEBUG` управляет отключением макроса `assert`: если `NDEBUG` определён, все проверки `assert(...)` удаляются из кода.

### Двойное включение файлов

Рассмотрим классическую ошибку, возникающую при трансляции:

```cpp
// point.hpp
struct Point {
    int x;
    int y;
};
```

```cpp
// shape.hpp
#include "point.hpp"

struct Shape {
    Point center;
    int size;
};
```

```cpp
// main.cpp
#include "point.hpp"
#include "shape.hpp"

int main() {
    Shape shape{{1, 2}, 3};
    return shape.size;
}
```

При компиляции `main.cpp` препроцессор сначала вставляет `point.hpp`, а затем разворачивает `shape.hpp`, который снова вставляет `point.hpp`. В единицу трансляции попадают две одинаковые структуры `struct Point`.

Компилятор немедленно сообщает об ошибке:
```text
error: redefinition of 'Point'
struct Point {
       ^
note: previous definition is here
```

### Стражи включения (Include Guards)

Чтобы файл обрабатывался препроцессором ровно один раз на единицу трансляции, используют **стражи включения**:

```diagram
title: Предотвращение повторного включения стражем
M: box "main.cpp"
P: box "point.hpp (struct Point)"
S: box "shape.hpp (включает point.hpp)"
TU: box "Единица трансляции"
M -> P : первое включение
M -> S : включение
S -> P : повторное включение
P -> TU : структура Point добавлена
S -> TU : определение Shape добавлено
```

Существует два способа защиты:

1. **Классический страж включения (Include Guard)**:
```cpp
// point.hpp
#ifndef POINT_HPP
#define POINT_HPP

struct Point {
    int x;
    int y;
};

#endif // POINT_HPP
```
При первом включении макрос `POINT_HPP` ещё не определён. Препроцессор заходит внутрь блока, определяет макрос и вставляет структуру. При повторном включении директива `#ifndef` оказывается ложной, и весь файл до `#endif` пропускается.

2. **Директива `#pragma once`**:
```cpp
// point.hpp
#pragma once

struct Point {
    int x;
    int y;
};
```
Директива `#pragma once` указывает препроцессору пропустить данный файл, если он уже был однажды прочитан в рамках текущей единицы трансляции. Хотя `#pragma once` формально не входит в текст стандарта C++, она поддерживается всеми ключевыми компиляторами (Clang, GCC, MSVC) и является де-факто индустриальным стандартом.

```quiz

explain: `#pragma once` работает на этапе препроцессинга и предотвращает повторную вставку одного и того же заголовка в одну и ту же единицу трансляции.
```

## 5. Компилятор

Компилятор принимает на вход единицу трансляции — полностью обработанный препроцессором текстовый файл — и выполняет синтаксический, семантический анализ, оптимизацию и генерацию кода.

:::remember
Каждый `.cpp`-файл компилируется компилятором **абсолютно изолированно и независимо** от остальных файлов проекта. Компилятор не знает, какие функции или переменные определены в других `.cpp`.
:::

### Что выдаёт компилятор

При передаче флага `-S` компилятор преобразует C++ код в понятный человеку ассемблерный текст:

```bash
clang++ -std=c++20 -S -masm=intel -O0 math.cpp
```

Посмотрим на полученный фрагмент функции `Increment(int& value)` для архитектуры x86-64 (Linux):

```nasm
_Z9IncrementRi:                   # Символьное имя функции в ассемблере
    push    rbp
    mov     rbp, rsp
    mov     qword ptr [rbp - 8], rdi # rdi хранит адрес переменной value
    mov     rax, qword ptr [rbp - 8]
    mov     ecx, dword ptr [rax]     # Загружаем int по этому адресу
    add     ecx, 1                   # Увеличиваем значение на 1 (++value)
    mov     dword ptr [rax], ecx     # Записываем изменённый int обратно по адресу
    pop     rbp
    ret
```

:::example
Здесь отчётливо видно устройство ссылок в низкоуровневом представлении:
- Ссылка на аргумент `value` пришла в функцию как обычный 64-битный адрес в регистре `rdi`.
- Для выполнения операции `++value` процессор читает значение по указанному адресу в регистр `ecx`, увеличивает его на единицу командой `add ecx, 1` и сохраняет результат обратно по исходному адресу в памяти.
:::

#### Декорирование имён (Name Mangling)

Обратите внимание на имя метки в ассемблере: `_Z9IncrementRi`. Компилятор C++ закодировал имя функции и типы её параметров по правилам **Itanium C++ ABI**:
- `_Z` — префикс декорированного имени;
- `9` — длина имени идентификатора (`Increment`);
- `R` — указатель/ссылка (Reference);
- `i` — тип `int`.

:::meaning
**Декорирование имён (Name Mangling)** — механизм генерации уникальных ассемблерных символов для функций на основе их сигнатуры. Именно благодаря декорированию имён в C++ возможна **перегрузка функций (function overloading)**: функции с одинаковым именем, но разными типами параметров, получают абсолютно разные символы на уровне объектного кода.
:::

### Зачем нужно ассемблирование

Процессор не понимает текстовые мнемоники ассемблера (`mov`, `push`, `ret`): он выполняет только последовательности двоичных байт машинных инструкций.

**Ассемблер** транслирует ассемблерный текст в двоичный **объектный файл** (`.o` в Linux/macOS, `.obj` в Windows). Объектный файл структурирован по секциям:
- `.text` — исполняемый машинный код функций;
- `.data` — инициализированные глобальные и статические переменные;
- `.rodata` — данные, доступные только для чтения (строковые литералы, константы);
- `.bss` — неинициализированные глобальные и статические переменные (заполняются нулями при старте);
- **Таблица символов (Symbol Table)** — список всех имён, определённых в данном модуле или требуемых из других модулей;
- **Таблица перемещений (Relocations)** — список мест в машинном коде, где адреса функций или переменных пока неизвестны и должны быть вычислены компоновщиком.

:::note
Современный `clang++` обычно содержит встроенный ассемблер, поэтому вызов `clang++ -c main.cpp` преобразует C++ в `.o` напрямую в памяти, минуя создание промежуточного текстового файла `.s` на диске.
:::

### Что внутри объектного файла

Изучить бинарное содержимое объектного файла позволяет утилита `objdump`:

```bash
objdump -dr --x86-asm-syntax=intel main.o
```

Фрагмент вывода машинного кода вызовов функций:
```text
1d: 48 8d 7d f4         lea    rdi, [rbp - 12]
21: e8 00 00 00 00      call   26 <_main+0x26>  X86_64_RELOC_BRANCH __Z9IncrementRi
26: 8b 7d f8            mov    edi, dword ptr [rbp - 8]
29: 8b 75 f4            mov    esi, dword ptr [rbp - 12]
2c: e8 00 00 00 00      call   31 <_main+0x31>  X86_64_RELOC_BRANCH __Z3Addii
```

:::warning
Обратите внимание на байты машинной инструкции вызова `call`: `e8 00 00 00 00`. Относительное смещение перехода пока заполнено нулями (`00 00 00 00`)!

Поскольку компилятор компилировал `main.cpp` отдельно от `math.cpp`, он не знал, по какому физическому адресу в памяти окажутся тела функций `Increment` и `Add`. Поэтому он вставил заглушку и создал запись о перемещении: `X86_64_RELOC_BRANCH` (в Linux — `R_X86_64_PLT32`), дающую указание компоновщику: *«Вычисли точное смещение до функции `__Z9IncrementRi` и запиши его сюда»*.
:::

### Символы объектного файла

Просмотреть таблицу символов позволяет утилита `nm`:

```bash
nm main.o | c++filt
```

Утилита `c++filt` выполняет обратную операцию — деманглинг (восстанавливает читаемые имена функций C++ из декорированных строк):

```text
                 U Add(int, int)
                 U Increment(int&)
0000000000000000 T main
```

И для файла `math.o`:
```bash
nm math.o | c++filt
```
```text
0000000000000020 T Add(int, int)
0000000000000000 T Increment(int&)
```

Буквенные флаги в выводе `nm` имеют чёткое значение:
- **`U` (Undefined)**: символ используется в коде, но его определение в данном объектном файле **отсутствует** (оно должно прийти из другого модуля).
- **`T` (Text)**: символ функции определён в секции кода `.text` с глобальной видимостью (внешнее связывание, доступно другим модулям).
- **`t` (Text local)**: символ определён в секции кода, но имеет внутреннюю видимость (локален для файла, недоступен компоновщику снаружи).


## 6. Компоновщик (линковщик)

Компоновщик (linker) выполняет заключительный шаг сборки исполняемого файла:
1. Объединяет одноимённые секции всех переданных объектных файлов (все `.text` объединяются в единый сегмент кода, все `.data` — в сегмент данных).
2. Разрешает внешние символы: для каждого символа с меткой `U` в одном файле находит соответствующий символ `T` в другом объектном файле или библиотеке.
3. Применяет перемещения (relocations): вычисляет абсолютные адреса и относительные смещения вызовов и подставляет их на место нулей в коде.


Вспомним структуру нашего проекта:
- **Интерфейс** (`math.hpp`): объявления `Increment` и `Add`.
- **Реализация** (`math.cpp`): определения тел функций.
- **Точка входа** (`main.cpp`): вызовы функций.

Собираем по шагам вручную:
```bash

clang++ -std=c++20 -c main.cpp  # порождает main.o
clang++ -std=c++20 -c math.cpp  # порождает math.o

# 2. Вызываем компоновщик для создания единой программы:
clang++ main.o math.o -o program

# 3. Запускаем готовый исполняемый файл:
./program
# Вывод: 4
```

### Что нужно пересобрать после изменений?

Понимание зависимостей между файлами — основа быстрой сборки проектов:

| Изменившийся файл | Что необходимо перекомпилировать | Последующие действия |
| :--- | :--- | :--- |
| `math.cpp` | Только `math.o` | Повторная компоновка: `clang++ main.o math.o -o program` |
| `math.hpp` | И `main.o`, и `math.o` | Повторная компоновка |

:::note
Если изменился только `.cpp`-файл, пересобирается только один объектный файл. Но если изменился заголовочный файл `.hpp`, пересобираются **все** единицы трансляции, которые прямо или косвенно его подключали. Именно поэтому системы сборки (Make, Ninja, CMake) тщательно отслеживают граф зависимостей.
:::

### Ошибки компиляции и компоновки

Критически важно уметь различать, на каком этапе произошёл сбой:

- **Ошибка компиляции**: возникает внутри отдельной единицы трансляции. Причины: синтаксическая ошибка, несовпадение типов, использование необъявленного идентификатора (`error: use of undeclared identifier 'Add'`).
- **Ошибка компоновки**: возникает, когда все `.cpp` успешно скомпилировались в `.o`, но компоновщик не смог корректно сопоставить символы. Причины: определение символа не найдено ни в одном из файлов, либо один и тот же символ определён более одного раза.

---

### Эксперименты: проверяем каждый этап на практике

Разберём три показательных сценария намеренных ошибок.

#### Сценарий 1: Убрали объявление из заголовка

В файле `math.hpp` оставили только функцию `Increment`, убрав объявление `Add`:
```cpp
// math.hpp
#pragma once
void Increment(int& value);
```

Запускаем компиляцию `main.cpp`:
```bash
clang++ -std=c++20 -c main.cpp
```
Результат — **ошибка компиляции**:
```text
main.cpp:9:18: error: use of undeclared identifier 'Add'
    std::cout << Add(x, y) << '\n';
                 ^
```
Компилятор ничего не знает о существовании `math.cpp`. В единице трансляции `main.cpp` имени `Add` нет, поэтому компиляция обрывается на первом этапе.

#### Сценарий 2: Забыли передать объектный файл компоновщику

Вернули объявление в заголовок. Оба файла успешно компилируются в объектные файлы:
```bash
clang++ -std=c++20 -c main.cpp
clang++ -std=c++20 -c math.cpp
```
Теперь попытаемся скомпоновать программу, забыв передать `math.o`:
```bash
clang++ main.o -o program
```
Результат — **ошибка компоновки**:
```text
Undefined symbols for architecture x86_64:
  "Add(int, int)", referenced from:
      _main in main.o
  "Increment(int&)", referenced from:
      _main in main.o
ld: symbol(s) not found for architecture x86_64
```
В Linux диагностика выглядит аналогично: `undefined reference to 'Add(int, int)'`.
Компиляция прошла без ошибок, но на этапе линковки символы с меткой `U` из `main.o` не нашли своих реализаций `T`.

#### Сценарий 3: Перенесли определение функции в заголовок

Поместим тело функции `Add` прямо в заголовочный файл `math.hpp`:
```cpp
// math.hpp
#pragma once
void Increment(int& value);

int Add(int a, int b) { // Определение прямо в заголовке!
    return a + b;
}
```

Компилируем оба файла вместе:
```bash
clang++ -std=c++20 main.cpp math.cpp -o program
```

Результат — **ошибка компоновки**:
```text
duplicate symbol '__Z3Addii' in:
    main.o
    math.o
ld: 1 duplicate symbol for architecture x86_64
```
В Linux это диагностируется как: `multiple definition of 'Add(int, int)'`.

:::warning
Почему директива `#pragma once` не предотвратила ошибку?

`#pragma once` защищает от повторного включения **внутри одной единицы трансляции**.
Когда компилировался `main.cpp`, заголовок был включён один раз, и тело `Add` попало в `main.o`.
Когда отдельно компилировался `math.cpp`, заголовок снова был включён один раз, и то же самое тело `Add` попало в `math.o`.
При компоновке компоновщик обнаружил два независимых внешних символа с одинаковым именем `Add(int, int)` в разных объектных файлах!
:::

#### Глобальная переменная в заголовке без спецификаторов

Точно такая же ошибка возникает, если объявить обычную переменную в заголовке:

```cpp
// shared.hpp
#pragma once
int shared = 239; // Не-inline переменная в заголовке
```

Если подключить `shared.hpp` в `main.cpp` и в `math.cpp`, компилятор создаст глобальный символ `shared` в обоих объектных файлах, и линковщик выдаст ошибку `duplicate symbol '_shared'`.

Как правильно организовать общую глобальную переменную:
```cpp
// shared.hpp
#pragma once
extern int shared; // Только объявление! Память не выделяется.
```
```cpp
// math.cpp
#include "shared.hpp"
int shared = 239;  // Единственное определение в одном .cpp файле.
```

## 7. Linkage и storage duration

Поведение имён переменных и функций в нескольких файлах регулируется двумя важнейшими свойствами: **связыванием (linkage)** и **продолжительностью хранения (storage duration)**.

### Связывание (Linkage)

:::meaning
**Связывание (Linkage)** определяет, могут ли объявления одного и того же имени в разных областях видимости или разных единицах трансляции ссылаться на одну и ту же сущность.
:::

Существует три основных типа связывания:
1. **External linkage (внешнее связывание)**: имя может обозначать одну и ту же сущность во всей программе. Доступно компоновщику для связывания между разными `.o` файлами (например, обычные глобальные функции и переменные с `extern`).
2. **Internal linkage (внутреннее связывание)**: имя обозначает сущность, доступную **только в пределах текущей единицы трансляции**. В других `.cpp` файлах то же имя будет обозначать совершенно другие, изолированные объекты (например, глобальные переменные со спецификатором `static` или константы `const` на уровне файла в C++).
3. **No linkage (без связывания)**: имя не связывается ни с чем за пределами своего локального блока (например, локальные переменные внутри тела функции).


### Практический пример: исследование адресов

Рассмотрим три файла:

```cpp
// math.hpp
#pragma once

static const float kPi = 3.14F; // internal linkage: своя копия в каждом .cpp
extern const float kE;          // external linkage: определение будет в main.cpp
const int kAnswer = 239;        // const на уровне файла в C++ по умолчанию internal linkage!
static int counter = 0;         // internal linkage: изменяемая отдельная копия в каждом .cpp
extern int total;               // external linkage: объявление общего объекта
void PrintInfo();
```

```cpp
// math.cpp
#include <iostream>
#include "math.hpp"

void PrintInfo() {
    std::cout << "kPi     " << kPi     << "  " << &kPi     << '\n';
    std::cout << "kE      " << kE      << "  " << &kE      << '\n';
    std::cout << "kAnswer " << kAnswer << "  " << &kAnswer << '\n';
    std::cout << "counter " << counter << "  " << &counter << '\n';
    std::cout << "total   " << total   << "  " << &total   << '\n';
}
```

```cpp
// main.cpp
#include <iostream>
#include "math.hpp"

const float kE = 2.72F; // Определение переменной с external linkage
int total = 0;          // Определение переменной с external linkage

int main() {
    counter = 3;
    total = 2;

    std::cout << "kPi     " << kPi     << "  " << &kPi     << '\n';
    std::cout << "kE      " << kE      << "  " << &kE      << '\n';
    std::cout << "kAnswer " << kAnswer << "  " << &kAnswer << '\n';
    std::cout << "counter " << counter << "  " << &counter << '\n';
    std::cout << "total   " << total   << "  " << &total   << '\n';

    std::cout << "--- PrintInfo() из math.cpp ---\n";
    PrintInfo();
    return 0;
}
```

Скомпилируем и запустим:
```text

counter 3     0x1041f4004
total   2     0x1041f4000

kPi     3.14  0x1041efeb0
```

:::example
Проанализируем совпадение адресов:
- **`kE` и `total`**: их адреса в `main.cpp` и `math.cpp` **полностью совпали** (`0x1041efea4` и `0x1041f4000`). Это один и тот же физический объект на всю программу, потому что они имеют **external linkage**.
- **`counter`**: адреса различаются (`...004` и `...008`). Запись `counter = 3` в `main.cpp` изменила только локальную копию `main.o`. Функция `PrintInfo()` напечатала значение `0`, потому что в `math.o` живёт своя отдельная статическая переменная `counter`.
- **`const int kAnswer` и `kPi`**: имеют разные адреса в разных `.o` файлах. В языке C++ переменные с модификатором `const` на уровне пространства имён по умолчанию имеют **internal linkage**.
:::

### Правило одного определения: One Definition Rule (ODR)

:::meaning
**One Definition Rule (ODR)** — фундаментальное правило стандарта языка C++:
1. В любой единице трансляции может присутствовать **не более одного определения** любой переменной, функции, класса, перечисления или шаблона.
2. Во всей программе сущность с внешним связыванием (external linkage), не являющаяся `inline`, должна иметь **ровно одно определение**.
3. Сущности, объявленные как `inline` или шаблоны, могут определяться в нескольких единицах трансляции, при условии, что их определения состоят из **идентичной последовательности токенов** и ведут себя эквивалентно.
:::

### Спецификатор inline

Спецификатор `inline` исторически служил подсказкой компилятору встроить код функции вместо вызова, но в современном C++ его главное значение — **управление связыванием и ODR**:

- Функция или переменная (начиная с C++17), помеченная `inline`, может быть определена в нескольких единицах трансляции (обычно через заголовочный файл).
- При этом сущность сохраняет **external linkage**: компоновщик объединяет все такие определения и гарантирует, что в программе будет существовать **ровно один общий объект** с одинаковым адресом во всех модулях!

```cpp
// math.hpp
#pragma once

inline int calls = 0; // Начиная с C++17: inline-переменная в заголовке!

inline int Add(int a, int b) { // inline-функция в заголовке
    ++calls;
    return a + b;
}
```

:::note
Компилятор имеет полное право не встраивать тело функции с `inline` в машинный код вызова, и наоборот — может встроить любую обычную функцию без ключевого слова `inline`, если сочтёт это выгодной оптимизацией. Ключевое слово `inline` в первую очередь управляет правилами ODR.
:::

### Сравнение подходов: общий счётчик и константа

Сравним три способа размещения переменных в заголовке `counter.hpp`, подключаемом в два `.cpp`:

```cpp
// 1. Вариант plain (обычная переменная)
#pragma once
int counter = 0;              // Ошибка компоновки: duplicate symbol!
const int kAnswer = 239;

// 2. Вариант static (internal linkage)
#pragma once
static int counter = 0;       // В каждом .cpp своя изолированная переменная
const int kAnswer = 239;

// 3. Вариант inline (external linkage без ошибок дублирования)
#pragma once
inline int counter = 0;       // Единый разделяемый объект на всю программу!
inline constexpr int kAnswer = 239;
```

Результаты сравнения адресов между `main.cpp` и `counter.cpp`:

| Вариант заголовка | Исход сборки | Результат для `counter` | Результат для `kAnswer` |
| :--- | :--- | :--- | :--- |
| **plain** | Ошибка компоновки (`duplicate symbol`) | — | — |
| **static (internal)** | Сборка успешна | `0 1 false` (разные адреса) | `239 239 false` (разные адреса) |
| **inline** | Сборка успешна | `1 1 true` (один общий адрес) | `239 239 true` (один общий адрес) |

:::remember
Использование `inline constexpr` для констант и `inline` для глобальных переменных в заголовках — стандартная идиома современного C++ (C++17 и C++20).
:::

### Storage duration (продолжительность хранения)

:::meaning
**Продолжительность хранения (Storage Duration)** определяет время существования области памяти, выделенной под объект в процессе выполнения программы.
:::

Стандарт C++ определяет четыре категории продолжительности хранения:

| Категория | Продолжительность хранения | Типичное физическое размещение |
| :--- | :--- | :--- |
| **automatic** | Память существует с момента входа в блок до выхода из него | Стек (Stack) вызовов |
| **static** | Память выделяется при запуске программы и освобождается при её завершении | Секции `.data` и `.bss` исполняемого файла |
| **thread** | Память существует на протяжении времени работы конкретного потока (`thread_local`) | Thread-local storage (TLS) |
| **dynamic** | Память выделяется и освобождается вручную разработчиком (`new`/`delete`, `malloc`/`free`) | Динамическая память (Куча / Heap) |

Разберём взаимодействие области видимости, связывания и хранения памяти на примере:

```cpp
// scope-linkage-storage.cpp
#include <iostream>

int total = 0; // Глобальная переменная

void Count() {
    int local = 0;        // Локальная автоматическая переменная
    static int calls = 0; // Локальная статическая переменная
    std::cout << ++total << ' ' << ++local << ' ' << ++calls << '\n';
}

int main() {
    Count(); // 1 1 1
    Count(); // 2 1 2
    return 0;
}
```

Анализ характеристик переменных:

| Имя | Область видимости (Scope) | Связывание (Linkage) | Хранение (Storage duration) |
| :--- | :--- | :--- | :--- |
| `total` | Глобальная (файл) | External | Static |
| `local` | Блок функции `Count` | No linkage | Automatic |
| `calls` | Блок функции `Count` | No linkage | Static |

:::example
Обратите внимание на `static int calls`:
- Её **область видимости** локальна: обратиться по имени `calls` из функции `main` нельзя (ошибка компиляции).
- Её **связывание** — отсутствует (no linkage).
- Её **продолжительность хранения** — статическая: память под неё не освобождается при выходе из `Count()`. При втором вызове функции значение сохраняется с предыдущего раза, поэтому выводится `calls = 2`.
:::

### Спецификаторы класса памяти

- `static` на уровне пространства имён: задаёт внутреннее связывание (internal linkage) и статическое хранение.
- `static` внутри блока функции: задаёт отсутствие связывания (no linkage) и статическое хранение.
- `extern`: объявляет имя переменной или функции с внешним связыванием (external linkage), откладывая определение.
- `thread_local`: объявляет объект с продолжительностью хранения `thread`.

```quiz
explain: В отличие от языка C, в C++ спецификатор `const` для глобальных переменных по умолчанию даёт internal linkage, что позволяет безопасно объявлять простые константы в заголовочных файлах.

? Что делает спецификатор `inline` при применении к глобальной переменной в заголовочном файле (начиная с C++17)?
- [ ] Размещает переменную в стеке вызывающей функции
- [ ] Запрещает изменять значение переменной
- [x] Разрешает определять переменную в нескольких единицах трансляции, объединяя её в один общий объект с external linkage
- [ ] Делает переменную локальной для каждого `.cpp` файла (internal linkage)
explain: Спецификатор `inline` для переменных позволяет избежать нарушения One Definition Rule: компоновщик оставляет ровно один экземпляр переменной на всю программу.

? Чем отличается время жизни (lifetime) объекта от продолжительности хранения (storage duration)?
- [ ] Это синонимы, стандарт не делает между ними различий
- [x] Хранение определяет существование области памяти, а время жизни — интервал от завершения инициализации до завершения работы деструктора
- [ ] Время жизни относится только к динамической памяти, а хранение — только к стеку
- [ ] Хранение измеряется в байтах, а время жизни — в секундах
explain: Память под объект может быть уже выделена (например, неинициализированный буфер), но время жизни объекта начинается только после его конструирования и завершается перед освобождением памяти.
```

## Дополнительно: девять фаз трансляции C++20

Стандарт языка C++ описывает процесс трансляции не как запуск отдельных утилит, а в виде последовательности **девяти логических фаз**. Реальные компиляторы оптимизируют и объединяют эти шаги, однако наблюдаемый результат строго соответствует данной спецификации:

| Фаза | Название и суть действия |
| :---: | :--- |
| **1** | **Отображение символов**: физические символы исходного файла сопоставляются с базовым набором исходных символов. Обрабатываются триграфы и концы строк. |
| **2** | **Склейка строк**: удаляются последовательности обратного слэша и перевода строки (`\` + newline), объединяя логические строки кода. |
| **3** | **Лексический анализ препроцессора**: текст разбивается на токены препроцессора и пробельные символы. Все комментарии заменяются одиночными пробелами. |
| **4** | **Выполнение директив и раскрытие макросов**: обрабатываются `#include`, `#define`, `#if`, `#pragma`. Все рекурсивные макросы раскрываются. Повторяются фазы 1–4 для включённых файлов. |
| **5** | **Кодировка исполнения**: символы и escape-последовательности в символьных и строковых литералах преобразуются в целевую кодировку исполнения (execution character set). |
| **6** | **Склейка строковых литералов**: соседние строковые литералы (например, `"Hello, " "World!"`) объединяются в одну строку. |
| **7** | **Синтаксический и семантический анализ**: токены препроцессора становятся токенами языка C++. Выполняются грамматический разбор, проверка типов и генерация кода единицы трансляции. |
| **8** | **Инстанцирование шаблонов**: компилятор инстанцирует необходимые шаблоны функций и классов, формируя точки инстанцирования. |
| **9** | **Компоновка (разрешение внешних ссылок)**: компоновщик связывает внешние ссылки всех единиц трансляции и библиотек, формируя исполняемый образ программы. |
