## 1. Виртуальное адресное пространство

### Сначала различим три вещи

**Адрес** — число, обозначающее место в памяти. **Оперативная память, RAM** — физическое устройство. **Виртуальное адресное пространство процесса** — набор адресов, с которыми работает запущенная программа. Это разные понятия.

:::note
**Простыми словами.** Программа видит собственную карту домов с номерами. ОС и процессор переводят номер на этой карте в реальное место хранения. Одинаковый номер дома на картах двух программ не означает один и тот же дом.
:::

Процесс — экземпляр выполняющейся программы со своими ресурсами. Потоки одного процесса делят адресное пространство: код, глобальные данные, динамические объекты. У каждого потока свои регистры и стек вызовов. Стек другого потока не становится недоступным автоматически: при наличии корректного указателя доступ возможен, но нужно соблюдать время жизни и правила синхронизации.

### Как виртуальный адрес превращается в физический

ОС разбивает виртуальную память на **страницы**, физическую — на **страничные кадры**. Размер страницы зависит от системы; 4 КиБ — распространённый пример, а не правило C++. Таблицы страниц задают отображение и права доступа. Аппаратный блок **MMU** выполняет перевод; **TLB** кеширует недавно использованные переводы.

```text
Виртуальный адрес = номер страницы + смещение внутри неё
                          |
                    TLB / таблицы страниц
                          |
Физический адрес  = номер кадра    + то же смещение
```

Для учебной страницы 4096 байт адрес `0x1234` — страница `1`, смещение `0x234`. Если страница 1 отображена в кадр `0xA`, физический адрес будет `0xA234`. Это модель перевода, а не способ вручную преобразовать обычный C++-указатель.

**Права** обычно обозначают `r` — чтение, `w` — запись, `x` — исполнение. Не каждый виртуальный адрес отображён; не каждое отображение допускает запись или исполнение.

### Page fault — не обязательно ошибка

При обращении к недоступной странице процессор передаёт управление обработчику ОС. Причиной может быть первое обращение к лениво выделенной странице, чтение отображённого файла, copy-on-write или загрузка выгруженной страницы. Если доступ разрешён, ОС подготавливает страницу и выполнение продолжается. Если адрес недопустим либо права нарушены, Linux обычно посылает `SIGSEGV`.

**ASLR** случайным образом меняет расположение областей между запусками. Поэтому адреса из одного запуска нельзя заучивать как постоянные.

:::remember
**Ответ на сдаче.** Виртуальное адресное пространство — адреса процесса, которые аппаратно переводятся в физические по отображениям, заданным ОС. Оно обеспечивает изоляцию процессов, защиту страниц и гибкое размещение памяти. Его размер не равен объёму RAM; не все адреса доступны. Page fault может быть штатной частью работы виртуальной памяти.
:::

## 2. Сегменты памяти программы. Стек и куча

### Типичная карта процесса

Это **учебная схема Linux/ELF**, а не требование стандарта C++ и не точный чертёж каждого запуска:

```text
Старшие виртуальные адреса
+---------------------------------------+
| Стек потока                     |      |
| обычно растёт к меньшим адресам v      |
+---------------------------------------+
| Отображения библиотек, файлов, mmap    |
| Другие стеки и области аллокаторов    |
+---------------------------------------+
| Свободные / неотображённые промежутки  |
+---------------------------------------+
| Классическая brk-куча           ^      |
| обычно растёт к большим адресам |      |
+---------------------------------------+
| .bss    — нулевые статические данные  |
| .data   — изменяемые заданные данные  |
| .rodata — данные только для чтения    |
| .text   — машинные инструкции         |
+---------------------------------------+
Младшие виртуальные адреса
```

У современного аллокатора много областей; большой `malloc` может получить отдельное отображение вместо участка классической `brk`-кучи. Стек и куча не обязаны быть двумя сплошными областями, которые «растут навстречу до столкновения».

| Область | Что там обычно находится | Типичные права |
|---|---|---|
| `.text` | Машинный код функций | `r-x` |
| `.rodata` | Строковые литералы и некоторые константные данные | `r--` |
| `.data` | Изменяемые глобальные и статические данные с ненулевой инициализацией | `rw-` |
| `.bss` | Глобальные и статические данные с начальным нулём | `rw-` |
| Стек | Кадры вызовов, часть локальных объектов, сохранённые регистры | `rw-` |
| Динамические области | Блоки, которыми управляет аллокатор | `rw-` |

**Секция файла** и **сегмент загрузки** — не одно и то же: ELF-сегмент может объединять несколько секций. Стек, куча и отображения — уже области памяти процесса. В учебной речи всё это часто называют «сегментами памяти», но на уточняющий вопрос нужно различать уровни. Это также не то же самое, что аппаратная сегментация x86.

### Разберём переменные

```cpp
int total = 7;                  // обычно .data
int count;                      // обычно .bss; начальное значение 0

void Work() {
    static int calls = 1;        // статические данные, обычно .data
    int local = 3;              // автоматический объект: стек или регистр
    int* p = new int{9};         // p — локальный указатель; *p — динамический int
    const char* text = "hello";  // text — локальный указатель; литерал — обычно .rodata
    delete p;
}
```

Здесь `p` и `*p` — **два разных объекта**. Класс `std::vector<int>` тоже может быть локальным объектом, а буфер его элементов — динамическим. Нельзя ответить, где находится объект, только по слову «указатель» или по типу класса.

:::warning
`const` не означает «обязательно .rodata». Локальная константа может находиться в стеке, регистре или вообще не иметь отдельной ячейки после оптимизации. Стандарт задаёт поведение, а не обязательное физическое расположение каждой переменной.
:::

### Сравнение стека и кучи

| Вопрос | Стек вызовов | Динамические области, «куча» |
|---|---|---|
| Кто обычно управляет | Код, который сгенерировал компилятор | Аллокатор; вызовы выделения и освобождения |
| Порядок | Вложенные вызовы и блоки | Порядок освобождения произвольный |
| Время жизни | Обычно связано с выходом из блока/функции | Может переживать функцию выделения |
| Цена | Часто достаточно сдвинуть указатель стека | Нужно найти блок, учесть метаданные и синхронизацию |
| Ограничения | Ограниченный размер стека потока | Лимиты адресов, ресурсов и доступных блоков |
| Типичная проблема | Глубокая рекурсия, большой локальный массив | Утечки, фрагментация, use-after-free |

:::remember
**Ответ на сдаче.** Обычно выделяют код, данные только для чтения, инициализированные и нулевые статические данные, стек и динамические области. Стек обслуживает вызовы, куча — выделения с независимым временем освобождения. Конкретная раскладка определяется ОС, ABI, компоновщиком и аллокатором.
:::

## 3. Стек вызовов. Длительность хранения и время жизни объектов

### Стек вызовов и кадр

При вызове функции нужно помнить, куда вернуться, и сохранить данные текущего выполнения. **Кадр стека** — область, связанная с конкретным вызовом. В ней могут быть адрес возврата, сохранённые регистры, локальные данные и часть аргументов. Аргументы и локальные значения также могут находиться в регистрах.

```text
main() вызывает A(), A() вызывает B()

Старшие адреса
    кадр main
    кадр A
    кадр B       <- текущий вызов, стек вырос вниз
Младшие адреса

B вернулась -> продолжается A -> A вернулась -> продолжается main
```

Рекурсивные вызовы имеют отдельные состояния параметров и локальных объектов. При инлайнинге или оптимизации хвостового вызова отдельного машинного кадра может не быть.

### Три разных вопроса об одной переменной

| Понятие | На какой вопрос отвечает |
|---|---|
| **Область видимости** | Где в исходном коде доступно имя? |
| **Длительность хранения** | Как долго существует хранилище для сущности? |
| **Время жизни объекта** | В какой период в хранилище существует именно этот объект? |

В C++ есть четыре категории длительности хранения:

- **Автоматическая**: обычные локальные переменные и параметры; хранилище связано с выполнением блока/вызова.
- **Статическая**: глобальные переменные и локальные `static`; хранилище на всё выполнение программы.
- **Потоковая**: `thread_local`; отдельное хранилище на время работы каждого потока.
- **Динамическая**: например, объекты, создаваемые обычным `new`; хранилище до освобождения.

**Автоматическая длительность не означает требование «лежать на машинном стеке».** Это свойство языка; место выбирает реализация.

Для обычного объекта время жизни начинается, когда есть память нужного размера и выравнивания и завершена инициализация. Для объекта класса оно заканчивается при начале вызова деструктора, либо при освобождении/переиспользовании хранилища; выполнение деструктора регулируется отдельными правилами. [Нормативные определения времени жизни](https://eel.is/c++draft/basic.life).

```cpp
void Tick() {
    static int ticks = 0; // хранилище на всю программу; имя видно только здесь
    int local = ++ticks; // новый local при каждом вызове
    (void)local;
}
```

После выхода из `Tick` имя `ticks` недоступно снаружи, но объект продолжает существовать. Локальный `local` заканчивает жизнь. У локального `static` с нетривиальной динамической инициализацией она выполняется при первом прохождении объявления; не нужно переносить это правило на все глобальные объекты.

### Порядок уничтожения

Обычные локальные объекты уничтожаются в порядке, обратном завершению их конструирования. Это работает при обычном выходе, `return` и раскрутке стека из-за исключения. `std::abort`, принудительное завершение процесса и `std::exit` имеют другие правила; «деструктор вызывается всегда» — неверная формулировка.

```cpp
#include <iostream>

struct Trace {
    char name;
    explicit Trace(char n) : name(n) { std::cout << '+' << name; }
    ~Trace() { std::cout << '-' << name; }
};

int main() {
    Trace a{'A'};
    { Trace b{'B'}; }
    Trace c{'C'};
} // вывод: +A+B-B+C-C-A
```

:::remember
**Ответ на сдаче.** Стек вызовов хранит состояния вложенных вызовов. Длительность хранения относится к хранилищу, время жизни — к объекту, область видимости — к имени. При placement new память может существовать раньше объекта и после его уничтожения.
:::

## 4. Динамическая память: malloc, calloc, realloc, free, new и delete

### Сначала запомним пары

| Получение | Освобождение | Инициализация | Неудача выделения ненулевого размера |
|---|---|---|---|
| `std::malloc(bytes)` | `std::free(p)` | Байты не инициализируются; конструктор не вызывается | `nullptr` |
| `std::calloc(n, size)` | `std::free(p)` | Все биты блока обнуляются; конструктор не вызывается | `nullptr` |
| `std::realloc(p, bytes)` | `std::free(результат)` | Старое начало сохраняется, добавленная часть не инициализируется | `nullptr`, старый блок остаётся |
| `new T(args)` | `delete p` | Инициализация объекта `T` | Обычно исключение `std::bad_alloc` |
| `new T[n]` | `delete[] p` | Инициализация каждого элемента | Обычно исключение `std::bad_alloc` |

`malloc`/`calloc`/`realloc`/`free` объявлены в `<cstdlib>`. Операторы `new`/`delete` встроены в язык; для `std::nothrow`, `std::bad_alloc` и placement new нужен `<new>`.

### malloc и calloc

```cpp
#include <cstdlib>

int main() {
    constexpr std::size_t n = 4;
    int* p = static_cast<int*>(std::malloc(n * sizeof(int)));
    if (p == nullptr) return 1;
    for (std::size_t i = 0; i < n; ++i) p[i] = static_cast<int>(i);
    std::free(p);

    int* zeros = static_cast<int*>(std::calloc(n, sizeof(int)));
    if (zeros == nullptr) return 1;
    // Все int равны 0. Для int все нулевые биты представляют ноль.
    std::free(zeros);
}
```

В C++20 функции выделения могут неявно создавать объекты подходящих **implicit-lifetime** типов, например `int`. Поэтому показанный код с `int` корректен. Но `malloc(sizeof(std::string))` **не вызывает конструктор `std::string`**: использовать такой блок как готовую строку нельзя. [Правила функций выделения в C++](https://eel.is/c++draft/c.malloc).

`calloc` обнуляет **биты**, а не вызывает «конструктор с нулевыми значениями». Представление `nullptr` и вещественного `0.0` не обязано состоять из нулевых битов на любой возможной реализации.

Если `n` приходит извне, до `n * sizeof(T)` проверяют `n <= max_size_t / sizeof(T)`, иначе беззнаковое переполнение может превратить большой запрос в маленький блок. Для слишком выровненных типов обычного `malloc` может быть недостаточно.

### realloc: самый опасный маленький шаблон

Нужно увеличить C-блок с 4 до 8 элементов:

```cpp
#include <cstdlib>

int main() {
    int* p = static_cast<int*>(std::malloc(4 * sizeof(int)));
    if (p == nullptr) return 1;
    for (int i = 0; i < 4; ++i) p[i] = i + 10;

    void* next = std::realloc(p, 8 * sizeof(int));
    if (next == nullptr) {
        std::free(p); // старый блок остаётся нашим
        return 1;
    }
    p = static_cast<int*>(next);
    for (int i = 4; i < 8; ++i) p[i] = 0;
    std::free(p);
}
```

Пошагово:

1. `realloc` пробует изменить блок на месте либо выделить другой и перенести начало.
2. При успехе сохраняются первые `min(старый размер, новый размер)` байт.
3. Работать дальше нужно с **возвращённым указателем**. Старый указатель и указатели внутрь прежнего блока больше не используем, даже если числовой адрес не изменился.
4. При неудаче с положительным размером возвращается `nullptr`; старый блок и его данные остаются.
5. Дополнительная память не обнуляется автоматически.

:::warning
`p = static_cast<int*>(std::realloc(p, bytes));` теряет старый адрес при отказе. Для освобождения используйте `free`, а не `realloc(p, 0)`: правила нулевого размера зависят от версии стандарта и реализации. `realloc(nullptr, положительный_размер)` работает как `malloc`.
:::

Нельзя передавать в `realloc` память от `new`, адрес локальной переменной или середину блока. Нельзя так «переносить» нетривиальные C++-объекты вроде `std::string`: побайтовое перемещение не заменяет их конструкторы перемещения.

### new: память плюс инициализация

```cpp
int* a = new int;          // int не инициализирован: до записи не читать
int* b = new int{};        // int равен 0
int* c = new int{42};      // int равен 42
int* d = new int[3];       // три int без заданных значений
int* e = new int[3]{};     // три нуля
int* f = new int[3]{1, 2}; // 1, 2, 0

delete a;
delete b;
delete c;
delete[] d;
delete[] e;
delete[] f;
```

Для класса `new T` вызывает подходящий конструктор по умолчанию, если он доступен. Поэтому утверждение «`new T` никогда не инициализирует» неверно: оно зависит от `T`.

Обычное new-выражение получает память через функцию выделения `operator new`, затем инициализирует объект. Если конструктор бросит исключение, соответствующее освобождение памяти выполняется автоматически. `delete` сначала вызывает деструктор, затем освобождает хранилище. [Описание new-выражения](https://eel.is/c++draft/expr.new).

```cpp
#include <new>

int* p = new (std::nothrow) int{7};
if (p == nullptr) {
    // Не удалось именно выделение памяти.
}
delete p;
```

`std::nothrow` меняет способ сообщения об **ошибке выделения**; исключения из конструктора класса всё ещё могут выйти наружу.

### Что нужно сказать про delete[]

- `new T` сочетается с `delete`, а `new T[n]` — с `delete[]`, даже если `n == 1` или `T` — `int`.
- `delete[]` уничтожает элементы в обратном порядке; реализация сама обеспечивает знание, сколько элементов уничтожить. Служебный счётчик перед блоком — возможная реализация, не гарантия языка.
- `delete nullptr`, `delete[] nullptr` и `free(nullptr)` безопасны. Это не разрешает освобождать один живой адрес дважды.
- Ни `delete`, ни `free` не присваивают переменной указателя `nullptr`.
- Освобождение обычно возвращает блок аллокатору; оно не обещает немедленно уменьшить занятую RAM процесса.

:::remember
**Ответ на сдаче.** C-функции управляют сырым хранилищем и не вызывают конструкторы/деструкторы классов. New-выражение выделяет память и инициализирует объект; delete уничтожает и освобождает. Семейства нельзя смешивать. Для realloc обязательно сохранить старый указатель до проверки результата.
:::

## 5. Placement new

### Создать объект в уже имеющемся месте

Обычный `new` отвечает сразу на два вопроса: «где взять память?» и «как создать объект?». Стандартный **placement new** получает адрес уже подготовленной памяти и создаёт объект **там**.

:::note
**Простыми словами.** Обычный new арендует помещение и обставляет его. Placement new обставляет помещение, которое уже есть. Уничтожить обстановку и вернуть помещение владельцу — две отдельные операции.
:::

```cpp
#include <iostream>
#include <new>

struct Point {
    int x;
    explicit Point(int value) : x(value) { std::cout << "construct\n"; }
    ~Point() { std::cout << "destroy\n"; }
};

int main() {
    alignas(Point) unsigned char buffer[sizeof(Point)];
    Point* p = ::new (static_cast<void*>(buffer)) Point{42};
    std::cout << p->x << '\n';
    p->~Point();
    // delete p; // UB: buffer не получен обычным new
} // вывод: construct, 42, destroy — на отдельных строках
```

**Размер** `sizeof(Point)` — сколько места нужно. **Выравнивание** `alignas(Point)` — требование к начальному адресу. Достаточного размера без правильного выравнивания мало. Для чтения используем указатель, возвращённый placement new; это также избавляет от ряда тонкостей повторного использования старых указателей.

Временная линия:

```text
buffer существует: [-----------------------------------------]
Point существует:         [-------------------]
                     placement new        ~Point()
```

После `p->~Point()` буфер остаётся, но обращаться к полям прежнего `Point` нельзя. В это хранилище можно корректно создать следующий объект. При выходе из блока буфер исчезает сам; он не отслеживает, лежит ли в нём объект, которому нужен деструктор.

Если сырой блок был получен через `malloc`, последовательность другая: `malloc` → placement new → работа → явный деструктор → `free`. `delete` и здесь не заменяет `free`.

Применение: контейнеры с резервной ёмкостью, пулы объектов, собственные аллокаторы. `vector` может иметь память на 100 элементов, хотя реально сконструировано только 10: **ёмкость и число живых объектов различаются**.

:::remember
**Ответ на сдаче.** Стандартный placement new создаёт объект по заданному адресу без выделения нового блока. Вызывающий обеспечивает размер, выравнивание и допустимость хранилища, затем отдельно организует уничтожение объекта и освобождение самого хранилища.
:::

## 6. Ошибки работы с памятью

### Сначала классифицируем, потом пытаемся «угадать вывод»

**UB**, undefined behavior, — неопределённое поведение: стандарт не задаёт результат выполнения. Это не «случайное число» и не обещание падения. **Ошибка компиляции** обнаруживается до запуска. **Утечка** — потеря ресурса; сама по себе она не обязана быть UB.

| Ошибка | Минимальный пример | Почему плохо |
|---|---|---|
| Чтение до инициализации | `int x; int y = x;` | Для такого `int` в C++20 — UB |
| Выход за границы | `int a[3]{}; a[3] = 1;` | Нет элемента с индексом 3 |
| Нулевой указатель | `int* p = nullptr; *p = 1;` | Нет объекта для записи |
| Use-after-free | `delete p;` затем чтение `*p` | Объект уже уничтожен |
| Double free | Дважды освобождён один блок | Блок уже не принадлежит вызывающему |
| Смешанные семейства | `new int[3]` и `free(p)` | Нарушены правила освобождения |
| Висячая ссылка | Возврат ссылки на локальную переменную | Ссылка пережила объект |
| Неверное выравнивание | Создание `T` по неподходящему адресу | Нарушено требование типа |
| Переполнение размера | `n * sizeof(T)` переполнилось | Выделено меньше, чем ожидает код |
| Утечка | Потерян последний способ освободить блок | Ресурс не возвращён |

### Обнуление одного указателя не исправляет остальные

```cpp
int* owner = new int{42};
int* observer = owner;
delete owner;
owner = nullptr;
// int x = *observer; // UB: observer остался висячим
```

Аналогично, ссылка на элемент `vector` может стать висячей после операции, перераспределившей буфер. Время жизни локальной переменной-указателя не продлевает время жизни объекта по её адресу.

### Утечка и RAII

```cpp
void Leak() {
    int* p = new int{42};
    p = nullptr; // адрес потерян, delete сделать уже нечем
}
```

**RAII** — Resource Acquisition Is Initialization: ресурсом владеет объект, который получает его при создании и освобождает в деструкторе. Для динамического массива обычно нужен `std::vector<T>`, для единственного владельца объекта — `std::unique_ptr<T>`.

```cpp
#include <memory>
#include <vector>

void Safe() {
    auto value = std::make_unique<int>(42);
    std::vector<int> data(100, 0);
} // владельцы освобождают ресурсы, в том числе при исключении
```

Знать raw new/delete нужно для понимания механики. В прикладном коде автоматическое владение уменьшает число путей, на которых можно забыть освобождение.

### Чем проверять

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g -O1 \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  example.cpp -o example
./example
```

ASan помогает находить выходы за границы и use-after-free; UBSan — часть других нарушений. Поиск утечек зависит от платформы и настроек. Чтение неинициализированной памяти требует других средств, например MemorySanitizer в поддерживаемом окружении: ASan не ловит его в общем случае. Санитайзеры проверяют выполненные пути и не являются доказательством корректности.

ОС защищает **страницы**, а не границы каждого массива. Поэтому UB может не вызвать `SIGSEGV`; верный вывод при одном запуске не делает код верным.

:::remember
**Ответ на сдаче.** Основные ошибки — неправильные границы, время жизни, инициализация, владение и парность выделения/освобождения. Для UB нельзя предсказывать результат по одному запуску. Утечки предотвращают ясным владением и RAII, ошибки доступа ищут предупреждениями, тестами и санитайзерами.
:::

## 7. Ссылки и константные ссылки. Отличия от указателей

### Ссылка — другое имя, указатель — отдельный объект

```cpp
int a = 10;
int b = 20;
int& r = a;
int* p = &a;

r = b;   // a стало 20; r всё ещё обозначает a
p = &b;  // теперь p указывает на b
```

| Свойство | `T&` | `T*` |
|---|---|---|
| Связывание | Нужно инициализировать при определении | Можно присвоить адрес позже, но до чтения |
| «Нет объекта» | Корректного нулевого состояния нет | `nullptr` |
| Смена цели | Перепривязать нельзя | Можно, если сам указатель не `const` |
| Доступ к объекту | `r`, `r.member` | `*p`, `p->member` |
| Арифметика | `r + 1` — операция над объектом | `p + 1` — переход к следующему элементу массива |
| Адрес | `&r` — адрес объекта, на который ссылаемся | `&p` — адрес самого указателя |
| Владение | Сама не освобождает объект | Сам по себе raw-указатель тоже не освобождает |

`sizeof(r)` даёт размер типа объекта, а не размер скрытого механизма ссылки. Реализация может хранить ссылку похожим на указатель способом, но язык не требует отдельной ячейки для каждой ссылки. Массивов ссылок и указателей непосредственно на ссылку нет.

### Что именно запрещает const

```cpp
int x = 1;
const int& read = x;
x = 2;             // допустимо: read теперь тоже видит 2
// read = 3;       // ошибка компиляции

const int* p = &x; // нельзя менять x через p; можно менять p
int* const q = &x; // можно менять x через q; нельзя менять q
```

`const T&` ограничивает изменение **через эту ссылку**. Это не заморозка объекта для всего приложения. `T& const` записать нельзя: сама ссылка и так не перепривязывается.

Неконстантная lvalue-ссылка обычно связывается с подходящим изменяемым lvalue — например, именованной переменной. `const T&` также может связываться с временным объектом:

```cpp
int n = 3;
int& a = n;
const int& b = 42;    // допустимо, временный int живёт вместе с b
// int& c = 42;      // ошибка компиляции
const double& d = n; // создаётся временный double со значением 3
n = 9;               // d остаётся равным 3.0: это не ссылка на n
```

:::warning
«Ссылка не может быть нулевой» не означает «ссылка всегда безопасна»: она может стать висячей после уничтожения объекта. Попытка получить ссылку через разыменование `nullptr` уже нарушает правила.
:::

:::remember
**Ответ на сдаче.** Ссылка — не перепривязываемый псевдоним объекта. Указатель — самостоятельное значение адресного типа с возможным nullptr. Константная ссылка запрещает изменение через неё и может привязаться к временному объекту; она не владеет произвольным объектом и не гарантирует его вечную жизнь.
:::

## 8. Передача аргументов, возврат значений и временные объекты

### Какой интерфейс выбрать

| Параметр | Что получает функция | Когда использовать |
|---|---|---|
| `int value` | Своё значение | Небольшой входной объект |
| `T value` | Отдельный объект, скопированный/перемещённый/созданный на месте | Функции нужна своя версия объекта |
| `T& value` | Доступ к исходному объекту с изменением | Изменяемый обязательный аргумент |
| `const T& value` | Доступ без изменения через параметр | Чтение большого объекта без копии |
| `T* value` | Копию указателя | Отсутствие объекта допустимо или нужен указательный интерфейс |
| `const T* value` | Копию адреса с доступом только для чтения | Необязательный входной объект |

**Указатель тоже передаётся по значению**, если параметр имеет тип `T*`: можно изменить объект через него, но переприсваивание самого параметра не изменит указатель вызывающего кода.

```cpp
void ResetLocal(int* p) { p = nullptr; } // меняется лишь копия адреса
void ResetCaller(int*& p) { p = nullptr; } // меняется указатель вызывающего
```

`ResetCaller` не освобождает объект: обнулить единственный владеющий указатель таким способом — получить утечку. Для передачи владения лучше `std::unique_ptr<T>`.

### Что возвращать

```cpp
std::string MakeName() {
    return std::string{"M3102"}; // корректный возврат по значению
}

int& First(int (&a)[3]) {
    return a[0]; // корректно, пока живёт переданный массив
}

int* BadPointer() {
    int local = 7;
    return &local; // возвращает висячий указатель; разыменование после вызова — UB
}
```

Возврат **по значению** создаёт результат, которым владеет вызывающая сторона. Для однотипного prvalue, как в `MakeName`, C++17 и новее гарантирует построение результата без промежуточного копирования. Для `T local; return local;` возможна NRVO; она не гарантирована в общем случае. Поэтому «возврат большого объекта всегда дорогой» — плохое правило.

Возврат ссылки/указателя не создаёт владения: нужно доказать, что цель продолжает жить. Ссылка на элемент контейнера дополнительно зависит от операций, инвалидирующих ссылки.

### Когда умирает временный объект

По умолчанию — в конце **полного выражения**, часто у точки с запятой:

```cpp
void Show(const std::string& s) {
    // s можно читать здесь, но нельзя сохранять для использования позже
}

Show(std::string{"hello"}); // временная строка жива весь вызов; затем уничтожается
```

Прямая привязка локальной `const T&` к временному объекту может продлить его жизнь до конца жизни ссылки. Но продление не «передаётся» следующей ссылке. [Правила временных объектов в проекте C++20](https://timsong-cpp.github.io/cppwp/n4861/class.temporary).

```cpp
const std::string& Echo(const std::string& s) { return s; }

void Demo() {
    const std::string& a = std::string{"long"}; // живёт до конца жизни a
    const std::string& b = Echo(std::string{"short"});
    // После предыдущей ; временная "short" уже уничтожена. b — висячая.
    // std::cout << b; // UB
}
```

| Ситуация | Сколько живёт временный объект |
|---|---|
| `const std::string& r = std::string{"x"};` | До конца жизни локальной ссылки `r` |
| `Show(std::string{"x"});` | До конца полного выражения с вызовом |
| Возвращаем ссылку-параметр, связанную с временным | Возврат ссылки не добавляет времени жизни |
| В C++20 функция возвращает `const T&`, привязанную к `T{}` в `return` | Временный уничтожается при завершении полного выражения в return; результат — висячая ссылка |
| `new Holder{std::string{"x"}}`, где у Holder поле `const std::string&` | До конца выражения с new; поле становится висячим |

Последняя строка важна: динамический объект `Holder` может жить долго, а временная строка — уже нет. Квалификатор `const` сам по себе ничего не продлевает; важен **контекст привязки**. Правила возврата ссылки непосредственно на временный объект ужесточены в C++26; здесь разбирается C++20.

### auto может убрать ссылочность

```cpp
int x = 1;
int& r = x;
auto copy = r;   // int, отдельный объект
auto& alias = r; // int&, другое имя x
copy = 5;       // x не меняется
alias = 7;      // x становится 7
```

:::remember
**Ответ на сдаче.** Передача по значению даёт отдельный параметр, по ссылке — доступ к исходному объекту. Возвращать локальный объект по значению безопасно, ссылку или адрес на него — опасно. Временный обычно живёт до конца полного выражения; продление жизни ссылкой действует только в предусмотренных контекстах и не передаётся через возврат другой ссылки.
:::

## 9. Перегрузка функций

**Перегрузки** — функции с одним именем и разными списками параметров. При обычном вызове компилятор выбирает подходящую перегрузку по типам и допустимым преобразованиям аргументов.

```cpp
const char* Kind(int) { return "int"; }
const char* Kind(double) { return "double"; }

Kind(3);    // int
Kind(3.0);  // double
Kind('a');  // int: продвижение char -> int лучше преобразования char -> double
Kind(3.0F); // double: продвижение float -> double
```

Для обычных числовых примеров полезный порядок: **точное совпадение → promotion (продвижение) → другое стандартное преобразование → пользовательское преобразование**. Это не полный алгоритм: при нескольких аргументах кандидат должен быть не хуже по всем и лучше хотя бы по одному; дополнительные правила также учитывают ссылки, квалификаторы и шаблоны.

```cpp
void F(int, double);
void F(double, int);
// F(1, 1); // ошибка компиляции: каждая лучше по одному аргументу
```

### Что различает перегрузки

| Пара объявлений | Результат |
|---|---|
| `void F(int); void F(double);` | Разные перегрузки |
| `void F(int); void F(int, int);` | Разные перегрузки |
| `int F(int); double F(int);` | Ошибка: один возвращаемый тип не различает функции |
| `void F(int); void F(const int);` | Одна функция: верхнеуровневый const параметра-значения не различает |
| `void F(int*); void F(const int*);` | Разные перегрузки: различается доступ к объекту по адресу |
| `void F(int&); void F(const int&);` | Разные перегрузки |
| `void F(int[]); void F(int*);` | Одна функция: параметр-массив корректируется до указателя |

В паре `F(int&)`/`F(const int&)` изменяемая переменная `int` выбирает первую, константная переменная и временный `int` — вторую.

### Неоднозначность не решается «похожестью чисел»

```cpp
void Print(int);
void Print(float);
// Print(2.5); // ошибка: double -> int и double -> float, ни одно не лучше
Print(2.5F);   // float, точное совпадение
```

`nullptr` безопаснее старого `NULL`, но не выбирает произвольный указательный тип:

```cpp
void Find(int*);
void Find(double*);
// Find(nullptr); // неоднозначность
Find(static_cast<int*>(nullptr)); // выбрана версия int*
```

:::remember
**Ответ на сдаче.** Перегрузка разрешается во время компиляции: формируются кандидаты, отбрасываются неподходящие и выбирается единственная лучшая функция. Если лучшей нет — ошибка компиляции. Одного возвращаемого типа и верхнеуровневого const параметра-значения недостаточно для новой перегрузки.
:::

## 10. Аргументы функций по умолчанию

```cpp
// В заголовке:
void Draw(int width, int height = 100, bool filled = false);

// В файле реализации значения повторять не нужно:
void Draw(int width, int height, bool filled) {
    // ...
}

// В месте, где видно первое объявление:
// Draw(20);          эквивалентно Draw(20, 100, false)
// Draw(20, 30);      эквивалентно Draw(20, 30, false)
// Draw(20, 30, true)
```

Аргументы можно пропускать **с конца**, а не из середины. Для обычных функций после параметра с default-аргументом остальные должны иметь default-аргументы, заданные здесь или в уже видимом объявлении той же области. Повторять уже заданное значение нельзя, даже если оно такое же. [Правила default-аргументов](https://eel.is/c++draft/dcl.fct.default).

### Это не дополнительная функция

```cpp
void F(int);
void F(int, int = 0);
// F(1); // ошибка: подходят обе, default не делает вторую хуже
```

Значения по умолчанию должны быть видны **в точке вызова**. Они не входят в тип функции:

```cpp
void Log(int level = 1);
void (*p)(int) = Log;
// p(); // ошибка: указатель имеет тип функции с одним обязательным int
p(1);
```

### Выражение вычисляется при каждом таком вызове

```cpp
int counter = 0;
int Next() { return ++counter; }
int Value(int x = Next()) { return x; }

// Value() вернёт 1, следующий Value() — 2, Value(9) — 9 и Next не вызовет.
```

Не нужно думать, что результат `Next()` вычисляется один раз при объявлении. При этом поиск имён в default-выражении и его вычисление — разные этапы: имена связываются в контексте объявления.

:::remember
**Ответ на сдаче.** Default-аргументы подставляются для пропущенных правых аргументов по видимым объявлениям. Они не меняют тип функции и не создают перегрузки; их выражения вычисляются, когда соответствующий аргумент понадобился при вызове.
:::

## 11. Инициализация и присваивание. Виды инициализации

**Инициализация** задаёт состояние при создании объекта. **Присваивание** работает с уже существующим объектом. Наличие `=` само по себе ничего не решает:

```cpp
std::string a = "first"; // инициализация
std::string b = a;       // инициализация: конструктор копирования
b = a;                  // присваивание: operator=
```

### Формы записи и последствия

| Запись | Название / результат |
|---|---|
| `int a;` внутри функции | Default-initialization: значение int не задано |
| `int a{};` | Пустая list-initialization приводит к value-initialization: 0 |
| `int a = 7;` | Copy-initialization |
| `int a(7);` | Direct-initialization |
| `int a{7};` | Direct-list-initialization |
| `int a = {7};` | Copy-list-initialization |
| `int a[3]{1, 2};` | Aggregate initialization: 1, 2, 0 |
| `static int a;` | Статическая нулевая инициализация: 0 |
| `new int()` | Value-initialization: 0 |
| `new int` | Default-initialization: значение не задано |

Названия частично пересекаются: list-initialization описывает синтаксис, а aggregate/value-initialization — то, что по этому синтаксису происходит для данного типа. `int a();` — **объявление функции**, а не нулевой `int`. [Формальные категории инициализации](https://eel.is/c++draft/dcl.init).

### Фигурные скобки запрещают сужение, но не все опасности

```cpp
double d = 3.8;
int a = d;     // допустимо: 3, если значение представимо
// int b{d};  // ошибка компиляции: narrowing
int c{static_cast<int>(d)}; // явное намерение преобразовать
```

Преобразование вещественного числа, чья целая часть не представима в целевом целом типе, — отдельная опасность; запись через `=` не делает его безопасным.

### Для классов () и {} могут означать разное

```cpp
std::vector<int> a(3, 7); // три элемента: 7, 7, 7
std::vector<int> b{3, 7}; // два элемента: 3, 7; выбран initializer_list
```

Конструкторы с `std::initializer_list` получают приоритет в предусмотренных правилами list-initialization случаях. Поэтому совет «всегда заменить круглые скобки фигурными» может изменить программу.

Пустые `{}` не гарантируют нулевые поля **произвольного класса**:

```cpp
struct S {
    int x;
    S() {} // пользовательский конструктор не инициализирует x
};
S s{};
// s.x читать нельзя: конструктор оставил поле без значения
```

Вместо этого поле можно объявить `int x = 0;` или инициализировать списком конструктора.

### explicit

```cpp
struct Count {
    explicit Count(int value) : value(value) {}
    int value;
};

Count a(3);      // допустимо
Count b{3};      // допустимо
// Count c = 3; // ошибка: explicit запрещает это неявное преобразование
```

:::remember
**Ответ на сдаче.** Инициализация создаёт начальное состояние, присваивание меняет существующее. Различают default-, value-, copy-, direct-, list- и aggregate initialization. Для скаляров пустые {} дают ноль, но поведение классов зависит от конструктора; {} также запрещают narrowing и могут выбрать initializer_list.
:::

## 12. Работа с файлами

### Два интерфейса — общий принцип

Файл открывают, проверяют успех, читают/пишут с проверкой результата и закрывают. Сишный интерфейс из `<cstdio>` использует `FILE*`; C++-потоки из `<fstream>` — объекты с автоматическим управлением ресурсом.

| Режим fopen | Смысл |
|---|---|
| `"r"` | Чтение существующего файла |
| `"w"` | Запись: создать или **обрезать существующий** |
| `"a"` | Запись в конец: создать, если нет |
| `"r+"` | Чтение и запись существующего |
| `"w+"` | Чтение и запись с созданием/обрезкой |
| `"a+"` | Чтение и запись с добавлением в конец |
| Суффикс `b`: `"rb"`, `"wb"` | Бинарный режим, без текстовых преобразований |

Для BMP нужен бинарный режим. В Windows текстовый режим может преобразовывать окончания строк; в POSIX различия обычно нет, но переносимый код всё равно пишет `b`.

### fread и fwrite считают элементы

```cpp
std::size_t n = std::fread(buffer, element_size, count, file);
```

`n` — число **полностью прочитанных элементов**, не обязательно байтов. Для сырого буфера удобен `element_size == 1`: тогда результат выражен в байтах. Нельзя обработать весь размер буфера, если прочитана только часть.

```cpp
#include <cstdio>

int main() {
    std::FILE* file = std::fopen("input.bin", "rb");
    if (file == nullptr) return 1;

    unsigned char buffer[4096];
    std::size_t n;
    while ((n = std::fread(buffer, 1, sizeof(buffer), file)) != 0) {
        // Обработать ровно n байт: buffer[0] ... buffer[n - 1].
    }
    bool failed = std::ferror(file) != 0;
    if (std::fclose(file) != 0) failed = true;
    return failed ? 1 : 0;
}
```

Короткое чтение может означать конец файла или ошибку; различаем через `feof`/`ferror`. `while (!feof(file))` — неверная схема: признак EOF выставляется **после попытки чтения**, а не заранее.

При `fgetc` результат хранится в **int**: нужно различать все значения `unsigned char` и специальное `EOF`. При `fwrite` проверяют количество записанных элементов. Ошибка записи может проявиться позже при сбросе буфера или `fclose`, поэтому успешного `fwrite` недостаточно для гарантии успеха всей операции.

### Позиция и буферизация

- `fseek(file, offset, SEEK_SET)` смещает относительно начала; `SEEK_CUR` — текущей позиции; `SEEK_END` — конца. Возвращает 0 при успехе.
- `ftell` возвращает позицию либо `-1L` при ошибке. Для текстового файла результат не нужно трактовать как произвольное число байт; есть ограничения на допустимые смещения.
- Тип `long` ограничивает переносимость операций с очень большими файлами; для них используют подходящие платформенные или потоковые интерфейсы.
- `fflush` сбрасывает пользовательский буфер выходного потока в нижележащую систему; это не обещание физической записи на накопитель.
- В `r+`/`w+` при смене чтения и записи нужны предусмотренные стандартом операции позиционирования/сброса. Нельзя бездумно чередовать их.

### C++-потоки

```cpp
#include <fstream>
#include <string>

int main() {
    std::ifstream in("numbers.txt");
    if (!in) return 1;
    int value;
    while (in >> value) {
        // Обрабатываем только успешно прочитанное value.
    }
    if (in.bad() || (in.fail() && !in.eof())) return 1;

    std::ofstream out("answer.txt");
    if (!out) return 1;
    out << "done\n";
    out.close(); // закрываем явно, чтобы успеть проверить ошибку
    return out ? 0 : 1;
}
```

Для чтения строк — `std::getline(in, line)`. После `in >> number` в потоке может оставаться перевод строки: следующий `getline` прочитает пустой остаток. Для бинарных данных — `read`/`write`, для проверки числа прочитанных байт — `gcount()`. Само открытие с `std::ios::binary` **не делает** `<< 123` записью двоичного представления int: форматирование остаётся текстовым.

:::remember
**Ответ на сдаче.** Проверяю открытие, результат каждой операции и завершение записи. fread/fwrite возвращают число элементов; EOF узнаётся из результата чтения, а не предсказывается. Текстовый и бинарный режимы различаются преобразованиями, а формат данных выбирает сама программа. Потоковые объекты закрывают файл в деструкторе, но ошибки записи лучше проверить явно.
:::

## 13. BMP-файлы

### Выберем конкретный вариант формата

BMP — семейство форматов. Для начала разбираем **Windows BMP: BITMAPFILEHEADER + BITMAPINFOHEADER, 24 бита на пиксель, BI_RGB без сжатия**. Палитровые, RLE, bitfields и V4/V5 требуют дополнительных правил; этот разбор не универсальный декодер. [Общая структура BMP](https://learn.microsoft.com/en-us/windows/win32/gdi/bitmap-storage).

```text
Смещение 0                    14                          bfOffBits
          | заголовок файла    | DIB-заголовок и доп.данные | пиксели ... |
          | BITMAPFILEHEADER   | BITMAPINFOHEADER ...      |            |
```

### Какие поля знать

Смещения указаны **от начала файла**, для выбранного 40-байтного DIB-заголовка; многобайтовые числа — little-endian.

| Смещение | Байты | Поле | Смысл |
|---|---|---|---|
| 0 | 2 | `bfType` | Сигнатура: байты `42 4D`, то есть `BM` |
| 2 | 4 | `bfSize` | Заявленный размер файла |
| 6 и 8 | по 2 | `bfReserved1/2` | Резерв, нули |
| 10 | 4 | `bfOffBits` | Смещение начала массива пикселей |
| 14 | 4 | `biSize` | Размер DIB-заголовка: здесь 40 |
| 18 | 4 | `biWidth` | Знаковая ширина; здесь принимаем только > 0 |
| 22 | 4 | `biHeight` | Знаковая высота: знак задаёт ориентацию |
| 26 | 2 | `biPlanes` | Должно быть 1 |
| 28 | 2 | `biBitCount` | Здесь 24 |
| 30 | 4 | `biCompression` | Здесь 0 (`BI_RGB`) |
| 34 | 4 | `biSizeImage` | Размер пиксельных данных; для BI_RGB может быть 0 |

Поля заголовков описаны в [BITMAPFILEHEADER](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapfileheader) и [BITMAPINFOHEADER](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapinfoheader). **Не заучивайте «пиксели всегда с байта 54»**: это лишь 14 + 40 для простого файла без промежуточных данных. Авторитетное поле — `bfOffBits`.

### Цвет, строки и padding

Для выбранного 24-битного варианта каждый пиксель занимает 3 байта в порядке **B, G, R**, а не R, G, B. Например, красный — `00 00 FF`. [Порядок компонент BGR](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-rgbtriple).

Размер каждой строки на диске округлён вверх до кратного 4 байтам:

```text
rowBytes = width * 3
stride   = ((rowBytes + 3) / 4) * 4    // целочисленное деление
padding  = stride - rowBytes
imageBytes = stride * abs(height)
```

Для общей битности формула — `((width * bitsPerPixel + 31) / 32) * 4`, когда она применима к данному несжатому варианту. Padding — добавка **в конце строки**, не после каждого пикселя. Вычисления нужно выполнять в достаточно широком типе с проверкой переполнения.

**Пример:** ширина 3, высота 2, 24 bpp. Полезная строка — 9 байт, stride — 12, padding — 3. Пиксельный массив — 24 байта. При `bfOffBits = 54` минимальный размер этого файла — 78 байт.

### Какая строка первая

- `biHeight > 0`: **bottom-up**, первой в файле лежит нижняя строка.
- `biHeight < 0`: **top-down**, первой лежит верхняя строка для выбранного несжатого формата.
- Внутри строки пиксели идут слева направо.

Если координата `y = 0` у нас обозначает верхнюю строку, то:

```text
H = модуль высоты, вычисленный безопасно в широком типе
fileRow = height > 0 ? H - 1 - y : y
offset = bfOffBits + fileRow * stride + x * 3
```

Не вычисляйте `abs(INT32_MIN)` в 32-битном знаковом типе: положительный результат в нём не представим. Сначала расширьте тип и проверьте допустимость размеров.

### Почему нельзя просто fread в struct

В структуре C++ могут быть выравнивающие промежутки (**padding**); её `sizeof` не обязан совпадать с размером заголовка на диске. Дополнительно влияют размеры типов и endianness. `#pragma pack` зависит от реализации и не решает вопрос порядка байтов.

Надёжная учебная схема — читать байты и явно собирать числа:

```cpp
#include <cstdint>

std::uint32_t ReadLE32(const unsigned char* b) {
    // Предусловие: b указывает как минимум на 4 доступных байта.
    return std::uint32_t{b[0]}
         | (std::uint32_t{b[1]} << 8)
         | (std::uint32_t{b[2]} << 16)
         | (std::uint32_t{b[3]} << 24);
}
```

Приведение к беззнаковому 32-битному типу делается **до** сдвига. Знаковую высоту в C++20 можно восстановить как `std::bit_cast<std::int32_t>(ReadLE32(...))` из `<bit>`, если эти типы доступны; BMP предполагает 8-битные байты.

### Порядок проверок загрузчика

1. Открыть в бинарном режиме; убедиться, что заголовок прочитан полностью.
2. Проверить сигнатуру, размер DIB, planes, битность и compression. Неподдерживаемый вариант явно отклонить.
3. Проверить ширину, высоту, ограничения размера изображения.
4. Без переполнений вычислить stride и число пиксельных байт.
5. Убедиться, что `bfOffBits` не указывает внутрь обязательных заголовков и что нужные данные помещаются в **реальном** файле. Заявленные размеры не считать доказательством.
6. Читать строки с учётом ориентации, BGR и padding; проверять короткое чтение.

:::remember
**Ответ на сдаче.** Для 24-битного BI_RGB BMP нужно разобрать заголовки, взять bfOffBits, читать BGR-пиксели, учитывать выравнивание строк до 4 байт и знак высоты. Структура в памяти не равна формату файла; размеры и границы проверяются до выделения и обращения к данным.
:::

## 14. Классы

### Тип, данные и допустимые действия

**Класс** — пользовательский тип, который объединяет данные и операции над ними. **Объект** — конкретный экземпляр этого типа. **Инкапсуляция** позволяет защитить внутреннее состояние и поддерживать **инвариант** — условие, которое должно сохраняться для корректного объекта.

```cpp
#include <stdexcept>

class Counter {
public:
    explicit Counter(int initial = 0) : value_(initial) {
        if (initial < 0) throw std::invalid_argument("negative counter");
    }

    void Reset() { value_ = 0; }
    int Value() const { return value_; }

private:
    int value_;
};

int main() {
    Counter c{5};
    c.Reset();
    const Counter fixed{3};
    int n = fixed.Value();
    (void)n;
    // fixed.Reset(); // ошибка: метод не const
    // c.value_ = -1; // ошибка: private
}
```

Здесь инвариант — `value_ >= 0`. `private` не шифрует память, а ограничивает доступ в программе. `public` задаёт интерфейс; `protected` доступен классу и наследникам. У `class` доступ по умолчанию private, у `struct` — public; также различается доступ наследования по умолчанию. Остальные возможности у них в основном общие.

### Конструктор, список инициализации и деструктор

Конструктор не имеет возвращаемого типа и создаёт начальное состояние. Деструктор `~T()` выполняет завершающие действия; он также не имеет возвращаемого типа и не принимает обычных аргументов.

```cpp
class Pair {
    const int first_;
    int second_;
public:
    Pair(int a, int b) : first_(a), second_(b) {}
};
```

Список после `:` **инициализирует поля до тела конструктора**. Присваивание в теле происходит позже и не подходит для начальной установки ссылки или `const`-поля. Поля инициализируются **в порядке объявления в классе**, независимо от порядка в списке; уничтожаются в обратном. Базовые подобъекты создаются до полей.

### this, const-методы и static

В обычном нестатическом методе `this` — указатель на текущий объект; `this->value_` обращается к его полю. Метод `Value() const` обещает не менять обычные поля через этот объект и может вызываться для `const Counter`. Это не обещание абсолютной чистоты функции: существуют `mutable`, внешнее состояние и объекты по указателям.

`static`-поле относится ко всему классу, а не к каждому экземпляру. `static`-метод не имеет `this` и вызывается без конкретного объекта. Код методов не копируется внутрь каждого экземпляра.

### Копирование и владение

```cpp
class BrokenBuffer {
public:
    BrokenBuffer() : data_(new int[4]{}) {}
    ~BrokenBuffer() { delete[] data_; }
private:
    int* data_;
};

// BrokenBuffer a;
// BrokenBuffer b = a;
// Ошибка конструкции класса: неявное копирование копирует только адрес.
// При уничтожении a и b один блок будет освобождён дважды — UB.
```

**Правило трёх**: если класс сам управляет ресурсом и требует особого деструктора, обычно нужно определить или запретить также копирующий конструктор и копирующее присваивание. **Правило пяти** добавляет перемещающий конструктор и перемещающее присваивание. Это рекомендации проектирования, а не команда «обязательно написать пять методов вручную».

**Правило нуля**: поручить владение готовым типам, чтобы специальные методы класса работали автоматически:

```cpp
#include <vector>

class Buffer {
public:
    explicit Buffer(std::size_t n) : data_(n, 0) {}
    std::size_t Size() const { return data_.size(); }
private:
    std::vector<int> data_;
}; // копирование, перемещение и освобождение обеспечивает vector
```

Копирование `vector` копирует элементы, копирование raw-указателя — только адрес. `unique_ptr` запрещает копирование и позволяет перемещение, передающее владение.

Если объект производного класса удаляют через указатель на базовый, деструктор базового класса должен быть виртуальным. Это отдельное правило полиморфного владения, а не требование «любой деструктор всегда virtual».

:::remember
**Ответ на сдаче.** Класс задаёт тип, состояние и интерфейс, конструктор устанавливает инвариант, деструктор освобождает принадлежащие ресурсы. Важно различать инициализацию полей и присваивание, учитывать порядок полей и корректно определять копирование владельцев. Предпочтителен RAII и правило нуля.
:::

## 15. GTest — GoogleTest

### Что проверяет тест

GoogleTest — библиотека тестирования C++. **Тест** создаёт условия, вызывает проверяемый код и сопоставляет результат с ожидаемым. **Test suite** объединяет тесты; **fixture** готовит повторяющееся окружение. Тесты должны быть независимыми: порядок запуска не должен менять результат. [Введение GoogleTest](https://google.github.io/googletest/primer.html).

```cpp
#include <gtest/gtest.h>

int Add(int a, int b) { return a + b; }

TEST(AddTest, AddsPositiveNumbers) {
    EXPECT_EQ(Add(2, 3), 5);
}

TEST(AddTest, HandlesZero) {
    EXPECT_EQ(Add(0, 0), 0);
}
```

`TEST(SuiteName, TestName)` объявляет и регистрирует тест. Передача программы через успешную компиляцию не проверяет её результат; успешный тест проверяет только заложенные в него случаи.

### EXPECT и ASSERT

| Макрос | Что проверяет |
|---|---|
| `EXPECT_EQ(a, b)` | Равенство значений |
| `EXPECT_NE(a, b)` | Неравенство |
| `EXPECT_TRUE(condition)` | Истинность |
| `ASSERT_NE(p, nullptr)` | Не nullptr, иначе завершить текущую функцию |
| `EXPECT_STREQ(a, b)` | Содержимое двух C-строк |
| `EXPECT_DOUBLE_EQ(a, b)` | Близость double по правилам GTest |
| `EXPECT_NEAR(a, b, eps)` | Абсолютная разница не больше eps |
| `EXPECT_THROW(expression, ExceptionType)` | Брошено исключение нужного типа |

`EXPECT_*` при неудаче регистрирует ошибку и продолжает текущую функцию. `ASSERT_*` регистрирует фатальную ошибку и **выходит из текущей функции**, а не завершает весь набор тестов. Если ASSERT находится во вспомогательной функции, сам по себе он не гарантирует немедленный выход из вызывающего теста. [Справочник проверок](https://google.github.io/googletest/reference/assertions.html).

```cpp
TEST(PointerTest, ChecksBeforeDereference) {
    int value = 7;
    int* p = &value;
    ASSERT_NE(p, nullptr);
    EXPECT_EQ(*p, 7); // сюда не идём при провале ASSERT
}
```

`EXPECT_EQ` для двух `const char*` сравнивает адреса, поэтому для текстового содержимого нужен `EXPECT_STREQ` или преобразование в `std::string`. Сравнение вещественных через точное `==` часто не подходит из-за округлений. Погрешность `EXPECT_NEAR` должна следовать из задачи, а не быть случайным большим числом.

### Fixture

```cpp
#include <gtest/gtest.h>
#include <vector>

class VectorTest : public ::testing::Test {
protected:
    void SetUp() override { values = {1, 2}; }
    std::vector<int> values;
};

TEST_F(VectorTest, CanAppend) {
    values.push_back(3);
    EXPECT_EQ(values.size(), 3u);
    EXPECT_EQ(values.back(), 3);
}

TEST_F(VectorTest, StartsFresh) {
    EXPECT_EQ(values.size(), 2u);
}
```

Для каждого `TEST_F` создаётся новый объект fixture: конструирование → `SetUp` → тело теста → `TearDown` → уничтожение. Изменения первого теста не передаются второму. Файлы и внешнее состояние нужно изолировать самостоятельно; отдельный объект fixture не очистит общую папку за вас.

### Минимальная сборка с уже установленным GTest

Сохраните первые два `AddTest` и функцию `Add` в `tests.cpp`:

```cmake
cmake_minimum_required(VERSION 3.20)
project(theormin3_tests LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
find_package(GTest CONFIG REQUIRED)
enable_testing()

add_executable(theormin_tests tests.cpp)
target_link_libraries(theormin_tests PRIVATE GTest::gtest_main)
include(GoogleTest)
gtest_discover_tests(theormin_tests)
```

```bash
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

`gtest_main` предоставляет `main`, поэтому собственная функция `main` в этом варианте не нужна. `find_package` требует доступной установки GoogleTest; вариант с загрузкой через FetchContent приведён в [официальном руководстве по CMake](https://google.github.io/googletest/quickstart-cmake.html).

Для адресного запуска тестового исполняемого файла есть `--gtest_filter=AddTest.*`, для проверки независимости — `--gtest_shuffle`, для повторения — `--gtest_repeat=10`. [Флаги и дополнительные возможности](https://google.github.io/googletest/advanced.html).

Полезные случаи для BMP: ширина с padding и без него, обе ориентации, неправильная сигнатура, короткий заголовок, обрезанные пиксели, неподдерживаемая битность, переполнение размеров. GTest не заменяет санитайзеры и не делает намеренный UB обычным корректным тестом.

:::remember
**Ответ на сдаче.** GoogleTest регистрирует тесты через TEST/TEST_F, запускает их и сообщает о проверках. EXPECT позволяет продолжить, ASSERT останавливает текущую функцию. Проверяем нормальные и граничные случаи, ошибки и независимость тестов; для памяти дополнительно используем санитайзеры.
:::

## 16. Память и расположение объектов: собираем всё вместе

Этот пункт обобщает темы 1–6. Нужно уметь по коду определить **отдельно каждый объект**, его длительность хранения, владельца и момент уничтожения.

```cpp
#include <memory>
#include <string>
#include <vector>

int global = 5;
int zero;

struct Packet {
    int id;
    std::vector<int> values;
};

int main() {
    static int calls;
    int local = 7;
    const char* literal = "hello";
    Packet packet{1, {10, 20, 30}};
    auto owner = std::make_unique<Packet>(Packet{2, {40, 50}});
    std::string text = "short";
    (void)local;
    (void)literal;
    ++calls;
}
```

| Сущность | Что и где обычно находится | Кто завершает жизнь / освобождает ресурс |
|---|---|---|
| `global` | Статический int, обычно .data | Завершение программы |
| `zero`, `calls` | Статические int с нулём, обычно .bss | Завершение программы |
| `local` | Автоматический int, стек/регистр | Выход из main |
| `literal` | Автоматический указатель | Выход из main |
| Символы `"hello"` | Массив со статической длительностью, обычно .rodata | Доступен всё выполнение |
| `packet` и его поля-объекты | Автоматический Packet, обычно стек | Его деструктор при выходе |
| Буфер `packet.values` | Динамическое хранилище элементов | Деструктор vector |
| `owner` | Автоматический unique_ptr | Его деструктор |
| Объект `*owner` и его поля | Динамический Packet | unique_ptr вызывает delete |
| Буфер `owner->values` | Отдельное динамическое хранилище | Деструктор вложенного vector |
| `text` | Автоматический объект string | Его деструктор |
| Символы `text` | Могут быть внутри string из-за SSO или в динамическом буфере | Управляет string |

**SSO**, small string optimization, — распространённая оптимизация хранения коротких строк внутри самого объекта. Стандарт не требует конкретного порога и самой этой оптимизации. Из слова `std::string` нельзя вывести «символы обязательно в куче».

### Выравнивание и размер

`sizeof(T)` — размер объекта в единицах `char`, включая padding. `alignof(T)` — требуемое выравнивание. Например, `struct { char c; int n; };` часто занимает 8 байт, а не 5; точный размер зависит от платформы. Соседние элементы массива `T` идут с шагом `sizeof(T)`, поэтому padding тоже участвует в шаге.

### Что происходит внутри аллокатора

Аллокатор получает крупные области от ОС и выдаёт из них блоки. Он может хранить метаданные, списки свободных блоков, разделять/объединять блоки, кешировать освобождённое. Это детали реализации: нельзя законно читать «счётчик размера перед p», если интерфейс этого не разрешает.

**Внешняя фрагментация** — свободная память разбита на неудобные куски. **Внутренняя** — выданный блок содержит неиспользуемый запас из-за округления и служебных требований. Много свободных байт в сумме не гарантирует успех одного большого запроса.

:::remember
**Ответ на сдаче.** У каждого указателя, управляемого объекта и вложенного буфера свои размещение и время жизни. Хранилище может переживать объект; владелец может быть на стеке, а ресурс — в динамической памяти. Реальная карта состоит из отображений страниц, а аллокатор управляет блоками внутри них.
:::

## 17. Как выглядят сегменты и указатели стека: SP, BP, RSP, RBP

### Что, вероятно, подразумевается под «BSP»

В обычных схемах стека x86 используют **SP** (stack pointer) и **BP** (base/frame pointer). В 32-битном x86 — `ESP`/`EBP`, в x86-64 — `RSP`/`RBP`. Единого стандартного регистра стека «BSP» в этой модели нет: скорее всего, это смешение названий SP и BP. На других архитектурах названия и устройство отличаются.

| Регистр x86-64 | Роль в рассматриваемой модели |
|---|---|
| `RSP` | Текущая вершина машинного стека |
| `RBP` | Опорная точка кадра, если компилятор её использует |
| `RIP` | Указатель инструкции |
| `RAX` / `EAX` | В System V ABI обычно результат целочисленной функции соответствующего размера |
| `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9` | Первые шесть подходящих целочисленных/указательных аргументов в System V AMD64 |

Это **соглашение платформы, ABI**, а не правило языка C++. Классификация больших структур и вещественных аргументов сложнее. В Windows x64 первые четыре таких аргумента идут через `RCX`, `RDX`, `R8`, `R9`; смешивать схемы нельзя. [Проект спецификации System V AMD64 ABI](https://gitlab.com/x86-psABIs/x86-64-ABI).

### Пролог, кадр и эпилог

Учебный листинг в синтаксисе Intel; он иллюстрирует обычный кадр, но не претендует на обязательный результат компиляции:

```asm
; вход в функцию после call
push rbp           ; сохранить RBP вызывающей функции, RSP -= 8
mov  rbp, rsp      ; установить базу нового кадра
sub  rsp, 16       ; зарезервировать место под локальные данные/выравнивание

; тело: например, локальный int может быть по [rbp - 4]

mov  rsp, rbp      ; убрать локальную область
pop  rbp           ; восстановить базу вызывающей функции
ret                ; взять адрес возврата со стека и продолжить вызывающую функцию
```

Обычный near `call` на x86-64 кладёт адрес следующей инструкции на стек и передаёт управление. `ret` извлекает адрес возврата. `RBP` — регистр, а `[RBP]` — память по адресу, записанному в этом регистре; это разные вещи.

```text
Большие адреса
RBP + 8  | адрес возврата                         |
RBP      | сохранённый RBP вызывающей функции    | <- RBP
RBP - 4  | возможный локальный int               |
         | другие локальные данные / padding    |
RBP - 16 | низ зарезервированной области         | <- RSP
Малые адреса
```

При `sub rsp, 16` числовое значение `RSP` **уменьшается**, то есть стек растёт вниз. После возврата байты не обязаны стираться. Но прежние локальные объекты уже не существуют, и сохранённые адреса на них не становятся безопасными только потому, что «там всё ещё 42».

Оптимизатор может не использовать `RBP` как frame pointer, держать значения в регистрах, встроить вызов и убрать локальный объект. В System V AMD64 есть **red zone** — 128 байт ниже `RSP`, которыми можно пользоваться по правилам ABI; это не добавляет такой области Windows x64 и не отменяет время жизни C++-объектов.

### А где «указатель кучи»?

У процесса нет обязательного единственного аппаратного регистра «вершины кучи», аналогичного `RSP`. Аллокатор держит своё состояние в обычной памяти: арены, списки свободных блоков, служебные структуры. Возвращённый `new`/`malloc` указатель — адрес конкретного блока/объекта, а не указатель на всю кучу.

`brk`/`sbrk` исторически управляют границей одной области данных Linux; `mmap` создаёт другие отображения. Поэтому картинка с одной стрелкой «heap pointer» — лишь упрощение, а не универсальное устройство malloc.

### Как посмотреть своими глазами

На Linux в отдельной учебной программе выведите адреса объектов; для указателя на char приведите его к `const void*`, иначе поток попытается вывести строку:

```cpp
#include <iostream>

int global = 1;
int zero;

int main() {
    int local = 2;
    int* dynamic = new int{3};
    const char* literal = "hello";
    std::cout << "global: " << static_cast<const void*>(&global) << '\n'
              << "zero: " << static_cast<const void*>(&zero) << '\n'
              << "local: " << static_cast<const void*>(&local) << '\n'
              << "pointer object: " << static_cast<const void*>(&dynamic) << '\n'
              << "dynamic int: " << static_cast<const void*>(dynamic) << '\n'
              << "literal: " << static_cast<const void*>(literal) << '\n';
    std::cin.get(); // оставляет процесс живым для просмотра карты
    delete dynamic;
}
```

В другом терминале `cat /proc/<PID>/maps` показывает отображения и права. Подставьте настоящий PID своей программы. Метка `[heap]` обозначает классическую область, но не все блоки аллокатора обязаны быть в ней. Секции/сегменты ELF можно смотреть через `readelf -S ./example` и `readelf -l ./example`; инструкции — через `objdump -d -Mintel ./example`.

Для учебной отладки собирайте с `-g -O0 -fno-omit-frame-pointer`. Адреса и смещения всё равно зависят от сборки. Сравнивать численные адреса на картинке можно, но вычитать в C++ указатели на несвязанные объекты нельзя: определённая разность указателей относится к одному массиву.

:::remember
**Ответ на сдаче.** RSP задаёт вершину стека x86-64, RBP может задавать базу кадра, RIP — положение выполнения. Call сохраняет адрес возврата, пролог создаёт кадр, эпилог убирает его. У кучи нет универсального аналогичного регистра: динамическими областями управляет аллокатор. Роли регистров и точная раскладка зависят от архитектуры и ABI.
:::
