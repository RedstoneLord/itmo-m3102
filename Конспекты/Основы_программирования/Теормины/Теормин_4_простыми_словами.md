# Теормин 4. Сборка C++, препроцессор, связывание и пространства имён

Пять тем для устной сдачи и разбор того, как они встречаются в архиваторе HamArc. Примеры рассчитаны на C++23, команды сборки — на GCC или Clang с Unix-подобной командной строкой. После теории попробуйте [практикум с задачами и решениями](https://github.com/RedstoneLord/itmo-m3102/blob/master/Конспекты/Основы_программирования/Теормины/Теормин_4_практикум.md).

## 1. Этапы компиляции

:::meaning
**Единица трансляции** в обычном проекте с заголовками — отдельный исходный файл со всем, что в него вошло после обработки директив препроцессора. Если `main.cpp` и `coder.cpp` включили один заголовок, его содержимое попало в две разные единицы трансляции.
:::

В разговоре «скомпилировать программу» часто означает всю сборку. Если спрашивают об этапах, полезно различать четыре шага типичной цепочки инструментов. У стандарта C++ есть отдельное, более подробное описание фаз трансляции. Промежуточные файлы из таблицы можно запросить у драйвера, а при обычной сборке они могут не сохраняться.

| Шаг | Вход и результат | Что происходит |
|---|---|---|
| Препроцессинг | `.cpp` и заголовки → обработанный текст `.ii` | Обрабатываются `#include`, макросы и условная компиляция. |
| Компиляция в узком смысле | Обработанная единица трансляции → ассемблерный текст `.s` | Проверяются синтаксис и семантика. Выбираются перегрузки, создаётся и оптимизируется представление программы, генерируется код. |
| Ассемблирование | Ассемблерный текст → объектный файл `.o` | Получаются машинные инструкции, данные, символы и записи о местах, которые надо поправить при связывании. |
| Линковка | Объектные файлы и библиотеки → исполняемый файл или библиотека | Линкер сопоставляет ссылки на символы с определениями и размещает код и данные. При динамическом связывании часть работы выполняется при загрузке или позже. |

```diagram

C: round "codec.cpp"
H: note "codec.hpp"
OM: box "main.o"
OC: box "codec.o"
L: round "Линкер → hamarc"

```

### Откуда компилятор знает про функцию из другого файла

**Объявление** сообщает, какая сущность называется данным именем. **Определение** тоже является объявлением и, например для функции, содержит тело, а для объекта обычно задаёт сам объект. Заголовок позволяет компилятору проверить вызов, а определение позволяет линкеру связать его с кодом функции.

```cpp
// codec.hpp
#pragma once
int EncodedBytes(int bytes);
```

```cpp
// codec.cpp
#include "codec.hpp"

int EncodedBytes(int bytes) {
    return 2 * bytes;
}
```

```cpp
// main.cpp
#include "codec.hpp"

int main() {
    return EncodedBytes(3) == 6 ? 0 : 1;
}
```

:::example
**Проследим за вызовом `EncodedBytes(3)`.**

1. Препроцессор подставляет объявление из `codec.hpp`.
2. Компилятор видит параметр типа `int` и результат типа `int`, поэтому может проверить вызов без тела.
3. В обычной отдельной сборке `main.o` ссылается на символ функции, а `codec.o` содержит его определение.
4. Линкер находит определение. Если убрать `codec.o` из команды линковки, компиляция `main.cpp` по-прежнему проходит, но итоговый исполняемый файл собрать не удастся.
:::

```bash
g++ -std=c++23 -E main.cpp -o main.ii
g++ -std=c++23 -S main.ii -o main.s
g++ -c main.s -o main.o
g++ -std=c++23 -c codec.cpp -o codec.o
g++ main.o codec.o -o hamarc
```

В GNU-окружении `nm -C main.o` обычно покажет `U EncodedBytes(int)` (ссылка без определения в этом файле), а `nm -C codec.o` — `T EncodedBytes(int)` (глобальный символ в секции кода). Опция `-C` делает декорированные имена C++ читаемыми. Декорирование, или *name mangling*, помогает различать одноимённые функции с разными параметрами и пространствами имён. Конкретная схема зависит от ABI платформы. `extern "C"` задаёт языковое связывание для взаимодействия с C и само по себе не создаёт определение.

### Как это выглядит в CMake

При `cmake -S . -B build` CMake читает описание проекта и готовит правила сборки. При `cmake --build build` эти правила исполняются. Команда `ctest --test-dir build --output-on-failure` запускает зарегистрированные тесты после сборки.

В HamArc цель `hamarc` собирает `main.cpp`, `coder.cpp`, `utils.cpp`, `hamarc.cpp` и `parser.cpp`. Отдельная цель `argparser` собирает реализацию парсера. `target_link_libraries(hamarc PRIVATE argparser)` связывает эти цели. Включение `argparser.h` даёт объявления, а подключение цели даёт определения. Для своей лабораторной используйте CMake 3.24 или новее и C++23.

**Ответ на сдаче.** Каждый `.cpp` с включёнными заголовками обрабатывается отдельно и превращается в объектный файл. Линкер соединяет эти файлы и код библиотек. Если объявление видно, но определения нет среди входов линкера, вызов может успешно скомпилироваться и дать ошибку на линковке.

## 2. Препроцессор и макросы

### Директивы и порядок обработки

| Директива | Что делает |
|---|---|
| `#include` | Включает содержимое заголовка. Кавычки обычно начинают поиск с путей, связанных с включающим файлом. Угловые скобки используют настроенные пути поиска. Детали определяет реализация. |
| `#define`, `#undef` | Определяют макрос и отменяют его определение. |
| `#if`, `#elif`, `#else`, `#endif` | Выбирают, какие фрагменты попадут в обработанный исходник. |
| `#ifdef`, `#ifndef` | Проверяют наличие или отсутствие определения макроса. |
| `#error` | Выдаёт диагностику, если директива находится в активной ветке. |

`#ifdef TRACE` сработает и при `-DTRACE=0`, потому что проверяется наличие имени. `#if TRACE` с тем же значением выберет ложную ветку. `#if` работает с выражениями препроцессора, поэтому попытка проверить уже объявленную переменную `constexpr` не проверит её значение. Обычный `if` обрабатывает компилятор и проверяет корректность обеих веток. Для `if constexpr` действуют отдельные правила об отброшенной ветке, в частности при инстанцировании шаблонов.

В тестах HamArc `#ifdef _WIN32` выбирает оформление пути для командной строки, а `target_compile_definitions` задаёт для тестовой цели макросы с путями к ресурсам и исполняемому файлу. Для своего флага можно написать:

```cmake
target_compile_definitions(hamarc PRIVATE TRACE=1)
```

### Макросы и побочные эффекты

Объектоподобный макрос заменяет имя последовательностью токенов. Функциональный макрос также подставляет токены аргументов. Он не знает C++-типы, области видимости и перегрузки. В объявлении функционального макроса открывающая скобка пишется сразу после имени.

```cpp
#define BAD_SQUARE(x) x * x
#define SQUARE(x) ((x) * (x))

constexpr int Square(int x) {
    return x * x;
}
```

:::example
`BAD_SQUARE(2 + 3)` разворачивается в `2 + 3 * 2 + 3` и даёт $11$. `SQUARE(2 + 3)` даёт $25$, потому что скобки сохраняют группировку. Но `SQUARE(i++)` превращается в два неупорядоченных изменения одной переменной в операндах умножения и даёт неопределённое поведение. При вызове `Square(i++)` инкремент выполняется один раз.
:::

Даже заключение макроса в пространство имён не ограничит его действие. Например, макрос `Encode(x)` может развернуться и в записи `codec::Encode(3)`, потому что препроцессор видит токен `Encode` перед скобкой.

Оператор `#` в определении функционального макроса превращает токены аргумента в строковый литерал, `##` склеивает токены. Для переменного числа аргументов используются `...` и `__VA_ARGS__`. В C++23 `__VA_OPT__(,)` позволяет подставить запятую только при наличии вариативных токенов.

```cpp
#include <cstdio>

#define SHOW(expr) std::printf("%s = %d\n", #expr, (expr))
#define TRACEF(format, ...) std::fprintf(stderr, format __VA_OPT__(,) __VA_ARGS__)
```

У `SHOW(2 + 3)` первая часть превращается в строку `"2 + 3"`, вторая вычисляется как выражение. Вызовы `TRACEF("ok\n")` и `TRACEF("size=%d\n", 4)` оба имеют правильное число запятых. Типобезопасные константы, обычные функции и шаблоны предпочтительны для вычислений. Условная компиляция и доступ к токенам вызова — типичные причины применять макросы.

### Почему заголовок защищают от повторного включения

```cpp
#ifndef HAMARC_CODEC_HPP
#define HAMARC_CODEC_HPP

struct CodecOptions {
    int payload_bits;
};

#endif
```

Второе включение в ту же единицу трансляции увидит уже определённый макрос и пропустит тело заголовка. В другой единице трансляции этот guard срабатывает независимо. `#pragma once`, как в `coder.h` и `consts.h` HamArc, — практичная поддерживаемая популярными компиляторами альтернатива. Стандартной идиомой остаётся guard на макросе.

:::warning
Защита заголовка решает повторное включение **внутри одной** единицы трансляции. Если в заголовке определена обычная функция с внешним связыванием и его подключили два исходника, guard позволит получить по определению в каждом объектном файле. Тогда проблему надо решать по правилам ODR.
:::

**Ответ на сдаче.** Препроцессор включает заголовки, выбирает активные ветки и подставляет токены. Макрос может продублировать вычисление аргумента. Скобки помогают с приоритетами операторов, а однократное вычисление аргумента обеспечивает обычная функция.

## 3. Связывание и длительность хранения

Четыре вопроса легко спутать, потому что одно объявление даёт ответ сразу на несколько из них.

| Понятие | Вопрос |
|---|---|
| Область видимости (scope) | Где поиск может найти это имя? |
| Связывание имени (linkage) | Когда объявления этого имени могут обозначать одну сущность? |
| Длительность хранения (storage duration) | Как долго потенциально доступно хранилище объекта? |
| Время жизни (lifetime) | Когда в этом хранилище существует конкретный объект или ссылка? |

### Внешнее, внутреннее и отсутствие связывания

```cpp
// state.cpp
int archives_opened = 0;
extern int retries;        // определение должно быть там, где его обеспечит программа
static int local_cache = 0;
const int block_bytes = 8;

namespace {
int DecodeHeader() { return 0; }
}

int NextTicket() {
    static int count = 0;
    return ++count;
}
```

| Имя | Связывание | Длительность хранения объекта |
|---|---|---|
| `archives_opened` | Внешнее. В другом .cpp допустимо объявить `extern int archives_opened;` и обратиться к тому же объекту. | Статическая |
| `retries` | В данном примере внешнее. Объявление без инициализатора само по себе не определяет объект. | Статическая у определённого объекта |
| `local_cache` | Внутреннее. В другом .cpp одноимённое `static int` будет отдельной переменной. | Статическая |
| `block_bytes` | Внутреннее по умолчанию для такой `const`-переменной на уровне пространства имён. | Статическая |
| `DecodeHeader` | Внутреннее в безымянном пространстве имён. | К функции понятие длительности хранения объекта не применяется |
| `count` | У имени нет связывания, оно локально для блока. | Статическая. Значение сохраняется между вызовами. |

В современном C++ существует и **связывание модуля**. Оно относится к объявлениям, присоединённым к именованному модулю, если соответствующее имя имеет связывание модуля по правилам C++. В обычном проекте HamArc с `#include` для примеров выше достаточно трёх случаев из таблицы.

:::remember
`static` перед переменной в пространстве имён даёт имени внутреннее связывание. `static` у локальной переменной даёт ей статическую длительность хранения. Внутри класса ключевое слово `static` у поля означает одно поле класса, общее для его объектов. Всегда смотрите на место объявления.
:::

### Четыре длительности хранения

- **Автоматическая.** Обычные локальные объекты и параметры. Например, `Parser parser;` в `main` уничтожается при выходе из своего блока обычным путём. Стек — типичная реализация.
- **Статическая.** Хранилище существует на протяжении выполнения программы. У локальной статической переменной динамическая инициализация выполняется при первом прохождении через объявление. Инициализация, которая может быть выполнена статически, возможна раньше.
- **Потоковая.** У каждого потока своя копия объекта с `thread_local`, хранилище связано с длительностью потока. Локальная `thread_local` переменная может иметь имя без связывания.
- **Динамическая.** Например, объект, созданный выражением `new`. Локальный указатель на него может иметь автоматическую длительность хранения. Уничтожение указателя само по себе не освобождает динамический объект.

У объекта `std::vector` в локальном блоке автоматическая длительность хранения, а его динамически выделенный буфер имеет отдельное хранилище. При уничтожении вектора его деструктор освобождает этот буфер. Пример связывает тему с RAII из третьего теормина.

### ODR и определения в заголовках

**ODR** (*One Definition Rule*) ограничивает число и вид определений. Обычной не-`inline` функции с внешним связыванием, которую вызывают, нужно одно определение в программе. Для `inline` функций, `inline` переменных и некоторых других сущностей, в том числе классов и шаблонов, стандарт допускает определения в разных единицах трансляции при соблюдении условий. Например, для обычных заголовков определения должны состоять из одинаковой последовательности токенов, а соответствующие имена при поиске обычно должны находить те же сущности. Для некоторых нарушений стандарт не требует диагностики.

В `consts.h` HamArc запись `const int kBufferSize = 256;` даёт отдельную константу с внутренним связыванием в каждой включившей её единице трансляции. Если нужна одна общая константа с одним адресом, можно использовать `inline constexpr`:

```cpp
// archive_config.hpp
#pragma once

namespace config {
inline constexpr int kBufferSize = 256;
}
```

Другой вариант — `extern const int kBufferSize;` в заголовке и определение в одном `.cpp`, который включает этот заголовок. Для обычной функции в заголовке `inline` регулирует возможность нескольких определений. Подстановка тела функции вместо вызова — отдельное решение оптимизатора.

**Ответ на сдаче.** Связывание относится к имени, длительность хранения — к объекту. У локального `static` имя остаётся локальным, а хранилище сохраняется. У двух `static`-переменных из разных `.cpp` имена могут совпадать, а объекты будут разными.

```quiz
explain: Внутреннее связывание отделяет определения двух единиц трансляции.
```

## 4. Ошибки разных этапов компиляции

| Этап | Типичный симптом | Что проверить |
|---|---|---|
| Конфигурация CMake | Не найден пакет или указан отсутствующий исходник | Имена целей, пути, версию инструментов и зависимости |
| Препроцессинг | Не найден заголовок или сработал `#error` | Имя файла, пути поиска, определения макросов |
| Компиляция | `expected ';'`, `no matching function`, `ambiguous`, `use of deleted function` | Первую содержательную диагностику, типы аргументов, видимые объявления |
| Ассемблирование | Неизвестная инструкция в рукописном ассемблере | Имя инструкции, её операнды и целевую архитектуру |
| Линковка | `undefined reference` или `multiple definition` | Совпадение сигнатуры и пространства имён, наличие .cpp в цели, библиотеки и ODR |
| Загрузка или выполнение | Не найдена динамическая библиотека, файл не открывается, байты извлекаются неверно | Окружение запуска, входные данные, состояния потоков, тесты и инварианты |

:::example
**Похожий симптом после двух разных правок.**

1. Убрали объявление `EncodedBytes` из заголовка. `main.cpp` перестал компилироваться, потому что вызов не находит имя.
2. Вернули объявление и убрали `codec.cpp` из цели. Объектный файл `main.o` собрался. Линкер не нашёл тело функции.
3. Добавили тело прямо в заголовок и снова включили заголовок из двух .cpp. Теперь типичная диагностика линкера — два определения.
:::

Не вся ошибка линковки означает «забыли написать функцию». Сравните объявление `int Size(int);` и отдельное определение `int Size(long)`. Обе единицы трансляции могут быть корректны по отдельности, но при вызове первой перегрузки линкер не найдёт её определение. Если определение написано внутри чужого пространства имён, получится аналогичная проблема.

Когда первое сообщение ссылается на длинную подстановку макроса, полезно посмотреть результат `-E`. При сбое сборки в CMake команда `cmake --build build --verbose` показывает реальные вызовы инструментов. `nm -C` помогает сравнить символ, который требуется вызывающему объектному файлу, и символ, который предоставляет библиотека.

:::warning
Сообщение об открытии повреждённого архива возникает уже во время выполнения. Расхождение содержимого после извлечения может быть логической ошибкой. Выход за границы массива или знаковое переполнение при расчёте смещения могут дать неопределённое поведение без заметного падения.
:::

**Ответ на сдаче.** Сначала выясняю, какой результат уже получился. Если не образовался .o — смотрю препроцессор и компилятор. Если .o есть, а исполняемого файла нет — проверяю символы и входы линкера. Если запускается — проверяю вход, коды возврата и корректность результата.

```quiz
title: Проверка диагностики ошибок

? Объявление функции видно и вызов успешно превращается в .o. На финальной сборке появляется undefined reference. Где возникла ошибка?
- [ ] Препроцессинг
- [ ] Ассемблирование
- [x] Линковка
explain: Линкер не нашёл нужное определение среди входных объектных файлов и библиотек.

? Что может привести к ошибке линковки при вызове `int Size(int)`?
- [x] .cpp с определением не добавили в цель.
- [ ] Вызов стоит после объявления с точной сигнатурой.
- [ ] Заголовок был защищён include guard.
- [x] Отдельно определена `Size(long)`, а `Size(int)` так и не определена.
explain: Требуется именно символ `Size(int)`. Перегрузка с `long` предоставляет другой символ.
```

## 5. Пространства имён

:::meaning
**Пространство имён** объединяет объявления и даёт им область видимости. Квалифицированное имя указывает, где искать сущность. В HamArc `utils::CheckValid` — проверка параметра, `nargparse::AddFlag` — функция библиотеки парсинга, `consts::kBufferSize` — константа.
:::

```cpp
namespace hamarc::codec {
int CountBits(int bytes) {
    return 8 * bytes;
}
}

namespace hamarc::archive {
int CountBits(int headers) {
    return 64 * headers;
}
}

namespace hc = hamarc::codec;

int FromCodec(int bytes) {
    using hamarc::codec::CountBits;
    return CountBits(bytes);
}

int FromArchive(int headers) {
    return ::hamarc::archive::CountBits(headers);
}
```

- `hamarc::codec::CountBits` — квалифицированное имя. Начальное `::` начинает поиск с глобального пространства имён.
- `namespace hc = hamarc::codec;` — псевдоним пространства. Можно написать `hc::CountBits(3)`.
- `using hamarc::codec::CountBits;` — *using-объявление* для конкретного имени.
- `using namespace hamarc::codec;` — *using-директива*: влияет на дальнейший неквалифицированный поиск, поэтому может привести к неоднозначности. В общем заголовке её действие может затронуть включившие его исходники.
- Именованное пространство можно продолжить вторым блоком `namespace hamarc::codec { ... }` в том же или другом файле. Само наличие одинаковых пространств имён в двух .cpp не делает объявления одного файла видимыми другому.
- Безымянное пространство `namespace { ... }` удобно для функций и типов реализации, которые нужны только в этой единице трансляции. Поместив его в заголовок, получите отдельные сущности в каждом включившем исходнике.

:::example
Если в одном блоке написать `using namespace hamarc::codec;` и `using namespace hamarc::archive;`, вызов `CountBits(3)` будет неоднозначен. У найденных функций одинаковые типы параметров, и ни одна не выигрывает при выборе перегрузки. Запись `hamarc::codec::CountBits(3)` выбирает нужное пространство до выбора перегрузки.
:::

При неквалифицированном вызове функции иногда действует ADL (*argument-dependent lookup*). Например, для аргумента типа `codec::Block` поиск может добавить функции из связанного пространства `codec`. Сначала на защите достаточно объяснить разницу между обычным поиском имени и выбором перегрузки. Квалификатор `HammArc::` в определении метода — область класса, хотя синтаксис `::` похож на обращение к пространству имён.

**Ответ на сдаче.** Пространства имён позволяют держать одноимённые сущности отдельно. Я указываю нужное пространство через `::` или ввожу одно имя через `using`. Вспомогательные функции одного .cpp можно поместить в безымянное пространство.

```quiz
title: Проверка пространств имён

? Какая запись вводит конкретное имя CountBits в текущий блок?
- [ ] `namespace hc = hamarc::codec;`
- [x] `using hamarc::codec::CountBits;`
- [ ] `using namespace hamarc::codec;`
explain: Using-объявление работает с указанным именем. Псевдоним даёт короткое имя самому пространству.

? Что произойдёт при неквалифицированном вызове CountBits(3), если две using-директивы сделали доступными две функции CountBits(int) из разных пространств?
- [x] Компилятор сообщит о неоднозначности.
- [ ] Линкер возьмёт функцию из первого по порядку .cpp.
- [ ] Вызов выберет последнюю директиву.
explain: При разрешении перегрузки обе функции одинаково хорошо подходят.

? Какой оператор в начале квалифицированного имени начинает поиск с глобального пространства? Введите только символы оператора.
= ::
explain: Например, `::hamarc::codec::CountBits(3)` начинает поиск с глобальной области.
```
