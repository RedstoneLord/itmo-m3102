## 1. Задачи по пяти обязательным темам

Сначала назовите этап или правило C++, затем объясните ответ. Для задания с несколькими .cpp держите в голове, что каждый из них компилируется отдельно.

### Задания

1. Есть `main.cpp`, `coder.cpp` и подключённый обоими `coder.hpp`. Назовите число единиц трансляции, промежуточный результат каждого из четырёх этапов и действие флагов `-E`, `-S`, `-c`. Что пересоберётся при правке только тела функции в `coder.cpp` и что обычно пересоберётся при правке заголовка?
2. В `main.cpp` виден `int Size(int);`; другой файл определяет `int Size(long)`. Будет ли вызов `Size(3)` компилироваться? Может ли линкер сам выбрать перегрузку `long`? Как локализовать проблему?
3. Компилятору передали `-DDEBUG=0`. Какие ветки из `#ifdef DEBUG`, `#if DEBUG` и `#if defined(DEBUG) && DEBUG` активны?
4. Для `#define TWICE(x) x + x` вычислите `3 * TWICE(1 + 2)`. Что изменится у `#define TWICE(x) ((x) + (x))`? Почему второй вариант всё ещё опасен с `i++`?
5. В `coder.hpp` с `#pragma once` определена `int Code(int x) { return x; }`. Заголовок включают два `.cpp`. Какая типичная ошибка возникает и как исправить её двумя способами?
6. Для каждого имени из фрагмента ниже назовите связывание, а для каждой переменной — длительность хранения. Отдельно объясните, что происходит с объектом, созданным через `new`.

```cpp
int total = 0;
extern int retries;
static int cache = 0;
const int width = 8;
thread_local int last_error = 0;

namespace {
void Reset() { cache = 0; }
}

void Work() {
    static int calls = 0;
    int count = 0;
    int* p = new int{count};
    delete p;
}
```

7. Заголовок с `namespace config { const int kSize = 256; }` включён в двух .cpp. Оба возвращают адрес `&config::kSize`. Получится ли один объект? Что изменится при `inline constexpr`?
8. Разложите случаи по этапам: нет `coder.hpp`, неоднозначный вызов, опечатка в ассемблерной инструкции, два определения обычной функции, тест извлёк файл неверной длины, отсутствующая библиотека обнаружена при загрузке процесса.
9. В пространствах `archive` и `codec` есть по `void Run(int);`. В одном блоке написали обе using-директивы, затем `Run(1);`. Какие варианты записи оставят доступ к одной нужной функции?
10. Почему `#include "argparser.h"` и `target_link_libraries(hamarc PRIVATE argparser)` решают разные задачи? Что покажут `cmake --build build --verbose` и `nm -C` при `undefined reference`?

### Решения

1. Две единицы трансляции. Результаты: обработанный исходник, ассемблерный текст, объектный файл, исполняемый файл. `-E` останавливается после препроцессора, `-S` — после генерации ассемблерного текста, `-c` — после объектного файла. При обычной инкрементальной сборке правка тела в `coder.cpp` меняет его объектный файл и требует перелинковки. После правки используемого обоими заголовка пересобираются оба объекта.
2. Вызов компилируется по `Size(int)`. Для линкера `Size(long)` — другой символ. Посмотрите, какой символ требуется в `main.o` и какой определён во втором объектном файле. Совместное подключение заголовка в .cpp с реализацией помогает проверять интерфейс, но случайно добавленная перегрузка на уровне пространства имён может всё равно скомпилироваться.
3. Активен только `#ifdef DEBUG`. В третьем условии левая часть истинна, правая ложна.
4. Первое выражение разворачивается в `3 * 1 + 2 + 1 + 2`, результат $8$. Второе — в `3 * ((1 + 2) + (1 + 2))`, результат $18$. В `((i++) + (i++))` два изменения одной переменной не упорядочены. Для однократного вычисления аргумента подходит функция с параметром по значению.
5. Guard допускает по одному определению на каждый .cpp, а обычная внешняя `Code` получает два определения в программе. Типичный ответ — `multiple definition`. Можно оставить в заголовке объявление и перенести тело в один .cpp. Если тело должно быть в заголовке, подходит `inline` и соблюдение ODR.
6. `total`, `retries`, `last_error`, `Work` — внешнее связывание. `cache`, `width`, `Reset` — внутреннее. `calls`, `count`, `p` — без связывания. Статическое хранение у `total`, `retries` (при наличии определения), `cache`, `width`, `calls`. Потоковое у `last_error`, автоматическое у `count` и `p`. Объект `*p` имеет динамическое хранение и уничтожается при `delete p`. У функции спрашивают связывание её имени.
7. Получатся два отдельных объекта `const int` с внутренним связыванием. После замены на `inline constexpr int kSize = 256;` получается одна переменная с одним адресом, если определения соблюдают ODR.
8. По порядку: препроцессинг, компиляция, ассемблирование, обычно линковка, выполнение, загрузка. Для компиляции и линковки важно отличать «вызов не нашёл подходящее объявление» от «вызов уже выбран, нужного определения нет».
9. Можно написать `codec::Run(1)` или `::codec::Run(1)`. Можно убрать широкие директивы и ввести конкретное имя `using codec::Run;`. При сохранении обеих директив неквалифицированный вызов в исходном примере неоднозначен.
10. Включение даёт компилятору объявления. Связывание с целью даёт определения и применимые требования использования библиотеки. Подробный вывод CMake помогает увидеть, какие файлы и библиотеки реально переданы, а `nm -C` — сопоставить отсутствующий символ с доступными.

## 2. Путь команды, данных и ошибок в HamArc

### От аргументов до операции

| Код | Что объяснить на своём проекте |
|---|---|
| `bin/main.cpp` | Точка входа, вызовы парсера, проверка доступности архива, `switch` по операции, вывод и код завершения. |
| `bin/parser.cpp` и `argparser/argparser.h` | Флаги, именованные аргументы и позиционные имена файлов. Перегрузки `AddArgument`, указатель на результат и callback-валидатор. |
| `bin/hamarc.cpp` | Формат, чтение и запись заголовков, переходы по файлу, добавление, извлечение, удаление и объединение. |
| `bin/coder.cpp` и `bin/utils.cpp` | Кодирование и декодирование слова, перенос остатка через границу буфера, расчёт размера записи. |
| `tests/test_archiver.cpp` | Запуск готового CLI, временный каталог, инверсия битов и побайтовое сравнение. |

Для запуска ниже `argc` обычно равен $5$: имя программы, флаг операции, имя архива в одном аргументе и два имени файлов. Разбиение команды на аргументы выполняет окружение запуска. Кавычки в командной строке позволяют передать `"my file.bin"` одним аргументом. Возможность хранить такое имя внутри архива зависит ещё и от формата заголовка.

```bash
hamarc --create --file=archive.haf input.bin "my file.bin"
```

В `Parser::InitParser` указатели наподобие `&create_` передают парсеру адреса полей. Поэтому он может записать туда результат. `utils::CheckValid` передаётся как функция проверки целого параметра размера блока. Объявление соответствующей перегрузки принимает указатель на функцию типа `bool (*)(const int&)`. Позиционные аргументы читаются отдельно от флагов. `Parser::Check` проверяет, что выбран ровно один режим, а `main` переключается по `Parser::status`. Нулевой код выхода обычно означает успех. Сообщение в `std::cerr` само по себе не меняет код выхода.

### Из чего состоит архив

В разбираемом варианте HamArc заголовок архива строится как строка `HAF d=<n> e=<k>` с переводом строки, где $n$ — число бит кодового слова, $k$ — число бит данных. Далее идут записи, у каждой свой закодированный заголовок `HAF f=<имя> s=<байты>` с переводом строки и закодированные данные. `s` хранит размер исходного файла. Заголовки кодируются фиксированными блоками $4\to 8$, а размер блока данных задаётся в заголовке архива. Это позволяет прочитать параметры архива до создания кодера данных с этими параметрами.

```tree
Архив .haf
  Заголовок архива
    Сигнатура и размеры блоков
  Первая запись
    Имя и исходный размер
    Кодовые слова данных
  Следующая запись
    Имя и исходный размер
    Кодовые слова данных
```

| Операция | Что ей нужно сделать |
|---|---|
| `create` | Проверить входы и параметры, записать формат и записи. Успех должен означать, что архив действительно можно открыть. |
| `list` | Прочитать заголовки. Если известна длина полезной части на диске, можно перейти к следующей записи без её декодирования. Это не проверяет целостность пропущенного содержимого. |
| `extract` | Найти нужные записи, декодировать данные и вывести ровно исходное число байтов. Без имён обработать все записи. |
| `append` | Прочитать формат существующего архива, дописать записи с совместимыми параметрами, обработать повторы имён по принятому правилу. |
| `delete` | Например, переписать заголовок и нужные записи во временный файл. Исходный архив заменяют после успешной записи и закрытия результата. |
| `concatenate` | Проверить формат и совместимость архивов. При совпадении форматов можно копировать записи с их заголовками, при различии нужно либо преобразование, либо явный отказ. |

Прямое склеивание двух .haf как файлов поместило бы второй глобальный заголовок в позицию, где читатель ждёт заголовок записи. В описанной реализации объединение дополнительно проверяет размеры блоков и работает с открываемым архивом назначения. Контракт вашей команды определяется условием лабораторной, где пример `-A` показывает два входных архива и отдельный выход.

:::warning
Поля формата нужно проверять до вычисления смещений и чтения данных. Например, заголовок на разделителях требует правила для пробелов и переводов строки внутри имени. Подход с длиной имени и отдельным считыванием указанного числа байтов даёт однозначные границы. Для двоичных числовых полей договоритесь о ширине и порядке байтов. Запись образа всей структуры со `std::string` не сохранит строку как последовательность символов, а у обычных структур дополнительно возможны padding и зависимость от платформы.
:::

### Потоковый ввод-вывод

`std::ios::binary` отключает характерные для текстового режима преобразования. `read` принимает адрес буфера и запрошенное число байтов, `gcount()` возвращает число реально считанных байтов последней соответствующей операции. На последнем неполном чтении оно может быть положительным при уже установленном `eofbit` и `failbit`. Сначала обработайте эти байты, затем различите ожидаемый конец и ошибку чтения. Для поля фиксированной длины короткое чтение означает, что поле не удалось получить целиком.

`seekg` меняет позицию чтения, `seekp` — записи. После короткого чтения иногда нужно сбросить флаги через `clear()`, если проверка уже показала, что можно продолжать позиционирование. После самого перемещения проверьте состояние. `std::ios::app` ставит запись в конец перед каждой записью. Для изменения байта по позиции в тесте используют `std::fstream` с `in | out | binary` и явные переходы, без `app`.

В `Coder` два остатка. Один держит биты, которых ещё мало на целое кодовое слово. Второй держит биты результата, которых мало на очередной байт. Оба состояния должны пережить границу двух чтений. После завершения записи нужно обработать хвост и обнулить состояние перед независимым файлом. Исходный размер позволяет при извлечении отбросить дополнение последнего слова.

:::formula
При непрерывной упаковке слов и отдельном выравнивании конца записи до байта для исходного файла из $B$ байтов число кодовых слов $q$ и число байтов данных на диске $L$ равны

$$
q=\left\lceil\frac{8B}{k}\right\rceil,\qquad
L=\left\lceil\frac{qn}{8}\right\rceil.
$$

Здесь $k>0$, $n\ge k$, а заголовок записи считается отдельно.
:::

:::example
При $B=31$, $k=247$, $n=256$ на входе $248$ бит. Один бит не помещается в первое слово. Поэтому $q=2$, $L=64$, а после декодирования нужно записать $31$ байт, даже если декодированы два полных слова данных. При $B=0$ получается $L=0$, но запись о пустом файле всё равно содержит заголовок.
:::

Для больших файлов важно проверять переполнение *до* умножения и сложения. Например, в `utils::CalculateBitsEncoded` все операнды исходного выражения `byte_size * 8` имеют тип `int`. Даже если итог записать в широкий тип, переполнение может произойти раньше. После проверки множителей округление вверх можно считать как частное плюс признак ненулевого остатка, чтобы избежать потенциального переполнения в сумме `x + k - 1`. Для позиционирования нужно убедиться, что вычисленный размер представим в типе смещения потока.

Чтение порциями ограничивает память для содержимого файла размерами буфера и состояния кодера. Метаданные могут дополнительно занимать память пропорционально числу и длине имён. Временные файлы тоже потребляют место, даже когда оперативной памяти нужно мало. В `EncodeBlock` и `DecodeBlock` есть проход по позициям для каждой из $r$ проверок, поэтому работа на слово оценивается как $O(nr)$. Для оценки всей операции добавьте число слов, чтение, запись и переписывание архива, если оно требуется.

## 3. Код Хэмминга и пределы восстановления

### Зачем нужны проверочные позиции

При чётной проверке XOR всех битов группы должен быть нулём. Инверсия одного бита меняет XOR каждой группы, в которую этот бит входит. Код Хэмминга назначает позиции так, чтобы у каждой позиции была своя комбинация групп.

Нумеруем позиции с $1$. Проверочные биты стоят на степенях двойки $1,2,4,8,\ldots$. Проверка с маской $p$ охватывает позицию $i$, если соответствующий бит в двоичной записи $i$ выставлен. В коде это условие `(i & p) != 0`. Для ненулевого положительного $i$ выражение `(i & (i - 1)) == 0` верно ровно для степеней двойки. Позиция $i$ в алгоритме соответствует индексу `i - 1` в контейнере.

```cpp
const unsigned mask = 1u << bit;
const bool set = (byte & mask) != 0;
const auto flipped = byte ^ mask;
```

`&` оставляет биты, общие для обоих операндов. `|` устанавливает биты маски, `^` инвертирует их. Сдвиг формирует маску, если его величина меньше ширины продвинутого левого операнда и неотрицательна. Для байта удобно сначала ограничить номер бита диапазоном от $0$ до $7$ и затем преобразовать результат к нужному типу. `std::uint8_t`, если доступен, имеет ширину ровно восемь бит. В обычной арифметике такой операнд часто продвигается к `int`, поэтому тип результата выражения нужно проверять отдельно.

:::formula
Для $k$ информационных и $r$ проверочных битов длина обычного слова $n=k+r$. У $r$ проверок есть $2^r$ разных результатов. Чтобы отличить отсутствие ошибки и каждую из $n$ возможных одиночных ошибок, необходимо

$$
2^r\ge k+r+1.
$$
:::

### Ручной пример: слово из семи битов

Возьмём данные $1,0,1,1$ и положим их на позиции $3,5,6,7$. В таблице $p_i$ — бит проверки с маской $i$.

| Проверка | Позиции | Значение бита для чётности |
|---|---|---|
| $p_1$ | $1,3,5,7$ | $1\oplus0\oplus1=0$ |
| $p_2$ | $2,3,6,7$ | $1\oplus1\oplus1=1$ |
| $p_4$ | $4,5,6,7$ | $0\oplus1\oplus1=0$ |

```array
title: Кодовое слово до повреждения
caption: Индекс массива на единицу меньше позиции Хэмминга. Выделены проверочные биты.
[0, 1, 1, 0, 0, 1, 1] highlight: 0,1,3
```

:::example
Пусть повредилась позиция $6$. Нарушены проверки с масками $2$ и $4$, поскольку $6=2+4$. Проверка с маской $1$ проходит. **Синдром** — собранный по результатам проверок номер $6$. Инвертируем бит по индексу $5$ и возвращаем информационные позиции $3,5,6,7$.
:::

На схеме ниже деление и остаток выделяют нужный разряд номера позиции. Это тот же выбор группы, что и проверка с битовой маской. Переменная `syndrome` накапливает результат, стрелка `i` показывает индекс текущей ячейки, а `bad` — индекс для исправления.

```array
title: Вычисление синдрома для ошибки в позиции 6
[0, 1, 1, 0, 0, 0, 1]
pointers: i, bad
print: last
code:
let syndrome = 0;
for (let mask = 1; mask <= 4; mask = 2 * mask) {
    let parity = 0;
    for (let i = 0; i < a.length; i++) {
        if (Math.floor((i + 1) / mask) % 2 == 1) {
            if (a[i] == 1) parity = 1 - parity;
        }
    }
    if (parity == 1) syndrome = syndrome + mask;
}
if (syndrome != 0) {
    let bad = syndrome - 1;
    a[bad] = 1 - a[bad];
}
```

Если повредились позиции $3$ и $5$, синдром равен $3\oplus5=6$. Обычный однобитовый декодер примет это за одну ошибку в позиции $6$ и инвертирует третий бит. После «исправления» проверки пройдут, но данные могут быть другими. Две одиночные ошибки в двух **разных** словах, напротив, можно исправлять независимо.

### Что делает конкретный код

В `Coder::GetBlock` биты байта читаются от старшего к младшему. В `EncodeBlock` позиции, не являющиеся степенями двойки, заполняются данными, а проверочные биты рассчитываются отдельными проходами. В `DecodeBlock` нарушенные проверки объединяются через `syndrome |= p_pos`. При ненулевом синдроме внутри слова декодер инвертирует указанный бит, а при синдроме за границей слова выставляет ошибку. Это способ заметить **часть** повреждений. Дополнительной проверки общей чётности всего слова в этом декодере нет.

Например, фиксированный блок заголовка $4\to 8$ сам по себе не доказывает, что это расширенный SECDED $(8,4)$. В этом коде позиция $8$ участвует как обычная проверка с маской $8$. Для стандартного расширенного кода дополнительный бит имеет другую задачу: обеспечивает чётность **всего** кодового слова.

| Синдром обычных проверок | Общая чётность SECDED | Действие при не более чем двух ошибках в слове |
|---|---|---|
| Нулевой | Чётная | Ошибок нет |
| Ненулевой | Нечётная | Исправить одиночную ошибку по синдрому |
| Нулевой | Нечётная | Исправить дополнительный бит общей чётности |
| Ненулевой | Чётная | Обнаружены две ошибки, сообщить о невозможности однозначного исправления |

Нулевой синдром означает, что соответствующие проверки прошли. Без предположения о числе ошибок он не гарантирует, что слово совпадает с исходным. Поэтому на защите называйте гарантию **на одно кодовое слово**, версию кода и отдельно поведение для обрезанного архива. Потеря байтов сдвигает границы слов или оставляет запись неполной. Исправление инверсии бита эту задачу не решает.

Источники: [коды Хэмминга](https://en.wikipedia.org/wiki/Hamming_code), [разбор SECDED](https://robotics.ucsd.edu/rr_chap13.pdf).

### Задачи на трассировку и проверку проекта

1. **Последняя порция.** Файл имеет $600$ байтов, буфер — $256$. Сколько байтов вернёт `gcount()` при каждом чтении? Сколько потеряет цикл `while (input.read(buffer, 256))`, если обрабатывает данные только внутри тела?
2. **Формат.** Нужно положить в архив файл с пробелом в имени, затем пустой файл. Назовите, как парсер получит имя, как формат отделит его от размера и как декодер остановится перед следующей записью.
3. **Одна и две инверсии.** Для слова из семи битов найдите синдром после инверсий в позициях $3$ и $5$. Что сделает декодер? Как построить похожий тест, где обе инверсии должны исправиться?
4. **Выход за пределы формата.** Указанный размер записи больше оставшихся данных. В какой момент это можно заметить? Почему простой успех `seekg` не доказывает, что пропущенные байты были на диске?
5. **Ошибка при обновлении.** При удалении файла закончилось место на диске во время записи временного архива. Какое состояние должно остаться после отказа? Назовите момент, когда можно заменить оригинал.

### Ключ к трассировке

1. Три чтения дают $256$, $256$ и $88$ байтов. При очередной попытке чтения после третьей получим $0$. Условие, проверяющее успех полного `read`, не пропустит третью порцию в тело, поэтому потеряются $88$ байтов.
2. Кавычки сохраняют имя одним элементом `argv`. Формат может хранить длину имени и сами байты. Для пустого файла исходный размер равен нулю, у его записи нет закодированной полезной части. По длине закодированных данных читатель переходит к следующему заголовку.
3. $3\oplus5=6$. Декодер перевернёт ещё бит $6$. Для гарантированного исправления двух инверсий выберите по одной известной позиции в двух разных кодовых словах и сравните извлечённый файл с оригиналом.
4. Сопоставьте длину записи с доступными байтами, используя проверенную арифметику, или потребуйте полного чтения каждого поля и блока. Позиционирование может допускать смещение за концом файла. Проверять надо и позицию, и границы формата.
5. Оригинал остаётся доступным, ошибочная временная копия не должна стать итогом операции. Замену делают после успешной записи, проверки состояния и закрытия временного файла. Отказ замены тоже нужно сообщить.

### Как проверять архиватор

Тест `CreateAndExtractAndCompare` запускает CLI, меняет отдельные биты при помощи маски XOR и сравнивает извлечённые файлы с оригиналами. Координаты берутся по байтовым смещениям. Для целевого теста гарантии полезно выбрать позиции по известным границам кодовых слов. У теста с тремя инверсиями на разных смещениях своя проверяемая конфигурация. Из его прохождения нельзя вывести исправление трёх ошибок в одном слове.

| Сценарий | Что проверять |
|---|---|
| Круговой проход `create → extract` с одним и несколькими файлами | Совпадают имена, число байтов и содержимое каждого файла. |
| Пустой файл, байты со значением ноль, длины около границы буфера и кодового слова | Сохраняются хвост, нулевые байты и границы соседней записи. |
| Одна инверсия в данных, отдельно одна в защищённом заголовке | Известный повреждённый бит исправляется, исходные данные совпадают. |
| Две инверсии в разных словах | Оба слова восстановлены. |
| Две инверсии в одном слове при SECDED | Ошибка сообщена, испорченный результат не выдан за успешное восстановление. |
| Обрезанный заголовок или неполные данные | Чтение завершается с сообщением об ошибке. |
| Добавление, удаление, выборочное извлечение и объединение | Затронуты нужные записи, остальные читаются с прежним содержимым. |
| Неверные параметры, отсутствующий вход, ошибка записи | Ненулевой код завершения и понятная диагностика. |

В GTest `ASSERT_...` прерывает текущую функцию при провале, `EXPECT_...` позволяет выполнить последующие проверки. Успешное открытие файла лучше сделать обязательной предпосылкой сравнения. Для воспроизводимости задавайте содержимое, размеры и места инверсий явно. Тесты алгоритма на одном слове локализуют проблему в кодере, а тесты через CLI дополнительно проверяют парсер, формат и файловые операции. [Документация GoogleTest](https://google.github.io/googletest/primer.html).
