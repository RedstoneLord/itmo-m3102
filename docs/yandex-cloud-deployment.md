# Размещение М3102 в Yandex Cloud без GitHub API в браузере

План актуален на 23 сентября 2026 года. Деплой не выполнен: потребуется платежный аккаунт Yandex Cloud и доступ к его каталогу.

## Цель и текущая точка

Сайт статический. Сейчас каталог материалов и список конспектов читаются из GitHub API, файлы — с `raw.githubusercontent.com`, а общая очередь дедлайнов — из GitHub Issues. Расписание встроено в `index.html`, дедлайны лежат в `Дедлайны/deadlines.json`, личные задачи хранятся в `localStorage`. Перенос одного HTML-файла в Object Storage **не уберёт** зависимость от GitHub API: сначала нужно заменить источники данных в коде.

Публичные файлы репозитория сейчас занимают около **85,7 МиБ** (47 файлов); самая крупная запись лекции — **62,6 МиБ**. Это укладывается в бесплатный объём хранения, но трафик от аудио необходимо измерять.

## 1. Убрать GitHub API из статической части

1. Добавить сборочный скрипт `scripts/build_static.py`, который читает отслеживаемые Git-файлы и выпускает каталог `dist/`. Он копирует HTML, CSS, `Дедлайны/deadlines.json`, конспекты, PDF, DJVU, DOCX и аудио, но исключает `.git`, тесты и документы для разработки.
2. Во время сборки создать `dist/catalog.json`: массив `{path, name, size, type, updated}`. Для `updated` брать дату последнего коммита файла через локальный `git log`, а не запрашивать GitHub при открытии сайта. Путь в JSON должен оставаться относительным и проходить URL-кодирование по сегментам, чтобы кириллица и пробелы работали.
3. В `index.html` заменить `apiUrl()` и запрос `/contents` чтением `./catalog.json`. Папки показывать как группировку по `path`. `fetchRecentNotes()` сортировать по `updated` из того же файла. `rawUrl()` заменить ссылкой на файл с того же домена. PDF и Markdown должны продолжить открываться во встроенных просмотрщиках.
4. Оставить `Дедлайны/deadlines.json` и расписание статическими; личный план в `localStorage` не требует сервера. При ошибке `catalog.json` показать понятное состояние и кнопку повторной загрузки.
5. Проверить вкладку Network: при переходах по каталогу, конспектам и PDF нет запросов к `api.github.com` и `raw.githubusercontent.com`. Запросы к CDN библиотек можно сохранить или позднее положить библиотеки в тот же бакет.
6. До смены адреса добавить экспорт и импорт личного плана в JSON: `localStorage` привязан к домену, поэтому отметки с текущего сайта не появятся автоматически на новом адресе. Сначала дать пользователям скачать свой план, затем импортировать его на Yandex Cloud.

## 2. Опубликовать статическую версию в Object Storage

1. Создать отдельный каталог/платёжный аккаунт и бакет класса `STANDARD` с уникальным именем **без точки**, например `m3102-study-<суффикс>`. Для такого бакета Yandex Cloud даёт HTTPS на `https://<bucket>.website.yandexcloud.net` без собственного сертификата. Включить ограничение размера бакета около 1 ГБ, чтобы ошибка сборки не заполнила платное хранилище.
2. В настройках бакета открыть публичное чтение файлов и включить режим **Веб-сайт → Хостинг**, главная страница `index.html`, страница ошибки `index.html` либо отдельный `error.html`. В бакет не загружать секреты, `.git`, приватные документы и исходные ключи. Публичный список объектов включать только если этого требует выбранная конфигурация хостинга; сам каталог сайт получает из `catalog.json`.
3. Создать сервисный аккаунт для загрузки с минимальными правами на бакет и статический ключ. Не вставлять ключ в JavaScript или репозиторий. При автоматизации хранить ID и секрет ключа в GitHub Actions Secrets.
4. Для первой публикации собрать `dist/` и загрузить его через AWS CLI:

   ```bash
   python3 scripts/build_static.py
   aws --endpoint-url=https://storage.yandexcloud.net s3 sync dist/ s3://<BUCKET>/
   ```

   Для повторной синхронизации использовать `--delete` только после проверки состава `dist/`, иначе он удалит опубликованные файлы, которых случайно не оказалось в сборке. Настроить MIME-типы для HTML/CSS/JS/JSON/PDF/MP3 и короткий кэш для `index.html`, `catalog.json`, `deadlines.json`; для неизменяемых медиа возможен долгий кэш.
5. Проверить HTTPS-адрес: главная, `/Дедлайны/`, навигация по папкам, русские пути, чтение Markdown/PDF, аудио, дедлайны, мобильная верстка и обновление страницы на вложенном URL. Только после проверки направлять пользователей на новый адрес.

## 3. Перенести общую очередь дедлайнов

GitHub Issues сейчас даёт очереди общий сервер и порядок участников. Статический бакет не может принимать заявки. Чтобы полностью отказаться от GitHub API, использовать **одну публичную HTTPS Cloud Function** и **YDB Serverless**; API Gateway для такого маленького интерфейса не обязателен.

1. Создать YDB Serverless с таблицей `queue_entries`: `deadline_id`, `entry_id`, `name`, `created_at`, `status`. Порядок выдачи — `created_at, entry_id`. Ограничить максимальный объём БД и пропускную способность; не включать выделенную пропускную способность с отдельной оплатой.
2. Создать сервисный аккаунт функции с доступом только к этой БД. HTTPS-функция обрабатывает `GET` списка по дедлайну и `POST` заявки. `deadline_id` сверяется с допустимыми ID из `deadlines.json`; имя ограничивается по длине и очищается при выводе; тело запроса ограничивается по размеру. Возвращать CORS только для адреса сайта и обрабатывать `OPTIONS`.
3. Для публичной формы предусмотреть защиту от спама: минимум ограничение частоты/дубликатов и модерацию; при открытом доступе можно добавить SmartCaptcha с проверкой токена **на сервере**. Её первые 10 000 проверок в месяц входят в free tier, далее она платная. Не хранить ключ сервера в HTML. Для удаления ошибочных заявок сделать отдельное административное действие, закрытое IAM/авторизацией.
4. В `Дедлайны/index.html` заменить `loadQueues()` и `joinUrl()` на обращение к функции. При сбое функции сроки остаются видимыми, очередь показывает ошибку. Отключить минутный опрос, если он расходует лишние вызовы; обновлять по кнопке или при возвращении вкладки.
5. Перенести действующие открытые записи GitHub Issues **один раз**, проверив имена и порядок, затем закрыть старый приём заявок. После этого в Network не должно быть запросов к GitHub API и ссылка «В очередь» не должна вести на GitHub.

## 4. Автоматизировать обновления

После merge в `master` GitHub Actions может запускать тесты, собирать `dist/` и выполнять `aws s3 sync` с ключом из Secrets. GitHub здесь остаётся хранилищем исходников и местом сборки, **но браузер посетителя не обращается к GitHub API**. Если не хотите зависеть даже от GitHub Actions, тот же сборочный скрипт и команду синхронизации запускайте локально. Дедлайны обновляются изменением JSON в репозитории и новой синхронизацией.

Для безопасного релиза: сначала проверить сборку и ссылку на бакет, затем обновить адрес в навигации/описании репозитория. Предыдущую рабочую версию `dist/` хранить отдельно как архив для отката; версионирование всего бакета может увеличить платный объём.

## 5. Контроль расходов и условие «бесплатно»

По опубликованным тарифам Object Storage ежемесячно не тарифицирует первые **1 ГБ хранения STANDARD**, **10 000 операций записи/списка**, **100 000 операций чтения** и **100 ГБ исходящего трафика**. Текущий сайт (~86 МиБ) проходит по хранению; однако одна запись лекции ~62,6 МиБ, поэтому порядка **1,6 тыс. полных прослушиваний** уже могут израсходовать весь месячный бесплатный исходящий трафик без учёта остальных файлов. Для очереди free tier: Cloud Functions — 1 млн вызовов и 10 ГБ×час, YDB Serverless — 1 млн RU и 1 ГБ хранения, SmartCaptcha — 10 тыс. проверок в месяц. Лимиты общие для платёжного аккаунта, а превышение оплачивается.

Создать уведомления бюджета и мониторить хранение, операции, исходящий трафик, вызовы функции и RU YDB. **Бюджет присылает уведомления, но не останавливает расходы автоматически.** Для строгого нулевого риска нельзя обещать полностью бесплатную работу публичного сайта: на входящий трафик и вызовы могут повлиять скачивания и боты. Сдерживать риск помогают ограничение размера бакета, лимиты YDB, отсутствие постоянной ВМ/CDN и отключение лишнего опроса.
